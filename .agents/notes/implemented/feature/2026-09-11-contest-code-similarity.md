# Agent Note: 竞赛代码相似度检测

Status: implemented

## Problem

2026-09-05 的竞赛作弊面审计把「代码相似度检测」列为 Phase 2 防作弊路线图中**唯一完全空白**的项。
当时 `contest-anti-cheat.ts` 仅有 IP 分组与时间线（`listContestIpGroups` / `listContestIpTimeline`），
没有任何代码层面的抄袭线索能力：管理员面对「两人解法高度雷同」的怀疑时只能人工逐份比对源码。

需求约束：
- 不能引入重型依赖（AST 解析器 / 外部服务）——须在 noj-core 内纯 TypeScript 实现；
- 必须能容忍**变量改名、注释增删、空白变动、文档字符串**这类最常见的「洗稿」手法；
- 必须**不误报**真正不同的解法（误报会让管理员浪费大量时间并伤害选手）；
- 结果只能作为**人工复核线索**，不得自动判罚。

## Decision

实现「token 归一化 + winnowing 指纹 + Jaccard 相似度」，k=5、window=4、默认阈值 0.8。

**归一化**（`normalizeCode`）：按语言轮廓剥注释（`//` `#` `--` `%` `/* */` `(* *)` `{ }`）
与字符串/字符字面量（统一占位符）、Python 三引号整体剥除（连占位符都不留，
避免插入文档字符串凭空制造 token 差异）、压掉全部空白换行、用户自定义标识符按
**首次出现顺序**位置化改写为 `v1..vN`（语言关键字与精简的高频内建白名单除外）。
采用**单趟状态机扫描**而非「先剥注释再剥字符串」的两趟正则，以避免
`char *s = "http://x";` 这类交叉误判。

**指纹**（`fingerprint`）：winnowing 取每个窗口内哈希最小的 k-gram，得到指纹集合。

**取 k=5**：语句级结构约 5–7 token；k 过大（≥10）会让短解法完全无指纹，
k 过小（≤3）会让 `= 0 ;` 之类片段大量碰撞、抬高误报。
**取 w=4**：这是论文保证区间下沿——「长度 ≥ k+w-1 = 8 token 的公共片段必定留下公共指纹」。
实测 w=6/8 会让最难的同思路独立实现（两份 DP）从 0.2653 升到 0.3056/0.4583，
区分度反而变差，故取 4。

**规模限制**：默认上限 200 份候选提交，超出时**抛** `BadRequestError`
（`SIMILARITY_SCALE_EXCEEDED`，`meta` 带 `candidates` / `max_submissions`）**而非静默截断**。
静默截断会让管理员把「没算到」误读成「没有相似提交」——对风控功能而言这是危险的误导。
计算在请求线程同步执行（未入队列），200 份病态输入实测 1.8s / 50MB，故默认收敛到 200，
大场次引导用 `problem_id` 逐题分析。先按「题目 × 语言」分桶 + 指纹长度比剪枝。

**取数口径**：`contest_id` + `status='finished'` + `artifact_storage_url IS NULL` + 代码非空白；
默认跳过同一用户的两次提交（同用户自比无意义）。

**权限**：复用既有 `contest:anti_cheat_read`（与 `ip-groups` / `timeline` 同口径），
不自创权限。响应只含提交标识/用户/题目/语言/相似度/指纹统计，**不含源代码**，
并显式标注 `data_policy.automated_penalty = false`。

## Alternatives considered

- **AST / 控制流归一化**：判别力更强（能识别结构等价改写），但需要每种语言的解析器，
  与「不引入重型依赖」冲突，且语言覆盖会长期不完整。token 级方案对改名的鲁棒性已足够。
- **编辑距离 / 最长公共子序列**：O(n²) 且对局部改写极敏感；改名会显著拉低相似度，
  正是本题要检出的手法。
- **数字字面量一并归一化**：会让「range(10) 改成 range(1000)」也命中。
  选择**不归一化**以保住这层区分度，代价是「只改常量」的抄袭会漏报（漏报而非误报，可接受）。
- **规模超限时静默截断**：实现更简单，但会让管理员误以为已全部分析。选择显式报错。
- **写入数据库缓存结果**：需要新表 + 迁移 + 失效策略，而本功能是低频人工复核场景，
  每次按需计算（毫秒级）足够，不值得引入状态。
- **自动判罚**：审计明确本功能只提供线索；自动判罚的误报代价过高，且需申诉流程配套。

## Consequences

- 相似度是**线索而非结论**：响应固定带 `data_policy.automated_penalty: false`，
  管理端不得据此自动取消成绩。
- **位置化改写对「在代码前部新增标识符」敏感**：后续编号整体后移，会让插入点之后
  区域的指纹失配（漏报，不是误报）。已在 `canonicalizeIdentifiers()` 的 JSDoc 中记录，
  替代方案是对标识符按出现顺序之外的信息（如用法）聚类，复杂度显著上升，暂不采用。
- 「只改常量」的抄袭会漏报（见 Alternatives）。
- 大场次（单题 >200 份提交）需按 `problem_id` 分次分析；上限可通过 `options.maxSubmissions`
  提高，代价是请求线程的同步 CPU 时间。
- 计算仍在请求线程同步执行。若未来出现大规模使用需求，应移入 worker/队列
  （届时需配套任务状态与结果缓存）。
- 测试从「实现细节」层面锁定了判别力数值：雷同（改名/注释/空白/文档字符串）= 1.0000、
  不同实现 ≤ 0.0217、最难同思路 DP = 0.2653。若有人调整 k/w/归一化策略，这些断言会失败，
  迫使重新评估阈值。

# Agent Note: 公测上线优先 Issue 收口

Status: implemented

## Problem

公测前的运维与体验整改中，#428 的隔离恢复已证明 RTO 达标，但备份调度缺失导致 RPO 仍为 161.46 小时；#432 的启动门槛、练习公测和生产建议口径不一致；#453 的社区搜索保留 `ILIKE` 语义却缺少与查询表达式匹配的 trigram 索引；#434 已有静态题包检查，但不能把静态结构误认为真实 Judge 验收。

## Decision

- #428：新增 `backup schedule install/status/remove`，只维护带标记的 cron 区块，使用绝对路径、受保护的口令文件和独立日志；不在 core 进程内隐式创建宿主机调度。
- #432：将 README、安装器和生产部署文档统一为“启动/诊断、低并发公测、正式生产”分层，并新增固定变量、场景、指标和扩容触发条件的容量报告模板。
- #453：按迁移规范生成新编号迁移，为公开题解/讨论的标题和正文追加部分 trigram GIN 索引；PGlite 没有 `pg_trgm` 时，测试 DDL 检测扩展后跳过，生产 PostgreSQL 仍执行迁移。
- #434：新增评测包结构预检，阻断缺少入口或可见样例的包，缺少隐藏样例/标准解或尚未执行 Judge 时给出警告；不虚构不存在的标准解接口，也不把此阶段标记为完整可执行验收。

## Alternatives considered

- 在 noj-core 内部实现备份调度：会把宿主机 cron、权限和进程生命周期耦合进业务服务，故未采用。
- 在 PGlite 中强行创建 `gin_trgm_ops`：会使全部测试数据库初始化失败，故改为能力检测；真实索引由 PostgreSQL 迁移验证。
- 仅凭 `evaluate.py`、样例和隐藏文件存在就允许题目发布：无法证明标准解可运行、隐藏标记不泄漏或容器能清理，故保留运行时验收缺口。

## Consequences

- 备份调度具备可安装、可查看、可移除和重复安装不重复的自动化能力；当前工作区没有生产 `.env.prod`、口令文件和可直接连接的预发布快照，因此无法在本地安全替代真实 RPO 验收。#428 仍需在等价预发布/生产环境安装调度后执行一次脱敏恢复报告，才能关闭。
- #432 的文案与报告框架已统一，但当前没有固定 Release、硬件、Judge 并发、提交速率和 LLM 配置组成的公测场景，尚未替代真实容量压测，不能据此承诺公测规模。
- #453 的临时 10 万行 PostgreSQL 基准中，中文选择性查询从 FTS-only 的 P50/P95 241.52/268.20ms 降至 trigram 后的 0.10/0.12ms，计划从 Seq Scan 变为 BitmapOr；该结果是当前开发数据库的可复现实验，不是生产容量结论。
- #434 的静态门禁、出题人文档和测试已落地；当前题包模型没有统一的标准解入口/期望评分契约，且没有在该预检接口内安全调度 Judge 的执行协议，因此标准解执行、隐藏标记泄漏检查、超时/资源限制/清理及发布状态绑定仍需先确定契约并接入现有 Judge/self-test 链路后再关闭 Issue。

# Agent Note: 教学持久事件重复、乱序及真实进程重启恢复验收

Status: implemented

## Problem

教学消费者的单元测试不能证明部署中的 core 进程会启动后台任务，或停机后仍能
处理数据库积压。读取小范围进度接口可能同步补算投影，如果仅调用该接口判断
恢复，就会把 HTTP 修复误认为后台消费者成功。

## Decision

新增独立 `cross-domain/education_outbox_recovery.test.ts`，在隔离 E2E 栈执行：

- API 建立普通教师、学生、教育域、班级和已发布作业。加法题复用真实 v2 题包
  夹具，通过公开分享在学校使用。学生两次代码提交经过真实 Judge，先零分，
  作业实际结束后再取得 10 分。
- 通过真实绑定策略 API 切换 `exact(V1)`。直接只读数据库观察正式评测尝试与
  `assignment_progress`；按时范围保留第一份零分及尝试，补做范围采用第二份
  满分及尝试，比较真实受理时间和实际结束时间。
- 从真实 `submission.changed` 记录复制定位，保留原创建时间和业务定位，
  删除消费者游标，使用生产已有的 `_invalidate_on_claim` 到期失效机制。
  新事实的定位先交付完成，旧定位随后交付两次。每批均等待真实后台
  `processed_at`，核对两个投影单元 ID、来源提交、尝试、版本、当前策略、
  分数和逾期标记不变，同时投影 revision 实际增长。
- 通过 Docker 停止精确的 `noj-e2e-core`，在停机期间写入两条待消费定位记录。
  确认无租约、未处理、原投影未变后启动 core，等待真实健康响应。核对新 PID
  和启动时间，并先通过数据库确认后台完成及投影 revision 增长；最后才调用
  授权进度接口核对展示。
- Judge 和 Gateway 前后 PID、启动时间保持一致；异常路径的 finally 恢复 core
  并等待健康，不重建数据库或清理 Redis。

SQL 写操作仅登记持久事件交付元数据，不写评测尝试、提交成绩、业务时间或
`assignment_progress`。不同交付记录拥有不同事件 ID，验证的是重复定位交付
和乱序重算；没有声称重复使用同一租约或事件 ID 的崩溃重投已经实测。

## Alternatives considered

- 通过进度 REST 请求反复读取恢复：小范围同步修复可能掩盖后台问题，先以
  只读数据库和事件处理状态作为证据。
- 手写成绩与投影：跳过真实 Judge、受理时间和策略，因此采用实际零分与满分。
- 修改作业时间或让旧成绩载荷直接覆盖投影：不符合确认规则，作业通过正式 `/end`
  操作结束，事件只提供事实定位。
- 调用模块 worker 函数模拟重启：仍属于进程内测试，采用容器真实停止和启动。

## Consequences

2026-10-13 在 `noj_upgrade_acceptance_e2e_20261013`、Redis DB 2 执行标准
`deno task test:domain cross-domain --no-lock --filter=education-outbox-recovery`，
结果 **1 passed（4 steps）、0 failed、54 filtered out，12 秒**。 日志为
`/tmp/noj-client-education-recovery.log`。格式、lint、标准跨模块目录 类型检查和
Agent Note 格式通过。使用固定版本 postgres 驱动，执行参数 `--no-lock`
不改其他模块锁文件。

正常正式判定到两种投影更新的一个实际样本为 **1216ms**，满足 5 秒目标。 从启动
core 到健康并消费积压的实测时间为 **2287ms**，单独记录，不把它作为
正常评测延迟样本。core PID 从 **259092** 变为 **348047**，启动时间从
`2026-10-13T10:41:38.669635277Z` 变为 `2026-10-13T11:09:28.471874383Z`。
停机积压两条事件在新进程中完成，Judge 和 Gateway 没有重启。

此场景是一名学生、一题、两个真实提交的后台恢复验收，不代替 40×5 题型闭环或
大矩阵性能测试。没有模拟进程在持有租约时崩溃、租约超时或 Redis 故障；这些
限制与已有单元和独立连接测试分开记录。其余 54 项未在本次过滤执行中重跑。

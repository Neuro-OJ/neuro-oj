# Agent Note: 0.9.5 稳定版发布准备

Status: implemented

## Problem

SNG 当前运行 `v0.8.1`，需要一个可被生产安装器识别的稳定版本；直接使用尚未完成真实
预发布验收的 1.0 RC 会混淆版本承诺，且发布镜像的基础系统与构建依赖可能滞后于安全修复。

## Decision

基于最新 `main` 创建 `v0.9.5` 发布分支，统一各模块版本元数据，补齐 UI 类型导入，
并通过 Release workflow 的预发布触发机制构建镜像、CLI 资产、校验文件和安全证明，
由工作流在资产全部就绪后自动转正。运行镜像安装 Debian 安全更新；LLM 网关不再把仅
用于数据库生成的 drizzle-kit/esbuild 构建依赖带入生产依赖图；Release workflow 只监听
prereleased，避免同一预发布事件重复触发并竞争不可变镜像标签。为处理历史失败流水线
已经写入的同版本 GHCR 标签，另加了显式手动的清理入口；普通流水线不会执行该入口。

## Alternatives considered

- 直接把 `v0.9.5` 标记到现有 `main`：会保留版本不一致和 UI 检查失败，未采用。
- 直接发布正式 Release：会绕过工作流的构建与安全门禁，可能产生没有同版本镜像或 CLI
  资产的 Release，未采用。
- 仅重跑原流水线：无法消除已确认的 PCRE2、Go stdlib 和 esbuild 高危扫描结果，也无法
  解决重复触发造成的镜像标签竞争，未采用。
- 直接覆盖 GHCR 正式标签：会破坏不可变标签保护，未采用；改为显式清理历史失败残留后
  重新构建。

## Consequences

`v0.9.5` 已完成正式 Release，包含 7 个通过安全门禁的 amd64 镜像和 `noj-cli` Linux
amd64 资产；本次未发布 VS Code `.vsix`，插件仍需单独纳入资产流程。SNG 升级前仍需
确认备份口令、执行备份并安排维护窗口，且当前 SNG 资源低于正式生产建议。

# Agent Note: 生产更新流程可靠性修复

Status: implemented

## Problem

真实生产升级暴露出多个部署工具问题：已有安装同步文件时误把 NOJ 自身监听端口判为冲突；PostgreSQL dump 校验向容器内的 `pg_restore` 传递了错误的输入参数；一键安装没有准备升级备份所需的 GPG 口令；应用容器重建后 Nginx 仍可能使用旧容器地址；更新同步过程还可能覆盖正在执行的 bootstrap 文件并执行错误的安装收尾流程。

## Decision

部署文件同步模式跳过宿主机端口占用检查，首次启动仍保留端口门禁；PostgreSQL 备份校验改为通过标准输入传递 dump；安装、升级和手动备份在缺少口令文件时自动创建仓库外的受限随机口令文件，并只在配置中保存路径；Compose 健康检查后强制刷新 Nginx；`noj update` 使用临时 bootstrap 副本同步 Release 文件，避免自覆盖。

## Alternatives considered

- 只在 `sng` 上手工修改脚本：见效快，但会造成生产环境偏离 Release，后续更新会复发。
- 跳过升级前备份：可以绕过当前阻断，但会失去数据恢复门禁，风险不可接受。
- 让 Nginx 继续缓存上游地址：依赖容器网络实现细节，升级后仍可能出现 502，因此选择在服务健康后刷新代理。

## Consequences

一键安装和后续升级不再要求人工先创建口令文件，但运维人员必须异地保存自动生成的口令文件。更新流程会额外重建一次 Nginx 容器，不触碰数据卷。现有生产安装需要通过新 Release 获取这些修复，当前 `sng` 上的临时口令文件仍需保留。

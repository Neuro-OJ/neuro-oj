# Agent Note: 提交类 IP 限流按机房席位放大，低风险写入在 Redis 故障时放行

Status: implemented

## Problem

Issue #698 P0 指出 hardening 限流有两处会直接影响考试与教学可用性：

1. 代码提交、竞赛提交、客观题提交的 IP
   阈值与用户阈值相同（120/120、120/120、60/60），自测 IP 阈值
   30/分钟。学校机房整间共用一个 NAT 出口时，60 人集中交卷或自测会被 IP
   维度拒绝；而 IP
   阈值等于用户阈值时，对单个攻击者没有任何额外约束。项目此前已因同样的 NAT
   误伤下线过提交来源 IP 反作弊（VULN-06）。
2. `enforceRateLimit` 在 Redis 不可用时一律
   fail-closed（503）。点赞、收藏、关注、举报、教学写操作、创建题目这类被绕过也没有实际代价的写入，会在
   Redis 抖动时与认证、提交一起整站不可用。

## Decision

1. 新增 `SHARED_IP_SEATS = 60`，四类面向考生的接口 IP 阈值改为「用户阈值 ×
   席位数」：提交与竞赛提交 7200/分钟，客观题 3600/分钟，自测
   240/分钟。用户维度阈值不变，仍是单人上限。
2. `enforceRateLimit` 增加第四个参数 `onUnavailable: "reject" | "allow"`，默认
   `reject` 保持原行为。只有 `ServiceUnavailableError` 才会被 `allow` 吞掉并记
   warn，超限 429 与其他错误照常抛出。
3. 帖子/评论点赞、收藏、关注、举报、每日签到、教学写窗口、创建题目改用
   `allow`；注册、密码找回、验证邮件、邮件投递回执、私信、各类提交、自测、升级任务、
   题目导入保持 `reject`。判断标准是被绕过时是否产生评测算力、邮件、存储或垃圾内容等
   实际代价。签到与邮件回执的限流由 rc/v0.11 同期新增，合并时按同一标准归类：签到按天
   幂等，被绕过没有收益；邮件回执是公网回调入口。
4. 实现拆出 `enforceRateLimitWith(check, ...)`，计数函数可注入，使 Redis
   故障分支无需真实断开 Redis 即可测试；它不经模块门面导出。
5. 同步更新 `dev-docs/engineering/write-rate-limit-matrix.md` 的阈值表，新增「IP
   维度与机房 NAT」「Redis 故障策略」两节。

## Alternatives considered

- 把 IP
  阈值做成系统设置：管理员需要先知道问题才会去调，默认值仍会误伤首次使用的学校；且每个阈值多一个配置项会扩大误配面。固定倍数加文档说明更直接，需要时再提升为配置。
- 直接删除提交类的 IP 维度：仍需要一个兜底来拦截单 IP
  批量注册小号刷评测的情况，放大阈值保留了这层保护。
- 全部限流改为
  fail-open：提交、自测、导入被绕过会直接消耗评测与存储资源，认证类被绕过会放大撞库风险，因此只对低风险写入放行。
- 登录 IP
  限流（30s/10）同样有机房问题，但它已是后台可热改的系统设置，且涉及撞库防护取舍，本次不改默认值。

## Consequences

- 同一机房的正常考生不再因 IP 维度被拒；单 IP 刷量的上限变为原来的 60
  倍，但单账号上限不变。
- Redis 故障期间，低风险社区与教学写入不再受限流保护，日志中会出现
  `限流服务不可用，低风险写入按放行策略处理` 告警，可据此发现 Redis 故障。
- 新增面向考生的写端点时，需按矩阵文档选择 IP 倍数与故障策略。

# Agent Note: `problem init` 引导的 EOF 挂死与输入终止语义

Status: implemented

## Problem

`problem init` 的交互引导（#514 交付）有三个问题，其中第一个是**真实挂死**：

1. **EOF 导致无限循环并把进程堆吃满**。引导里 slug 的校验写作

   ```ts
   for (;;) {
     const raw = await input(io, "题目 slug（…）");
     if (SLUG_RE.test(raw)) { slug = raw; break; }
     io.write("slug 非法：…\n");
   }
   ```

   而 `PromptIO.readLine` 在**输入结束时返回空串**（`realIO` 读到 EOF 正是这条
   路径），空串永远不匹配 slug 正则。于是用户按 Ctrl-D 会看到 "slug 非法" 被
   **无限重复**，输出不断累积，最终 Deno 报
   `Fatal JavaScript out of memory: Ineffective mark-compacts near heap limit`。
   本会话在跑测试时**真实触发过一次**（进程核心转储）。

   根因不是校验规则，而是**假定了输入总会到来**——`PromptIO` 的契约里没有
   "没有更多输入"这个概念，等待输入的循环因此没有终止条件。

2. **回退无法表达**。R6 明文要求引导"含校验与回退"，而原实现只有"确认取消"。
   `select` 也只接受合法编号，调用方想实现"退回上一步"只能靠抛异常——那会让
   "回退"与"出错"在调用方无法区分。

3. **进度不可见**。多步提问没有 `[2/4]` 之类的提示，用户在只答两项时不知道自己
   还要答几项。

## Decision

1. **给"输入终止"一个有界语义**（`MAX_ATTEMPTS_PER_FIELD = 8`）。任一字段连续无效
   （含空输入）超过上限即**明确报错**，错误文案同时说清三件事：发生了什么（EOF 或
   连续无效）、卡在哪个字段、以及**可直接粘贴的自动化命令**
   （`noj-cli problem init --slug <slug> --type P --no-interactive`）。

   **上限取 8 而不是 3**：上限的唯一目的是"有限次后结束"，设小会把"边想边改"的
   正常用户踢出去——那是用错误的方式修 bug。8 次之内终结挂死，同时几乎不可能
   误伤真人。

   **为什么不把空串当"用户直接回车"放过**：这两者在 `readLine` 的返回值上
   **不可区分**，而放过会让 slug 变成空串（非法且有害的目录名）。与其猜，
   不如报错——错误信息里说清发生了什么以及怎么绕开。

2. **`select` 增加 `backWords` 与 `defaultIndex`**（`tui/widgets.ts`）：
   - `backWords` 命中即返回 **-1**，让"回退"成为类型可表达的结果；
   - `defaultIndex` 让回车接受默认项——这既补上"空输入无落点"（EOF 下
     `select` 原本也会无限重问），也符合引导文案里早就写着的"回车取默认"。

   两个选项都是**可选**的，因此既有调用点零改动；`maxAttempts` 缺省不设上限，
   保持既有语义。

3. **slug 字段的回退只认 `:b`，不认 `back`**：`back` 本身是**合法的 slug**
   （4 个小写字母），把它当回退会夺走一个合法的题目名。歧义时优先"输入即数据"，
   回退只认不会与数据冲突的带前缀形式。测试对这个取舍有**正反两条**断言。

4. **进度提示取自 `planInitPrompts`**（不硬编码 4）：已由旗标给出的字段不参与
   计数，否则只答两项却看到 `[1/4]` 会让人困惑。

5. **`title` 改为自己读原始行再判回退**。这是实现过程中实测踩到的第二处问题：
   `input(io, prompt, def)` 会把空输入替换成默认值，而当默认值（= slug）恰好是
   `back` 时，一次**普通的回车**会被误判成回退——调试输出里 `Q:标题 [back] => ''`
   紧接着又出现 `Q:slug` 一目了然。修法是"读原始行 → 判回退 → 空串才落默认值"。

## Alternatives considered

- **给 `PromptIO.readLine` 加 EOF 信号（返回 `string | null`）**：语义最干净，
  但要改动 `tui/io.ts`、`realIO`、`widgets.ts` 与全部既有 fake——而 R6 并未要求
  这一层重构。当前的字段级上限以**远小得多的改动面**达到同一效果（有限次后结束），
  且对既有调用方零影响。
- **把连续空输入的上限设小（3）**：会把"打错两次再想一下"的正常用户踢出引导，
  体验倒退。上限的语义是"保证终止"，不是"限制耐心"。
- **slug 也接受 `back` 作为回退**：会夺走合法的题目名 `back`。改用 `:b` 后
  两者都能表达。
- **用抛异常表达回退**：调用方无法区分"用户想回退"与"引导出错"。`select`
  返回 -1 是类型层面的区分。
- **在引导失败时返回部分答案让调用方兜底**：会让"生成了不完整的骨架"成为可能，
  而骨架一旦落盘就难以察觉缺了什么。明确报错更安全。

## Consequences

- **EOF 不再挂死，且有可回归的证据**：测试用"脚本用尽后恒返回空串"的 fake 断言
  (a) 必然抛错、(b) **提问次数有上界**、(c) 文案含自动化旗标。这条用例在修复前
  会以 OOM 结束——它是那种"不写就会被真实用户按出来"的缺陷。
- **20 个用例**覆盖 R6 三条验收：覆盖/校验/回退、非 TTY 语义（由既有
  `problem_test.ts` 覆盖用法错误路径）、以及**端到端**"引导答案 → 生成骨架 →
  通过 `problem lint`（零 error）"。
- **`select` 的行为对既有调用方不变**：新选项全部可选，`maxAttempts` 缺省无上限。
- **回退与"输入即数据"的冲突有明确规则**：`back` 在 slug 处是数据、在其它字段是
  回退指令。这条规则写在代码注释与测试名里，避免后来者"顺手统一"而重新引入
  夺走合法题目名的问题。
- **`problem/tui.ts` 从零覆盖变为有覆盖**：此前 #514 交付的实现没有任何测试，
  三个问题（含一个挂死）都是靠本轮补测才暴露出来的。

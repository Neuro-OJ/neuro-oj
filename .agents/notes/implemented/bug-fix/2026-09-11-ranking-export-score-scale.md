# Agent Note: 正式成绩导出的分数量纲修复与导出路径加固

Status: implemented

## Problem

2026-09-11 对 PR #491 的代码评审发现，成绩单导出存在一处会静默污染归档数据的量纲缺陷，以及若干导出路径上的工程问题：

1. **导出分数是页面显示值的 100 倍。** 快照表以 ×100 整数存储（`scoreToDb`），
   所有展示面都除以 100（`noj-ui/components/feature/contest/ContestRanking.vue` 的
   `score()`），但 `buildRankingCsv` 与 `buildRankingSnapshotJson` 直接写出原始值。
   满分 100 的题目在导出文件里是 `10000`。导出是给人核对/归档用的，与榜单不一致会让
   任何以导出为准的下游核对与重排出错。该缺陷在既有 `latest.csv` 中已存在，而本 PR
   新增了两条导出端点与两个分数列，等于把错误量纲扩散到更多出口。
2. **测试结构上不可能发现该缺陷。** fixture 用的是 `total_score: 100` / `best_score: 100`
   —— 流水线永远不会存入的值（存储侧是 `scoreToDb(100) = 10000`）。断言也只做
   `assertStringIncludes(csvV2, "90")` 这类子串匹配，截断或串列的 CSV 同样能通过。
3. **CSV 注入防护不完整。** `csvCell` 只查 `^[=+\-@]` 且只在 `[",\n]` 时加引号；
   Excel/Sheets 对公式前缀的识别不限于行首字符——制表符、回车可起前置分隔作用，
   前导空白也可能被忽略后仍按公式解析。`\r` 还会破坏行框（行用 `\n` 连接）。
   另有一个反向缺陷：`-0` 这类合法负数被当成公式前缀。
4. **导出内存无界且每次点击传输两遍。** CSV 以「数组 + join + BOM 拼接」一次性构造，
   一万人 × 十题的十万行数据会在内存中复制多份；UI 侧还先用 `api.get(base)` **下载并
   丢弃整个 JSON 快照**只为探测存在性，随后 `window.location.assign` 再传一遍。
5. **UI 版本列表存在竞态。** `openSettlement` 清空 `snapshotVersions` 后**不等待地**
   调用 `loadSnapshotVersions`；「打开 A（版本多）→ 关闭 → 打开 B（无版本）」时 A 的
   迟到响应会覆盖 B 的面板，导出按钮可能带上属于 A 的版本号。
6. **导出无缓存头、无导出审计。** 响应含全员成绩（个人数据），却未声明
   `Cache-Control`；读侧导出也未留下审计记录。

## Decision

**1. 在导出边界统一换算为展示量纲。** `total_score` 与 `best_score` 一律经
`scoreFromDb()`（`rank` / `attempts` 等计数值不换算），CSV 与 JSON 同口径——两个格式
描述同一版本时必须给出相同的数。选择改导出而不是改存储或改页面：存储量纲是全平台
既有契约（`scoreToDb`/`scoreFromDb` 成对使用），导出是唯一说错话的出口。

**2. 测试改用真实存储量纲并断言精确值。** fixture 改为 `10000` / `8750` / `1250`
（即展示分 100 / 87.5 / 12.5），断言逐列精确相等、列数为 9，并显式断言导出中
**不得出现** `10000`/`8750` 这类未换算值。两条新断言均经变异测试验证：把换算还原后
测试立即失败。

**3. `csvCell` 加固。** 前缀判定扩为 `^[\s]*[=+\-@\t\r]`（含前导空白与控制字符），
引号触发条件加 `\r`，`number` 类型直接返回字符串（不参与前缀判定，修掉 `-0`）。
新增独立用例覆盖 `\t=cmd`、`\r=cmd`、` =cmd`、`\t+cmd` 四种向量。

**4. 导出改为流式，去掉重复传输。** `buildRankingCsv` 改为 `Generator<string>` 逐行产出，
`csvResponse` 用 `ReadableStream` 逐块写出，峰值内存与总行数无关；补
`Cache-Control: private, no-store`。UI 侧删除「先下载 JSON 探测存在性」的步骤——
版本列表已在面板加载过，能渲染出按钮即说明版本存在。

**5. UI 竞态用请求序号解决。** `loadSnapshotVersions` 内部维护单调递增序号，只有
最后一次请求的结果才写入 `snapshotVersions` / `snapshotVersionsLoading`。与
`composables/useSearch.ts` 既有的 `requestSeq` 模式一致。

## Alternatives considered

- **改存储量纲（存展示分）。** 否决：那是全平台契约变更，涉及 `evaluation_results`、
  快照、竞赛榜单、提交详情等所有读写点，风险远超本缺陷；且 ×100 整数存储本就是为
  避免浮点误差而选定的设计。
- **只在 CSV 中换算，JSON 保持原始值（「JSON 是机器格式」论）。** 否决：同一版本两个
  格式给出互相矛盾的数字，会让核对者无法判断哪个是对的；且 JSON 导出的既有消费方
  （管理端下载）与 CSV 用途相同。
- **在 UI 侧除以 100。** 否决：导出文件会被下载到本地、被脚本与表格软件直接消费，
  修复必须在服务端出口生效；UI 侧换算对已下载/已归档的文件无效。
- **保留存在性探测，改用 HEAD 请求。** 部分可行，但需要新增 HEAD 路由；而版本列表
  已在面板中加载，探测本身是冗余的。直接删除更简单且无额外端点。
- **给 `message`/`scored` 类字段加白名单以保留失败原因。** 见同日的
  `2026-09-11-problems-init-forgery-hardening`：该决策属平台投影契约，需单独评审，
  不在导出修复范围内。
- **为 CSV 行数设上限并在超限时报错（而非流式）。** 否决：成绩归档必须完整，
  拒绝导出会把「数据大」变成「拿不到数据」；流式是更合适的解法。

## Consequences

- 导出文件与页面榜单、题面分数三者量纲一致；满分题在 CSV/JSON 中均为 `100`。
- 测试从「子串匹配」提升为「逐列精确断言 + 变异可失败」；contest 域用例 45 → 47。
- CSV 导出峰值内存不再随参赛人数线性增长，管理端每次导出少传输一份完整快照。
- 注入防护覆盖制表符/回车/前导空白；同时修掉 `-0` 被误加前缀的问题。
- 导出响应禁止缓存，降低共享终端上成绩数据残留的风险。
- 未做：导出操作的审计日志（`withAudit`）。成绩导出属读操作，现有审计分层主要覆盖
  写操作，是否纳入需与审计范围一并决定，故留作后续项而非在本 PR 内自行扩大审计面。

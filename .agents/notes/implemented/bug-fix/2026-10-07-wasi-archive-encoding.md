# Agent Note: 固定 WASI 工具链来源归档封装兼容

Status: implemented

## Problem

固定 LLVM 提交的 codeload 下载归档摘要与旧构建配方不同，生产 runtime
镜像因此无法构建。直接替换已发布配方或忽略来源摘要都会破坏标准的可审查性。

## Decision

在临时目录用新归档重建，验证最终计量相关编译器、头文件、库和链接器逐文件摘要与冻结组件清单完全一致。另行记录同一提交的已验证归档封装摘要白名单，保留
v2/v3 配方、组件和计量清单原样。

下载先校验原摘要或精确白名单摘要。对于其他 gzip 封装，完整未压缩 tar 的 SHA-256
和字节数必须与已验证归档的固定基准完全一致；读取按冻结大小设硬上限，损坏、截断、超限或内容变化均拒绝并删除临时下载。替代封装不能用于重新记录组件清单，重建产物必须匹配原冻结组件。CI
增加下载校验回归，缓存键纳入归档信息。

Judge Check 仅上传验收日志，不再上传整个 target 编译目录，避免失败或取消被数 GiB
编译缓存上传阻塞。

## Alternatives considered

- 修改固定配方中的旧摘要：会使已经发布的标准来源记录改变。
- 忽略源码下载摘要：扩大构建信任边界。
- 只使用开发机现成 SDK：不能解决 CI 与生产构建入口。

## Consequences

归档封装兼容没有改变计量行为，最终组件一致性仍是交付硬门槛。新压缩封装不会授予不同
tar 内容构建权限；源码和完整 tar 元数据都必须逐字节匹配固定内容摘要。原生 Docker
SDK 运行验收仍单独执行。

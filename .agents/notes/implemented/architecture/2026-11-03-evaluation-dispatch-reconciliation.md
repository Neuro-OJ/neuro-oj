# Agent Note: 评测链路派发标记与孤儿对账

Status: implemented

## Problem

评测提交的数据库状态和 Redis 队列无法共享事务。进程可能已经把任务写入队列，
却在更新提交状态前退出，导致 sweeper 将同一任务再次入队；另一类故障是提交已经
进入 `judging`，但任务在派发窗口中丢失，原有只扫描 `pending`
的恢复逻辑无法发现。
恢复动作也缺少低基数的统计，难以区分重复跳过、重新入队和持续失败。

## Decision

使用活动评测尝试的 `run_id` 作为 Redis 派发标识。Producer 在容量检查和 `LPUSH`
的同一条 Lua 脚本中写入带 TTL 的 `queued` 标记；sweeper 恢复前以 `NX` 抢占短期
`dispatching` 标记，多副本只允许一个恢复器重建任务。结果成功落库或自测取消后清理
标记，清理失败由 TTL 兜底。

恢复器继续保持 at-least-once 和结果幂等语义：已发现 `queued` 标记时只补齐数据库
状态，不重复入队；标记缺失时重建任务。新增 `judging` 超过完整 processing 超时、
且活动尝试仍为 `queued/judging` 的对账扫描，用同一套版本快照重建任务。恢复动作以
`type/result` 两个低基数标签记录到 `noj_submission_recovery_total`。

`judging` 对账不把“无标记”直接判为孤儿：先分页扫描候选行并用 `MGET` 过滤仍有
标记的尝试，避免积压中的老行占满单页名额；剩余候选再复核主队列、processing 与
结果队列，仍在列表中的任务（标记引入前或滚动升级期间旧副本入队）补写 `queued`
标记而不重复派发。对账恢复保留原始 `judge_started_at`，不改写“最老 judging 年龄”
指标；管理员移出队列时同步清理标记，避免 pending 恢复误判“已入队”。

## Alternatives considered

- 引入数据库 outbox，把每次派发转成持久化事件：一致性边界更强，但需要新增表、
  worker 和迁移，超出本次可靠性补强的最小改动范围。
- 重写提交状态机并统一所有派发入口：长期可取，但会扩大跨模块风险，当前已有的
  版本绑定、幂等结果写入和队列 sweeper 可以继续复用。
- 只延长 `pending` 扫描或无条件重试：无法识别“已经入队”的窗口，仍会造成重复
  评测，也无法修复已经卡在 `judging` 的孤儿提交。

## Consequences

- 正常派发多一次 Redis key 写入，但队列入队和标记写入是原子的；不增加数据库迁移
  或运行时依赖。
- Redis 标记默认保留 24 小时，超过后允许 sweeper 重新接管长期失联任务；结果消费
  和取消路径会提前清理。
- 恢复过程仍可能在 Redis 或数据库故障时延后，下一轮继续处理；标记和结果幂等共同
  保证不会把“恢复失败”误判为已完成。
- 列表复核只在出现无标记候选时执行，`LRANGE` 长度受队列容量约束；稳态下每轮只多
  一次 `MGET`。
- 新增测试覆盖标记防重复、已入队状态补偿、`judging` 孤儿恢复、在途无标记任务不
  重复派发、恢复保留开始时间、移出队列清理标记，以及自测恢复夹具对真实任务丢失
  场景的建模。

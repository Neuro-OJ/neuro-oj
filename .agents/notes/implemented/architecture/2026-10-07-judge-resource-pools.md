# Agent Note: Judge 资源池准入与 WASM 提交内并行

Status: implemented

## Problem

OI WASM、Native 和 AI 共用任务并发限制，会互相阻塞。WASM 按 fuel
限制程序工作量，但增加并发仍会消耗宿主内存和墙钟；将每个提交独立开 16
个用例会放大全实例容量。模块重复编译和异步取消后提前释放槽位也会损害吞吐和资源保护。

## Decision

Core 从规范化后端推导三个池，任务绑定调度协议
1。队列按池保留三级优先级比例，同级容量跨池共享。用户 claim
分池、分正式与自测批次。

组内任务、编译、运行和预留内存统一通过 Redis
原子租约协调。启动配置冻结且同组一致，auto 预算使用物理/cgroup 上限的
50%。父任务包含基础内存及阶段余量，阶段优先借用余量，避免持有题目数据后互相等待编译内存。执行线程持有父、阶段租约直至退出；续租失败中断执行，资源故障返回
SE。停止全部 Worker 并排空后才能解除旧配置锁。

同提交复用 Engine 和已编译 Module，各用例仍有独立 Store、目录、输出和期限。SUM
并行，MIN/MAX 保留顺序和短路；Redis
在准备好的提交间分配运行槽位。等待资源时不发布测试点开始事件。共享 epoch
仅驱动期限检查，不把一例超时传播给另一例。

队列迁移保留身份、优先级和轮次，拒绝未排空的旧
processing；非法消息进入死信。等待诊断与轮次匹配，权限过滤后才能展示。监控容量按资源组和启用池并集去重。

独立 release 基准不消费站点队列，不修改成绩；club/road 的 1、2、4、8、16
槽位对照及四提交竞争均保持逐点
fuel、状态和计量身份一致。详见工程协议和基准报告。

## Alternatives considered

- 每进程 Semaphore：多 Worker 会使容量成倍增加，不能统一内存准入。
- 每提交固定 16 个用例：无法限制全实例测试点数，也不能公平分配。
- 每点新建 Engine：重复 JIT，增加吞吐和内存成本。
- 共享固定 epoch deadline：某一用例超时会误中断同 Engine 的其他 Store。

## Consequences

资源池隔离不等于
CPU、缓存或内存带宽隔离。预留是保守估算，继续依赖操作系统限制；Worker RSS
也不是整个宿主和所有容器的完整内存测量。吞吐报告说明负载波动，不能据此宣称单机
OJ 性能排名。部署需暂停入队并协调升级，当前本地 Judge 仍由用户控制。

CI 收尾保持门禁强度：新增测试不增加静默跳过，离线迁移用 fake Redis 执行契约、CI
使用真实 Redis 执行
Lua；事件/路由目录通过规定脚本生成，单文件超限按执行职责拆分而未增加规模基线。UI
声明已有锁文件的 registry 来源，使新版 Deno
原始测试与覆盖率任务能够保留锁校验；依赖锁文件没有修改。

生产 Compose 的默认 Worker 硬上限从 2 GiB 调整为 8 GiB：旧上限的 50% auto
预算不足以准入题包和编译阶段，导致默认部署的任务直接
SE。该值是硬上限而非预分配，已有显式覆盖不改写；有效物理/cgroup
上限仍约束调度预算，16 是槽位上限而非保证同时启动数。

消费者按池非阻塞探测，空池不执行阻塞等待，避免拖慢其他池的领取；空池退让最多
25ms。内存不足和用户占用重投增加 100ms 退让，避免 Redis 忙循环。原单池阻塞 API
保留兼容入口，真实 Redis 回归验证空 AI 队列不阻塞 WASM 领取及 ack。

# Agent Note: 备份调度的 crontab 标记区块与注入防线

Status: implemented

## Problem

`backup-schedule.sh`（162 行）管理生产备份的每日 cron 任务。它的**全部价值**不在
"写入一条 cron"，而在"**只动自己标记的那几行**"：crontab 是宿主机共享资源，
用户机器上通常已有其他运维任务与个人定时任务。`test-backup-schedule.sh` 的四条
断言（保留 `# unrelated host task`、区块不重复、更新后旧调度消失、删除不误删
他人任务）都是这一点的不同侧面。

同时它有两个必须保住的输入面：

1. **cron 表达式即注入面**：表达式被拼进 crontab 行首，由 cron 经 shell 执行。
   `15 2 * * *; touch /tmp/unsafe` 是既有的测试用例——bash 用白名单正则
   `[0-9*/?,-]+` 逐段拒绝。
2. **路径即注入面**：bash 用 `printf '%q'` 引用每个路径。这不是洁癖：安装目录含
   空格（`/opt/my noj`）时，未引用的一行会被 cron 拆成多个字段、**静默变成另一条
   命令**；而路径来自用户参数，属于可达输入。

## Decision

新增 `noj-cli/src/prod/schedule.ts`，把 bash 的 162 行收敛为"纯函数 + 两个
crontab 原语"：

1. **解析与合并是纯函数**：`removeManagedBlock` / `upsertManagedBlock` /
   `extractManagedBlock`。于是"幂等"与"不碰他人行"可**脱离进程**直接断言
   （共 6 个用例），而只有 `crontab -l` / `crontab -` 两次调用经注入的 runner。
2. **`upsertManagedBlock` 的幂等来自"先删后加"**：无论原 crontab 里有没有本工具的
   区块、有几个（异常情形），结果都恰好**一个**区块且位于**末尾**——与 bash
   的 `updated="$current"; updated+=$'\n'"$entry"` 同形，因此区块外行的相对顺序
   天然保持。
3. **末尾换行必须保留**（`removeManagedBlock` 带末尾 `\n`）：丢掉它不影响 cron
   解析，但会让"区块外逐字节不变"的承诺在 diff 与断言层面失效。
4. **无 `END` 标记时删到末尾**（保持 bash `awk` 的行为）：另一种选择（只删 BEGIN
   行、保留后续）会把本工具的命令行**留在 crontab 里**却少了标记，下次 `install`
   再也认不出它，产生**无法清理的重复任务**。
5. **先查元字符、再查段数**：这是本实现修正的一处**报错归属**。反过来的话
   `15 2 * * *; touch /tmp/unsafe` 会因分号后多出一个词而报"段数不对"，
   把"这是注入尝试"掩盖成"格式没写对"——评审与运维都会看错方向。
6. **`quoteForCron`：单引号包裹 + `'\''` 转义**，不用双引号。双引号里
   `$`/`` ` ``/`\` 仍有特殊含义、需要逐字符转义；单引号是唯一"没有例外"的形态，
   因此更不容易写错。安全字符集内不加引号只为可读性。
7. **绝对路径是校验而非假设**（cron 不继承用户 PATH）；口令权限校验**复用**
   `prod/drill/plan.ts` 的 `checkPassphraseFile`（不重写）。
8. **`remove` 在无区块时不写 crontab**：bash 在内容未变时直接 `ok` 返回。
   保持它可避免无意义的写入（crontab 写入会触发 cron 重载，部分发行版上还会
   改写文件并触发审计）。
9. **退出码分类要认两类错误**：本模块抛 `UsageError`，而复用的
   `checkPassphraseFile` 抛 `DrillPreflightError`（drill 侧语义）。只认前者会把
   "口令权限过宽"这类明确的前置问题误报成"运行失败 1"，与 help 的承诺不符。

## Alternatives considered

- **用 `Deno.Command("crontab", …)` 直接读写、不做纯函数分层**：那就无法单测
  幂等与"不碰他人行"，只能像 bash 测试那样起一个假 `crontab` 脚本来间接验证。
  分层后这两条性质是**直接可断言**的。
- **`quoteForCron` 用双引号 + 逐字符转义**：需要正确处理 `$`、`` ` ``、`\`、
  `"` 四类字符，任一处漏掉就是一个注入面。单引号没有这些例外。
- **给 `* * *` 之类的表达式做语义校验（范围、步长）**：超出 bash 的行为，
  且 cron 实现有差异（`?` 在部分实现里合法）。白名单字符集已足以挡住注入，
  语义错误由 cron 自己在执行时报错（输出进日志）。
- **`status` 未安装时返回 0**：会让脚本无法据此判断"要不要装"。bash 返回 1，
  保持它（且在消息里给出可读提示，而不是只给退出码）。
- **把 `checkPassphraseFile` 复制一份到 schedule.ts 以免跨模块依赖**：那会形成
  第二份权限判定实现，未来任一侧修复都不会传播。改为 import，并让错误分类认
  两类异常。

## Consequences

- **24 个用例**，全部注入 runner，**不触碰真实 crontab**；其中 6 个纯函数用例
  直接锁住幂等与"不碰他人行"。
- **注入防线可断言**：`;`/`&&`/`|`/`$(id)`/反引号/`>`/内嵌换行/`%` 全部拒绝，
  且断言**零 crontab 写入**（调用记录里没有 `-`）。
- **路径引用可断言**：含空格的安装目录下，经真实 `sh` 切分后的**词数必须与无空格
  时相同**——引用失效会让词数变多，那正是"静默变成另一条命令"的形态。
- **权限契约**：备份目录 700、日志 600（日志可能含内部路径与题目 ID）。
- **既有日志不截断**：以 append 打开，重复 install 不清空历史输出。
- **`backup-schedule.sh` 仍在**（T24 删除）：`cli.ts` 目前仍把 `schedule` 路由到
  脚本；本任务交付的是可注入的原生实现与其结果形状，命令面接线随 T24 落地。
- **测试辅助函数记录了两个实测坑**（供后续复用）：词切分验证必须经
  **base64 + argv** 传行（否则外层 shell 会先展开 `$1`/反引号），且要
  `set -f` 关掉 glob（cron 的 `* * *` 会被展开成当前目录的文件名）。

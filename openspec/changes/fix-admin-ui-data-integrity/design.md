## Context

Issue #175 涉及后台多个独立页面，但根因集中在共享的列表加载、变更后同步和通用组件行为。现有页面主要直接使用 `$fetch`，因此快速交互时旧响应可以覆盖新状态；部分变更成功后未更新界面。单条重测也缺少与批量重测一致的活跃任务保护。

## Goals / Non-Goals

**Goals:**

- 将每次列表加载与递增请求版本关联，仅允许最新请求更新状态。
- 在不丢失其他草稿的前提下更新单个系统设置。
- 让角色、重测和删除等变更操作提供可靠且可见的最终状态。
- 让宽表、弹窗和仪表盘在窄屏、失败与键盘操作场景可用。

**Non-Goals:**

- 不重构后台 API 为新的状态管理框架。
- 不增加数据库 schema 或迁移。
- 不为所有后台页面实现完整离线缓存或实时推送。

## Decisions

### 使用请求版本号而非共享 AbortController

每次加载递增本地版本号，并在响应和 finally 块提交状态前确认版本仍是最新。该方式无需依赖浏览器取消语义，适用于现有 `$fetch` 调用，也能阻止网络已完成但乱序返回的响应覆盖界面。`AbortController` 作为可选优化不作为正确性基础。

### 角色编辑通过用户详情返回角色 ID

用户列表响应包含已分配 `role_ids`，前端直接据此预选。避免额外逐用户请求及弹窗打开后的竞态；保存前仍由后端执行角色合法性和最后管理员保护。

### 单条重测只允许 finished/error 状态

后端在删除评测结果前校验提交状态，`pending` 或 `judging` 返回 400。前端在提交期间禁用该行重测按钮，并在成功后显示最新状态。该策略与批量重测的活跃任务保护一致，避免重复入队。

### 设置保存采用行级回写

保存单项设置后，用 API 返回值更新对应 setting 与草稿，不全量刷新列表；重置同样仅更新目标项。这样并发保存不会清除其他行的本地编辑。

### 通用组件提供最小可访问与窄屏基础能力

`AdminTable` 提供横向滚动容器；`AdminModal` 提供 dialog 语义、焦点进入、Tab 约束和焦点恢复。页面可按业务需要进一步提供卡片化表格，但共享组件确保行操作仍可达。

## Risks / Trade-offs

- [用户列表响应增加 role_ids] → 仅返回当前管理员已可管理的角色 UUID，不暴露权限详情；后端测试覆盖响应形状。
- [只允许 finished/error 单条重测] → 无法用重测修复卡住的 judging 任务；由现有队列/运维流程处理，避免重复任务造成更大损害。
- [横向滚动不是卡片化] → 移动端扫描体验仍不如专用视图，但可立即访问全部列与操作，改动风险低。
- [行级设置回写] → 依赖更新 API 返回完整项；接口现有返回值已满足。

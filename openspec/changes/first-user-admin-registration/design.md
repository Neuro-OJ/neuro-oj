## Context

当前生产 Compose 通过 `ADMIN_EMAIL` 和 `ADMIN_PASS` 在启动阶段创建或提升管理员，部署向导也要求用户提前填写这两个字段。系统初始化本身已经创建 root 用户和 RBAC 角色；root 是不可登录的系统账号，不能作为首个用户判断依据。

## Goals / Non-Goals

**Goals:**

- 让生产安装只需要基础运行配置，管理员在网站注册时产生。
- 只把第一个真实注册用户提升为 admin，并正确返回管理员状态。
- 让并发注册在空站点中只有一个管理员。
- 保留旧的 CLI 管理员引导能力，便于已有运维流程和紧急恢复。

**Non-Goals:**

- 不允许通过 URL、请求字段或客户端声明直接获得管理员权限。
- 不改变已有用户、管理员和角色关系。
- 不删除 `bootstrap admin` CLI；它仍可由运维人员显式执行。

## Decisions

- 在注册事务中先使用 PostgreSQL 事务级 advisory lock 串行化“空站点首个用户”判断，再排除 root 用户检查真实用户数量。相比仅在应用层先查询再插入，这可以防止两个并发请求同时成为管理员；相比新增状态表，不需要额外迁移和历史数据回填。
- 首个真实用户只分配 `admin` 角色，不再额外分配普通 `user` 角色。admin 角色包含全权限，避免角色关系重复；后续用户继续使用默认角色。
- 注册响应的 `is_admin` 使用本次事务实际分配结果，不通过客户端输入或旧的 `users.role` 列推断。
- 生产 Compose 移除 `bootstrap admin` 自动步骤以及管理员环境变量的必填插值。旧环境文件中的字段可以保留，但不再影响新生产初始化；显式 CLI `bootstrap admin` 继续支持兼容和恢复。
- 部署向导删除管理员邮箱和密码问题，并在部署完成后提示“打开网站注册首个用户”。管理员密码由注册页面输入，不写入服务器安装命令或生产环境文件。

## Risks / Trade-offs

- [安装完成后网站若公开暴露，陌生人可能抢先注册成为管理员] → 部署提示要求用户立即注册；文档建议先通过防火墙、面板反向代理访问控制或临时域名限制访问。后续需要时可由管理员关闭 `allow_register`。
- [PostgreSQL advisory lock 会让并发注册短暂排队] → 锁只在注册事务内持有，注册频率低，且只为保证首个管理员的唯一性。
- [升级后不再自动执行旧的管理员引导] → 已有管理员角色和用户数据保持不变；紧急场景仍可显式执行 `bootstrap admin --email --password`。

## Migration Plan

1. 更新镜像和 Compose 后执行数据库迁移、系统初始化；不修改现有用户角色。
2. 新站点启动后注册第一个真实用户，并立即检查其管理后台权限。
3. 已有站点如需沿用环境变量管理员引导，可在升级前显式执行 CLI 引导；回滚时旧环境字段仍可保留。

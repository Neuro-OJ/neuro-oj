## Why

生产环境目前主要依赖结构化日志和综合 `/health`，无法持续观察 API 错误率、评测队列积压、消费者存活、数据库/Redis 状态或磁盘风险。Issue #327 需要在正式上线前建立可采集、可告警、可演练的最小观测闭环，降低故障发现和定位延迟。

## What Changes

- 增加平台无关的 Prometheus 文本指标端点，覆盖 API 请求量、延迟、状态码、限流、数据库/Redis、评测队列、消费者和关键评测结果事件。
- 将 API 请求指标接入统一中间件，并限制标签为低基数的 method、route、status 等字段，避免泄露用户或提交数据。
- 将 `/health` 拆分为独立的 liveness 与 readiness 探针，同时保留现有综合健康响应的兼容性。
- 增加管理员可查看的生产观测面板，展示依赖状态、队列、评测和错误概览，并提供指标抓取配置说明。
- 增加 Prometheus 告警规则、仪表盘配置和故障 Runbook，覆盖队列堆积、评测卡死、数据库/Redis 异常、磁盘不足和错误率升高。
- 增加可重复的测试与故障演练脚本；无法由仓库自动配置的外部通知渠道改为部署文档中的接入契约。

## Capabilities

### New Capabilities

- `production-observability`: 提供服务指标、健康探针、生产仪表盘、告警规则和故障 Runbook。

## Impact

- 影响 `noj-core` 的中间件、健康路由、Redis/数据库观测适配和启动生命周期。
- 影响 `noj-judge` 的运行指标与结构化指标输出。
- 新增管理端观测页面、Prometheus/Grafana 配置示例、部署文档和测试。
- 不新增运行时依赖；指标注册表使用现有运行时能力实现。
- 生产部署需要配置 Prometheus（或兼容采集器）及外部告警通知渠道；应用本身不绑定具体厂商。

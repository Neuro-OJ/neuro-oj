## Context

NOJ-226 的普通用户搜索路由用于私信联系人，当前只返回非敏感基本信息；全局搜索已经存在管理员权限校验和邮箱字段，但匹配条件没有显式覆盖邮箱模糊搜索。竞赛参与者管理页直接调用普通用户搜索路由，造成 UI 契约与权限边界同时不清晰。

NOJ-230 的社区首页使用游标分页，列表数据会在客户端追加。摘要函数位于模板表达式中，因此任意响应式更新都会遍历并处理所有已加载帖子。

## Goals / Non-Goals

**Goals:**

- 复用管理员专用搜索入口和既有 RBAC，支持用户名/邮箱模糊匹配。
- 保持私信联系人搜索的隐私和响应契约不变。
- 让社区摘要只在 API 数据首次进入列表时计算一次。

**Non-Goals:**

- 不将邮箱加入普通 `/api/v1/users/search` 响应。
- 不改变搜索排序、分页、root 排除或私信功能。
- 不引入虚拟列表库，也不人为截断社区游标分页结果。

## Decisions

### 管理员竞赛搜索改用全局用户搜索

竞赛参与者管理页改为请求 `GET /api/v1/search?type=user`，由现有 `checkPermission(c, "user:search")` 和服务层 fail-closed 守卫保护。全局搜索服务增加 `email ILIKE` 条件，并同步更新精确总数查询。

这样复用已有管理员权限和完整用户搜索响应；直接给普通 `/users/search` 加邮箱会把个人邮箱暴露给所有可发起私信的登录用户。替代方案是仅移除竞赛页的邮箱显示和提示，但会继续缺少按邮箱定位用户的能力，因此不采用。

### 在数据加载边界预计算社区摘要

社区页面使用带 `preview` 字段的前端列表行：服务端 `useAsyncData` 首屏数据和客户端 `loadPosts` 追加数据都通过同一映射生成摘要，模板只读取 `item.preview`。

这种方式保留现有游标分页和响应结构，不需要后端新增字段或引入虚拟滚动依赖。替代方案是虚拟列表或固定最大列表长度，前者增加依赖和布局复杂度，后者会改变用户浏览历史内容的语义，因此不采用。

## Risks / Trade-offs

- [Risk] 邮箱模糊匹配在大型用户表上可能增加查询负担 → 沿用现有结果上限、排序和限流，并复用已有搜索向量/索引路径。
- [Risk] 首屏摘要会随序列化数据传到客户端 → 摘要上限保持 `stripMarkdown` 的 160 字符，增加的数据量受每页帖子数限制。
- [Risk] 后端全局搜索响应包含高亮等字段，而竞赛页只需要部分字段 → 前端仅解构/使用必要字段，不改变后端公共响应契约。

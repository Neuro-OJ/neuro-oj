## Context

当前 `noj-ui/pages/login.vue` 使用同一张 `AuthFormCard` 展示用户名、密码以及条件出现的 TFA 输入框。后端登录接口已经在密码正确且缺少二次凭据时返回 `TFA_REQUIRED`；恢复码文件也已经由浏览器本地解析，最终沿用同一个登录请求提交单个 `code`。

## Goals / Non-Goals

**Goals:**

- 让登录页在密码阶段与 TFA 阶段使用两个清晰的界面状态。
- 保留现有登录 API、`TFA_REQUIRED` 分支、恢复码文件导入和错误处理。
- 通过返回按钮让用户回到第一步修改登录凭据。
- 确保用户名和密码只存在于当前页面内存，不进入 URL、Cookie 或 localStorage。

**Non-Goals:**

- 不新增登录挑战 token 或后端会话状态。
- 不修改 TFA 校验、限流、恢复码消费和认证 Cookie 逻辑。
- 不自动尝试文件中的多个恢复码。

## Decisions

### 1. 使用同一路由内的两种界面状态

使用 `tfaRequired` 作为页面状态，在同一个 `/login` 路由内通过两个互斥的 `AuthFormCard` 界面切换。这样可以满足独立界面的视觉需求，同时避免把密码放入路由参数，也不需要额外的挑战票据。

备选方案是增加 `/login/tfa` 路由，但跨路由传递密码会引入持久化或全局内存状态，安全边界和刷新行为更复杂，不适合当前一次提交登录 API。

### 2. 第一阶段成功后保留内存中的登录凭据

收到 `TFA_REQUIRED` 时保留 `form.login` 和 `form.password`，仅显示 TFA 界面；返回第一步时继续保留两者，方便用户修正。登录成功、组件销毁或用户主动离开页面时，凭据不会写入任何持久化存储。

### 3. TFA 临时状态集中清理

新增清理函数统一重置 `form.code`、恢复码列表、文件错误和字段错误。返回第一步时调用该函数；TFA 登录失败不调用，确保用户可以改选恢复码后重试。

### 4. 复用现有表单提交逻辑

TFA 界面继续触发现有 `handleLogin`，由 `tfaRequired` 决定是否把单个 `form.code` 传给 `auth.login`。不新增 API，也不引入前端挑战状态。

## Risks / Trade-offs

- [用户在 TFA 步骤刷新页面会丢失已输入的密码] → 不持久化密码，刷新后要求重新输入，符合凭据安全边界。
- [用户点击返回后可能忘记当前已输入密码] → 返回操作只清理 TFA 临时状态并保留当前页面内存中的用户名/密码。
- [同一页面保留密码时间更长] → 仅保留到登录流程结束或页面离开，不写入 URL、Cookie 或本地存储。

## Migration Plan

仅部署前端页面变更；后端 API、数据库和环境变量无需迁移。回滚时恢复原来的单卡片条件渲染即可。

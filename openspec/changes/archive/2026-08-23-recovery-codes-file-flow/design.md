## Context

TFA 后端在 `confirm` 和 `recovery-codes/regenerate` 响应中返回明文恢复码，数据库只保存哈希；登录页在收到 `TFA_REQUIRED` 后通过现有 `auth.login(login, password, code)` 提交单个 TFA 凭证。当前前端恢复码只保存在 `settings.vue` 的内存状态，尚无文件保存或导入能力。

## Goals / Non-Goals

**Goals:**

- 在浏览器中将本次生成的恢复码保存为可下载的 UTF-8 文本文件。
- 在登录页本地解析恢复码文件，并让用户明确选择一个恢复码。
- 保持现有后端 API、哈希存储、一次性消费和限流行为不变。
- 将格式化和解析规则提取为无框架纯函数并覆盖单元测试。

**Non-Goals:**

- 不新增恢复码查询、文件上传或服务端文件存储 API。
- 不自动依次尝试多个恢复码。
- 不在本次变更中实现密码管理器或云端同步。

## Decisions

### 1. 使用带注释的文本文件格式

下载内容使用 UTF-8 `.txt`，以 `#` 开头的行作为说明，非空非注释行必须是一个 `XXXX-XXXX-XXXX` 恢复码。恢复码校验沿用后端字符集：大写字母和 `2-9`，排除 `0/O/1/I`。解析时去除首尾空白并统一为大写，去重后要求至少一个且不超过 10 个恢复码。

选择文本文件而不是 JSON 或专用二进制格式，是因为用户可以打印、查看和在密码管理器中保存；带注释的格式同时便于用户理解用途，解析规则仍然明确可测试。

### 2. 浏览器本地读取，提交单码

登录页使用浏览器 `File` API 读取用户主动选择的文件，解析结果仅保存在当前页面内存。选择列表中的一个恢复码后，复用已有的 `form.code` 和登录请求；整个 `File`、原始文本以及其他恢复码不会进入请求体。

不采用整文件上传或自动遍历尝试：前者会让服务端接触全部备用凭证，后者会增加限流和误消费风险。

### 3. 下载由用户操作触发

设置页在恢复码展示区域增加下载按钮，通过内存中的 `Blob` 创建临时对象 URL 并触发浏览器下载。文件名包含日期但不包含用户名、恢复码或其他敏感信息。浏览器仍需用户点击下载，避免依赖静默写盘能力。

同时提供复制全部恢复码操作作为下载失败时的辅助路径；复制失败只显示提示，不影响恢复码展示。

### 4. 清理敏感的临时 UI 状态

成功确认或重新生成后清空 TFA 验证输入框，避免已消费的恢复码继续留在输入框中。用户身份发生变化、禁用 TFA 或离开当前流程时清理二维码、secret、输入值和恢复码列表，避免跨用户残留。

## Risks / Trade-offs

- [下载文件可能被其他本地程序读取] → 下载内容只由用户主动触发，页面提示将文件保存到密码管理器或离线安全位置；不在服务端保存文件。
- [文件中包含已使用恢复码] → 允许用户逐个选择，服务端返回失败后保留列表；禁止自动遍历。
- [用户未保存就刷新页面] → 恢复码明文不会再次从服务端获取，页面在生成后持续展示并提供下载/复制入口，保持一次性明文返回的安全约束。
- [文件格式被手工修改] → 严格校验大小、注释行和恢复码格式，解析错误显示可理解的错误信息。

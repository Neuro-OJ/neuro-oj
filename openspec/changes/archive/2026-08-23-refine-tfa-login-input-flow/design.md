## Context

当前 `noj-ui/pages/login.vue` 已经将密码登录和 TFA 登录拆成两个界面，但 TOTP 输入、恢复码手动输入和恢复码文件导入同时可见。详见 `proposal.md` 的动机与范围。

## Goals / Non-Goals

**Goals:**

- 使用一个明确的页面状态区分动态验证码和恢复码两种验证模式。
- 保持已有的恢复码文件本地解析、恢复码选择和单个 `code` 提交逻辑。
- 切换回动态验证码时清理恢复码临时状态，避免将旧恢复码带入下一次提交。

**Non-Goals:**

- 不修改后端认证接口、TFA 校验规则或恢复码格式。
- 不把恢复码文件上传到服务器，也不增加浏览器持久化。
- 不拆分新的路由或新增组件文件。

## Decisions

### 使用页面级恢复码模式状态

在登录页增加布尔状态表示当前是否使用恢复码。状态为 false 时渲染动态验证码输入和“使用恢复码登录”入口；状态为 true 时渲染恢复码提示、文件导入和切回入口。这样只改变展示层，不改变 `form.code` 的单值提交模型。

替代方案是同时保留两个输入框并根据模式选择提交值，但会增加状态同步和误提交风险，因此不采用。

### 复用现有恢复码文件处理逻辑

恢复码模式继续使用现有文件 input、大小校验、本地文本解析、恢复码按钮选择和错误提示。切回动态验证码或返回密码登录时清空文件列表、文件错误和 `form.code`，保持当前页面状态可预测。

### 使用现有 Nuxt UI 按钮作为模式入口

模式切换使用 `UButton` 的无提交按钮类型，避免点击入口触发表单提交；提交登录仍由 `AuthFormCard` 的唯一 submit 按钮处理。

## Risks / Trade-offs

- [Risk] 用户可能误以为恢复码模式仍接受动态验证码。→ 在模式切换后更新输入标签和提示文案，并提供明确的切回入口。
- [Risk] 恢复码文件中有多个码时需要用户再次选择。→ 保留现有恢复码按钮列表，不自动选择未知恢复码。
- [Risk] 模式切换清空输入会让用户丢失当前码。→ 仅在用户主动切换模式时清空，默认进入 2FA 页面不清空密码登录上下文。

## Migration Plan

1. 在登录页增加恢复码模式状态，调整模板条件渲染和切换处理函数。
2. 运行 `deno task check`、`deno task test` 和 `deno task build`。
3. 通过 OpenSpec 严格校验；如需回滚，恢复登录页即可，不涉及数据迁移。

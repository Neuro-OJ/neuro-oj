## Context

当前管理竞赛页面在保存成功后调用整页 `reloadNuxtApp`，保存请求、页面重载和轮询刷新之间没有可等待的顺序关系。`loadContests` 已具备请求版本号保护，适合直接作为保存后的局部刷新入口；`useApi` 的默认错误 toast 也要求保存失败与刷新失败分开处理。

## Goals / Non-Goals

**Goals:**

- 将竞赛保存后的刷新改为当前页面内可等待的列表请求。
- 在保存成功后先反馈结果，再关闭弹窗并刷新列表；刷新失败不得回滚或重复保存。
- 保持现有轮询的请求版本保护和已有竞赛数据。
- 为核心保存流程提供可自动验证的前端测试覆盖。

**Non-Goals:**

- 不修改竞赛数据库、服务层校验、API 状态码或鉴权逻辑。
- 不改变竞赛表单字段、竞赛列表分页规则或自动轮询间隔。
- 不引入新的前端依赖或全局状态管理。

## Decisions

### 使用局部列表刷新替代整页重载

保存成功后调用 `await loadContests(currentPage.value)`，而不是触发 `reloadNuxtApp`。这样可以复用现有的请求序列保护、错误状态和最近刷新时间，并保证创建结果在同一页面生命周期中可见。整页重载作为备选会重新建立多个请求和组件状态，无法区分保存成功与后续加载失败。

### 区分保存结果和刷新结果

保存请求成功后立即显示“竞赛已创建/已更新”并关闭弹窗；随后列表刷新使用静默 API 请求，若失败仅设置列表刷新错误并保留旧数据。保存 catch 只处理真正的保存失败，避免把刷新故障映射成“竞赛创建失败”。

### 保留并强化单表单互斥

父页面在进入保存流程时立即设置 `saving`，表单按钮使用该状态禁用并展示“保存中...”。同时在保存函数入口增加互斥短路，防止同一事件循环或组件状态尚未完成更新时重复触发请求。

## Risks / Trade-offs

- [Risk] 保存成功后列表刷新失败时，新竞赛暂时不会出现在旧列表中 → 保留列表数据并展示明确的刷新错误，管理员可使用已有手动刷新或自动轮询恢复。
- [Risk] 刷新请求与自动轮询同时发生 → 继续使用页面现有的 `contestRequestVersion`，只接受最新请求结果。
- [Risk] 局部刷新失败被误认为保存失败 → 保存成功反馈与刷新错误状态分别处理，并使用静默刷新请求。

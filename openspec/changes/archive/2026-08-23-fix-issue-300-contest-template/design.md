## Context

普通做题模式把 `/api/v1/problems/:id/template` 作为 `templateUrl` 传入 `EditorWorkspace`，由工作区在草稿恢复后自动加载模板；竞赛模式使用同一工作区，但当前将 `templateUrl` 设为 `undefined`。竞赛题目响应包含真实的 `problem_id`，且竞赛提交仅改变提交 URL，不改变题目模板资源的来源。

## Goals / Non-Goals

**Goals:**

- 让竞赛编程题复用现有题目模板加载和“重置为模板”能力。
- 使用竞赛题目的真实 problem ID 请求模板。
- 保持已有本地草稿优先级、竞赛提交链路和访问控制不变。

**Non-Goals:**

- 不修改后端 API、支持包构建或题目模板解析逻辑。
- 不为客观题套卷引入代码模板。
- 不改变模板加载失败时的现有容错行为。

## Decisions

### 复用现有题目模板端点

竞赛模式继续调用 `/api/v1/problems/:id/template`，其中 `id` 使用 `workspaceProblem.id`（竞赛题目的 `problem_id`）。这样可以复用后端已有权限和模板解析逻辑，避免新增竞赛专用端点导致两套行为分叉。

备选方案是新增 `/api/v1/contests/:contestId/problems/:label/template`，但这只会重复转发已有题目资源，增加 API 面积和竞赛访问控制维护成本，因此不采用。

### 在页面层提供统一模板回调

将编辑器页面的 `templateUrl` 从“仅普通模式提供”调整为“普通模式与竞赛模式均提供”。`EditorWorkspace` 已经负责等待草稿恢复、空代码保护、加载状态、404 容错和手动重置，继续集中这些行为可以避免在页面中复制异步逻辑。

### 回归验证覆盖两种模式

增加针对模板 URL 选择逻辑的纯函数/页面配置测试，验证竞赛和普通模式都指向题目模板端点，并保留现有竞赛提交 URL 不变。若当前测试工具无法直接挂载 Nuxt 页面，则使用可独立测试的 URL 构造函数承载该选择逻辑。

## Risks / Trade-offs

- [Risk] 竞赛 API 对题目模板端点的访问控制与普通题目不同，可能导致模板请求被拒绝 → 通过现有端点的认证/权限测试和竞赛页面手工链路验证确认；若端点拒绝竞赛用户，再单独调整后端权限，不在本变更中预先复制接口。
- [Risk] 用户已有竞赛草稿会覆盖模板自动加载 → 复用 `EditorWorkspace` 的空代码判断和草稿恢复顺序，只有没有有效草稿时才加载模板。

## Migration Plan

无需数据迁移或部署脚本变更。发布前运行前端格式化、lint、回归测试；回滚时恢复竞赛 `templateUrl` 未提供的页面配置即可。

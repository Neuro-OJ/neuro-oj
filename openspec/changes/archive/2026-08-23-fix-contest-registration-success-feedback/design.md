## Context

竞赛详情页的 `register()` 当前把注册请求、竞赛详情刷新和题目加载放在同一个 `try/catch`。浏览器复现表明注册记录已经写入，但后续刷新异常会落入同一个错误分支，页面因此显示“网络连接失败”。后端接口和数据模型无需调整。

## Goals / Non-Goals

**Goals:**

- 仅将注册请求错误与注册成功后的界面同步错误分离。
- 注册接口成功后立即更新本地参赛状态并显示成功反馈。
- 后续刷新失败保持静默或记录开发日志，不覆盖已报名状态。

**Non-Goals:**

- 不修改报名 API、数据库约束或重复报名返回码。
- 不改变真实注册失败的错误文案和未登录跳转逻辑。

## Decisions

- 先单独捕获 `api.post()` 错误；只有该请求失败时才写入 `registerError`。这样 4xx/5xx 仍由现有 `extractApiError()` 提示。
- 注册请求成功后先更新响应中的本地竞赛状态，再尝试 `refresh()` 和题目加载。刷新失败不得重新进入注册错误分支；如果竞赛尚未开始，题目加载本来就不会发起请求。
- 保留后续刷新以同步参赛人数等服务端字段，但将它视为非关键的 UI 同步步骤。相比让整个成功流程失败，这能避免用户重复点击并收到误导性提示。

## Risks / Trade-offs

- [刷新持续失败时参赛人数等非关键字段可能暂时过期] → 页面仍保留原有刷新机制，用户重新加载页面即可同步；本地报名状态以已成功的 201 为准。
- [本地状态更新与服务端响应之间存在短暂差异] → 仅在注册接口明确返回成功后更新，真实注册失败不会更新状态。

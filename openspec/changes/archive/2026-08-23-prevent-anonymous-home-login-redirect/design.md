## Context

主页布局中的社区通知未读数属于后台状态探测，但对应接口只允许登录用户访问。统一 API 层默认会把 401 转换为登录跳转，因此匿名访问主页时会被错误重定向。

## Goals / Non-Goals

**Goals:**

- 让匿名用户访问主页时，私有后台状态请求失败不会改变当前路由。
- 保留受保护业务页面的默认 401 登录跳转和登录态清理。
- 通过调用方显式声明可选认证语义，避免削弱全局认证保护。

**Non-Goals:**

- 不修改社区通知接口的权限要求。
- 不把通知未读数改成公开数据。
- 不调整 JWT、Cookie 或后端认证中间件。

## Decisions

- **在调用方关闭 401 跳转，而不是修改全局默认值。** `useApi` 已支持 `redirectOnUnauthorized`，保留默认 `true` 可以避免受保护页面静默失败；通知未读数调用显式传 `false`，只影响可选的后台探测。
- **匿名时跳过通知未读数请求。** 导航栏只有在存在用户时才加载未读数；同时保留 `redirectOnUnauthorized: false` 作为令牌失效或状态竞态时的兜底，避免已登录状态过期再次把公共主页送去登录页。
- **不吞掉错误对象。** `useCommunityNotifications` 继续捕获后台请求错误并把未读数归零，API 层仍抛出原错误，保持现有错误处理契约。

## Risks / Trade-offs

- [Risk] 已登录用户的 token 失效后未读数不会触发全局登出 → [Mitigation] 该请求只是角标后台刷新；受保护页面和实际业务请求仍使用默认 401 跳转，用户进行需要认证的操作时会重新登录。
- [Risk] 未来新增类似后台探测请求时忘记关闭跳转 → [Mitigation] 在 API 层规范和回归测试中明确 `redirectOnUnauthorized: false` 的使用场景。

## Migration Plan

无需数据迁移或部署顺序调整。发布前运行前端格式化、Lint、类型检查和相关测试；若需回滚，仅回退前端调用方改动即可。

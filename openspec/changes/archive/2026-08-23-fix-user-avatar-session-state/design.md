## Context

认证代理目前只把用户的基础身份字段写入 `noj:session`，而 `UserMenu` 为了兼容 session 缺少头像字段的情况会探测公开头像端点。公开端点对无头像用户返回 404；因此需要让 session 明确携带头像状态，同时保留旧 Cookie 的兼容路径。

## Goals / Non-Goals

**Goals:**

- 在认证代理、运行时校验和客户端 session 恢复之间一致传递 `avatar_url`。
- 用 `null` 表示已知无头像，避免导航栏产生不必要的 404 请求。
- 不含字段的旧 session 仍能正常恢复并按兼容逻辑回退。

**Non-Goals:**

- 不修改头像 API 的状态码、缓存策略、存储格式或数据库 schema。
- 不改变其他用户头像展示位对 `avatar_url` 的默认处理。

## Decisions

- **把头像状态放入可读 session Cookie**：登录响应已经包含用户公开头像字段，复制这一字段比在每次页面加载时额外调用 `/auth/me` 更快，也能在导航栏首次渲染前区分 `null` 和未知状态。
- **字段保持可选以兼容旧 Cookie**：解析器接受字段缺失、字符串或 null；客户端对缺失字段先显示默认头像并刷新一次当前用户资料，不会渲染必然 404 的头像请求。
- **由代理写入规范化的 null**：用户响应缺少头像字段时写入 `null`，避免新 session 再产生第三种“登录成功但字段未定义”的状态。

## Risks / Trade-offs

- [Risk] 头像上传或删除后已有 session 中的头像状态可能短暂滞后 → 上传/删除页面仍会更新本地用户状态；下一次登录或认证 Cookie 更新会重新同步。
- [Risk] 旧 session 首次进入页面会额外刷新一次当前用户资料 → 该请求仅在头像字段缺失时执行一次，成功后可避免后续头像 404。

## Migration Plan

无需数据库迁移。部署后新登录和改密产生的 session 会携带头像状态；旧 session 在自然过期或重新认证后更新，期间按兼容逻辑运行。

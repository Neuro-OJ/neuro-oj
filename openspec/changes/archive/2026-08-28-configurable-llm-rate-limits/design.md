## Context

当前 `noj-llm-gateway` 在限流调用处将用户和 IP 分钟限流都传入固定值 60。配置加载集中在 `src/config.ts`，应用工厂将同一份配置传给 LLM 路由，因此可以在不改变请求协议的前提下沿现有依赖链传递配置。

## Goals / Non-Goals

**Goals:**

- 在启动阶段解析并严格校验两个独立的分钟限流配置。
- 将配置传递到限流检查，保持 Redis Lua 的原子检查与 UTC 分钟窗口。
- 覆盖默认值、非法值和自定义值的测试，并同步模板和运营说明。

**Non-Goals:**

- 不改变 Redis 键结构、Lua 原子语义、其它调用量/Token/费用配额。
- 不增加动态后台配置、响应限流头或 `Retry-After`。

## Decisions

- **在 `GatewayConfig` 中保存已校验的数值。** 这样启动后限流路径不重复解析环境变量，也能让配置错误尽早暴露。相比在每次请求中读取环境变量，该方式更明确且避免运行时配置漂移。
- **为 `enforceAndCount` 增加用户/IP 限流配置参数。** 该函数是分钟限流和其它配额汇合的边界，显式传参能保持其它调用者可测试，并避免将环境读取耦合到业务逻辑。相比在 `limits.ts` 内部直接读取环境变量，显式传参更易测试和复用。
- **保持两个变量缺失时均回退 60。** 这是向后兼容策略；只配置其中一个维度时，另一个维度仍独立回退默认值。
- **严格接受十进制正整数文本。** 使用完整字符串匹配和范围校验，拒绝小数、空白混入、符号和非有限值，避免配置看似成功但实际含义不明确。

## Risks / Trade-offs

- [错误配置导致网关无法启动] → 启动错误包含具体环境变量名称，并在两个环境变量模板与运营文档中说明合法范围。
- [限流值过大造成 Provider 额度风险] → 默认值保持 60，实际部署由运营者根据 Provider 额度设置，并保留现有日/月及费用配额作为第二层保护。
- [测试 FakeRedis 无法观察两个限流参数] → 增强测试替身记录 `eval` 的脚本参数，并断言用户/IP值分别传入，同时不依赖真实 Redis。

## Migration Plan

1. 部署新版本；未设置新变量的实例继续使用每分钟 60 次。
2. 需要调整时，在网关环境中设置两个正整数并重启网关，使配置在启动时生效。
3. 若需回滚代码，可移除新变量；旧版本忽略未知环境变量并恢复固定 60 行为。

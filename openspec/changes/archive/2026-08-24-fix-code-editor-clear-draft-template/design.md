## Context

`EditorWorkspace` 已有 `resetTemplate()` 流程：确认后请求模板，请求成功才清除草稿并更新 `code`，请求失败时保留原内容。设置面板的“清除当前草稿”则直接调用 `useDraftStorage().clear()`，只操作 localStorage，没有触发模板恢复。

## Goals / Non-Goals

**Goals:**

- 让设置面板的“清除当前草稿”与题目模板恢复保持一致。
- 复用现有模板请求、错误提示和草稿保存机制，保证失败时不覆盖内容。
- 保持竞赛题和没有模板地址的上下文安全，不发起无意义请求。

**Non-Goals:**

- 不修改题目模板 API、模板内容或草稿存储格式。
- 不改变工具栏“重置”按钮的确认和恢复语义。

## Decisions

- 在 `EditorWorkspace` 增加面向 UI 事件的处理函数，将“清除当前草稿”事件转发到已有 `resetTemplate()`；不直接让子组件操作 localStorage。
- 不复制模板请求逻辑。`resetTemplate()` 继续遵循“模板成功后才 clear + 替换 code”的顺序，因此请求失败天然保留原代码和草稿。
- 通过纯函数/可测试的边界（如已有模板恢复逻辑可抽取的最小辅助函数）覆盖成功与失败路径；不为完整 Monaco 编辑器引入重量级挂载测试。

## Risks / Trade-offs

- “清除当前草稿”会从单纯删除本地记录变成覆盖编辑器内容的操作；这是 issue312 要求的用户可见行为，且现有模板重置确认弹窗会防止误操作。
- 模板恢复成功后由 `code` watcher 异步保存，页面立即刷新极短时间内可能尚未写入；沿用现有 800ms 防抖策略，不引入新的存储机制。

## Context

NOJ 当前由 Deno/Hono API、Nuxt UI、PostgreSQL、Redis Pub/Sub 与数据库化系统设置组成。用户主页、私信、SSE、RBAC、审计日志和 Markdown 渲染可复用，但没有公开内容、互动关系或内容治理模型。部署既可能面向互联网，也可能是学校或企业内网实例，因此社区能力不能假设内容公开。

## Goals / Non-Goals

**Goals:**

- 用一套一致的数据模型承载题解、讨论和短动态。
- 让管理员无需重启即可裁剪模块、收紧访问、开启预审或切换部署预设。
- 复用现有 RBAC、审计、SSE 与 Markdown 安全边界。
- 在中小型单实例部署中保持查询简单、索引明确且不依赖额外基础设施。

**Non-Goals:**

- 不实现多社区空间、多租户或跨实例联邦。
- 不实现图片/附件上传、私信合并、全文推荐算法或多级树状评论。
- 不修改评测 Worker、评测消息协议或题目支持包。

## Decisions

### 统一帖子模型

`community_posts` 用 `type=solution|discussion|moment` 区分内容，并通过服务层与数据库 CHECK 约束上下文字段：题解必须关联题目，讨论必须关联板块，动态无标题。统一表可复用评论、互动、审核和搜索逻辑；相比三套内容表减少重复服务与迁移。

帖子状态为 `draft|pending|published|hidden|deleted`，删除和管理处置均保留记录。评论使用同表 `parent_id`，服务层仅允许回复根评论，从而提供一级视觉嵌套和稳定分页。

### PostgreSQL 按需生成时间线

主动短动态保存在帖子表，首次 Accepted、发布题解、参加竞赛等系统事件保存在 `community_activity_events`。动态流通过 `UNION ALL` 按 `(created_at,id)` 游标合并，并按关注关系过滤，不将每条事件扇出到所有粉丝。该方案适合 NOJ 的单实例和私域规模，避免 Redis 持久时间线与数据回补问题。

### 配置与权限分工

布尔与整数策略进入现有 `system_settings` 注册表的 `community` 分类；板块结构和板块角色授权进入专用表。全局“能否执行某动作”由 RBAC 控制，特定板块的读取、发帖、管理由 `community_board_role_grants` 进一步收紧。

预设通过单个管理 API 事务化写入相关设置：`public`、`private`、`knowledge`。预设不删除数据；关闭模块只隐藏入口并拒绝新请求，重新开启后原数据恢复可见。

### 审核与处罚

默认内容即时发布。账号注册时间位于配置预审窗口内时，新内容进入 `pending`，作者和审核员可见。举报只进入队列并提高优先级，不自动隐藏内容。社区处罚单独限制社区写操作，不复用全站封禁，避免学习和评测能力被一并剥夺。

### 通知与实时事件

通知持久化到 `community_notifications`，回复、点赞、关注和审核结果写入通知后，复用 `noj:events:user:<id>` 发布 `notification:new`。API 返回通知未读数；现有私信未读数保持独立。

### Markdown 与外链图片

数据库保存原始 Markdown。前端继续使用 markdown-it、KaTeX 和 DOMPurify；图片仅允许 HTTPS。启用外链图片时为图片补充 `loading=lazy`、`referrerpolicy=no-referrer`，关闭时将图片节点替换为普通链接。首版不引入服务端图片代理。

### 索引和计数

所有外键列建立索引；已发布内容、待审核内容和未读通知使用部分索引。点赞、收藏、关注以复合唯一键保证幂等。列表计数通过聚合查询返回，不在首版维护易漂移的缓存计数字段。

## Risks / Trade-offs

- [关注量和内容量很大时按需时间线查询变慢] → 使用游标、复合/部分索引；达到瓶颈后再引入物化时间线。
- [外链图片可泄露访问者 IP] → 私域预设默认关闭，启用时强制 HTTPS 与 no-referrer，并在后台明确提示。
- [统一帖子表存在类型相关空字段] → CHECK 约束和集中输入校验保证不变量。
- [预审造成用户误解] → 创建响应明确返回 `pending`，UI 展示审核中状态。
- [模块关闭后旧深链接行为不一致] → 配置 API 返回统一能力矩阵；被关闭模块的 API 返回 `FEATURE_DISABLED` 403。

## Migration Plan

1. 追加 Drizzle schema 与迁移，所有新表为空，不影响现有数据。
2. 启动时幂等写入社区权限和默认板块，并注册社区设置默认值。
3. 部署 API 和管理后台，默认使用 `private` 策略：登录可读、普通用户可写、外链图片关闭。
4. 管理员确认策略后逐项开放前台入口。
5. 回滚应用时保留新表；旧版本忽略它们。迁移不删除或重写现有业务表。

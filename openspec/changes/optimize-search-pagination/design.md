# 设计：搜索分页避免默认精确计数

## 决策

服务层的三个搜索函数均接受可选 `includeTotal`（默认 `false`）。列表 SQL 统一取 `limit + 1` 条，保留前 `limit` 条并以多出的结果生成 `has_more`。仅 `includeTotal=true` 时执行现有 `COUNT(*)` SQL，并在响应中返回 `total`。

路由读取 `include_total=true|1`，并向客户端返回始终存在的 `has_more`，以及仅在显式请求时存在的 `total`。前端不请求 `include_total`，通过 `has_more` 显示上一页/下一页，不再生成依赖总页数的页码列表。

## 兼容性

这是 API 响应字段的行为调整：`total` 从默认字段变为可选字段。仓库内唯一消费者是搜索页，随本变更同步修改。外部消费者若需要精确数值，须添加 `include_total=true`。

## 性能基准

100k 条题目中仅少量记录包含唯一查询词，用于验证可索引的高选择性路径。另保留全命中查询，预算设置为适合 GitHub 共享运行器的值，以监测灾难性回退而非制造噪声。两种情景均只验证默认无计数的搜索路径。

## 风险与缓解

- `limit + 1` 会多取一行：其代价固定且远低于精确计数。
- 无法显示总页数：搜索结果数量本就动态，下一页导航更符合实时搜索体验。
- `include_total` 可能被滥用：仅作为显式兼容路径，后续可在监控中评估是否需要限流或缓存。

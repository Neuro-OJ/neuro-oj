## Context

提交详情 API 已经将评测器返回的 JSON `details` 透传给提交者和管理员，但没有稳定的测试点 DTO，提交详情页也只展示原始评测输出。现有样例评测器使用 `visible`/`hidden` 分组和旧字段名，且没有记录单点耗时；项目已有 Redis 评测结果规范，可作为统一契约的基础。

## Goals / Non-Goals

**Goals:**

- 让新的评测器可以通过 `details.cases` 提供可渲染的标准测试点结果。
- 让样例题输出单点耗时、状态、期望输出和实际输出。
- 在提交详情页展示标准格式和历史格式，并对隐藏测试点脱敏。
- 不改变总分、提交状态机、数据库表结构和提交详情接口路径。

**Non-Goals:**

- 不为所有自定义题目的任意 `details` 自动推断测试点。
- 不把隐藏测试数据存储到新的数据库字段或提供给普通用户。
- 不新增前端测试框架；使用现有 Deno 工具测试纯 TypeScript 转换逻辑。

## Decisions

### 1. 使用扁平的标准 `details.cases` 数组

新评测器统一返回 `details.cases`，每项使用 `case_id`、`status`、可选 `visibility`、`time_ms`、`memory_kb`、`expected_output` 和 `actual_output`。扁平数组便于前端渲染和跨题目复用；历史的分组结构由前端适配器兼容，不要求一次性重测旧提交。

备选方案是继续让每道题定义自己的详情结构，但这无法提供通用 UI，也会把字段兼容成本推给用户。

### 2. 在评测器内测量单点耗时

样例评测器在每次 `SolutionRunner` 调用前后使用单调时钟测量耗时，并把毫秒值写入对应测试点；评分公式和总耗时不变。评测器才知道一个测试点的实际边界，Judge 层不应根据整段容器 stdout 反推单点耗时。

### 3. 前端通过纯函数归一化并脱敏

新增前端工具将标准结构和历史结构转换为统一数组。缺失或类型错误的字段按 null 处理，无法识别的条目跳过；隐藏条目的输入、期望输出和实际输出始终在归一化时清除，避免模板层误用原始字段。

### 4. 用独立组件承载明细面板

新增提交测试点组件，提交详情页只负责传入 `result.details` 和总结果。组件使用现有 Tailwind 样式和 Lucide 图标，表格在窄屏下横向滚动，长输出使用可折叠区域，避免继续扩大详情页的复杂度。

## Risks / Trade-offs

- [自定义评测器格式不一致] → 规范只保证标准 `details.cases`；前端兼容当前历史格式，未知结构安全隐藏。
- [隐藏数据泄露] → 新样例不返回隐藏输入/答案/实际输出；归一化层对隐藏条目再次清除敏感字段。
- [输出过长影响页面] → 输出区域限制最大展示长度并支持展开，原始总评测输出仍沿用 API 现有截断策略。
- [旧提交没有单点耗时] → UI 显示 `--`，不阻断旧结果查看。

## Migration Plan

1. 发布包含新样例评测器和 UI 适配器的版本；已有 `evaluation_results` 无需迁移。
2. 新提交使用 `details.cases`，旧提交由前端兼容显示。
3. 回滚时恢复旧前端与评测包即可，数据库结构和提交结果格式仍向后兼容。

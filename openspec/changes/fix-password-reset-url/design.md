## Context

当前认证路由负责从请求头构造基础 URL，再把该值传入密码重置服务；服务随后直接将其用于邮件链接。密码重置服务是所有令牌生成和邮件发送的共同边界，因此 URL 可信度判断应集中在那里。相关行为契约见 `specs/user-auth/spec.md` 的密码重置请求要求。

## Goals / Non-Goals

**Goals:**

- 让服务端配置的 `APP_URL` 成为重置链接的唯一生产来源。
- 在非生产环境保留基于请求头的本地开发回退。
- 生产环境缺少可信 URL 时在生成令牌前安全短路，同时不破坏统一 200 防枚举响应。
- 通过回归测试验证配置优先级、Host Header 注入防护和缺失配置行为。

**Non-Goals:**

- 不改变密码重置令牌格式、有效期、数据库结构或 API 响应消息。
- 不新增 URL 配置的管理后台设置，不把 `APP_URL` 变成可由管理员运行时修改的 DB-backed 设置。
- 不重做邮件 Provider 或请求头可信代理的既有机制。

## Decisions

### 在密码重置服务内解析 URL

`requestReset` 接收请求层提供的 URL 仅作为开发回退，并在自身读取 `APP_URL`。当 `APP_URL` 为非空值时始终使用它；当 `NOJ_ENV=production` 且 `APP_URL` 缺失时记录不含邮箱、Host 或令牌的错误日志并立即返回。这样即使未来新增调用方，也不会绕过生产安全边界。

备选方案是只在路由层解析 URL，但这会把安全约束暴露给每个调用方，新增调用方容易重新引入 Host 注入，因此不采用。

### 只做轻量 URL 规范化

读取配置后去除末尾斜杠，再拼接固定的 `/reset-password?token=...` 路径；不引入新的 URL 校验库，也不改变已有支持路径的 `APP_URL` 配置语义。环境变量本身由部署系统控制，超出本需求的协议/域名策略校验另行处理。

### 生产缺失配置在生成令牌前短路

缺失 `APP_URL` 时不查询用户、不写入 token、不调用邮件 Provider，避免产生无法使用或可能错误的令牌。路由忽略服务的内部短路结果，继续返回原有统一响应，以保持邮箱枚举防护。

### 以可捕获结构化日志记录配置错误

使用现有 logger 记录固定消息和模块/事件字段，不记录请求 Host、邮箱、重置令牌或完整 URL。测试通过 logger sink 验证错误日志存在，避免依赖控制台文本。

## Risks / Trade-offs

- [Risk] 生产部署升级后未及时配置 `APP_URL`，用户无法收到重置邮件。→ 通过环境模板、生产缺失日志和回归测试明确暴露配置错误；接口仍保持统一 200，避免泄露账号存在性。
- [Risk] 非生产回退仍信任请求头。→ 该路径仅保留给开发/测试；生产分支在服务层明确拒绝回退，且测试覆盖恶意 Host。
- [Risk] 配置末尾斜杠可能造成重复斜杠。→ 拼接前统一去除末尾斜杠，不影响带路径的基础 URL。

## Migration Plan

1. 发布代码、测试和两个环境模板的变更。
2. 生产部署在启动前设置 `APP_URL` 为固定的 HTTPS 应用地址。
3. 若回滚代码，新增环境变量可保留，不影响旧版本；旧版本仍有 Host 注入风险，因此回滚只作为短期故障恢复手段。

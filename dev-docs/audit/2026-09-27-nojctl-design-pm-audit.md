# nojctl 部署运维 CLI 设计 —— 产品视角审计

- 审计对象：`dev-docs/superpowers/specs/2026-09-27-nojctl-deploy-cli-design.md`（665 行，`Status: draft`，基线 `main @ fc20865e`）
- 审计视角：产品（用户价值 / 用户旅程 / 信息架构 / 风险与信任 / 范围 / 度量），**不是**代码评审
- 目标用户：没接触过服务器运维的运营者，典型画像 = **学校教练**（拿得到一台 Linux 服务器和一个域名，但不能被迫理解 compose / env 文件 / rootless Docker / 迁移不可逆）
- 审计方式：**只读**。除本文件外未修改任何文件、未提交、未运行任何改变系统状态的命令
- 证据规则：涉及现有代码/文档的判断一律给 `file:line`；spec 判断给章节号与行号；无法从仓库证实的一律标注 **假设 A#**（见附录 A）

**本次审计的一个方法论说明**：这个 spec 的技术质量明显高于平均水平（单一状态源、fail-closed、黄金文件、故障注入矩阵、退出码契约）。因此审计重点不在"能不能做出来"，而在两处：**第一公里**（教练在到达向导之前与走到完成页之后，是否真的得到了"可用的站"）和**长期自我维护**（第二次改配置、磁盘满了、口令丢了、教练换届时会发生什么）。

## 1. 总体结论

### 结论：**有条件进入实施**

理由（三条）：

1. **技术主干值得实施**：`apply` 事务 + 世代 + 失败关闭 + 生成式部署描述，直接命中 spec §3 列出的真实痛点，且 §10 的故障注入矩阵与 §7.3 的 CI 不变量是"原子性"这类口号唯一可信的证明方式。这部分不需要重做。
2. **但"零基础教练能自己把站开起来并维持下去"这一唯一的产品主张，目前有 7 个 Blocker 级别的断点**：其中 B1（HTTP 明文部署 → core 生产配置校验致命失败 / Cookie 被丢弃，**且这是从 v1 的倒退**）与 B2（邮件默认 disabled → 学生无法注册且后台改不了）会让"部署成功"与"学校真的能用"之间出现裂缝；B3（没有停站/开站）、B4（卸载后无法重装）是日常与应急的死路；B5（不接管既有安装 + 不读 v1 备份）会让**当前全部现网部署者**——也就是本设计的第一批用户——无处可去；B6（同机第二个实例接管第一个实例的容器与数据卷）是静默的数据事故；B7（Docker 没装/没权限时只有一条"退出 3"）是教练到达向导之前的第一道墙。
3. **结论的落点是"有条件"，条件是清单化的**：下面 §1.1 的 P0 前置条件必须在本 spec 定稿（`Status: draft → approved`）前落进文档，其中 P0-1、P0-2、P0-5、P0-6 是**改文档 + 改一屏交互**的成本，不是重写架构。

### 1.2 这套设计做对了什么（审计同时确认的优点，避免后续评审把这些改掉）

- **单一状态源 + 计划/执行分离**（§4.2 不变量 1–3）：这是"原子"能被测试的前提。
- **失败关闭**（§1.2 判断 4、§4.2 不变量 6）：不认识 `deploy_format`、别名无解、资产不齐、目录外来一律拒绝，不做静默回落——对"不知道该信谁"的教练，这正是需要的性格。
- **生成物归 CLI、配置归用户**（§4.2 不变量 7）与"文档化的键必进容器"两层门禁（§7.4）：直接消灭 spec §3.4 的 12 个"填了不生效"键；`.env.prod.example` 由 schema 自动生成（§5.7）比从 Release 下载模板（v1 做法，`noj-cli/README.md:32`）正确得多。
- **`TRUSTED_PROXIES` 由生成的 compose 子网确定性算出**（§5.5 屏幕 2）：`noj-core` AGENTS.md 要求生产必须配它，而 v1 让用户自己填——这条改对了（`.env.prod.example:43` 现在是手写值）。
- **`backup verify` 不依赖运行中的栈**（§8.2）与 `prune` 默认 dry-run（§8.2）：把"备份是否可信"从祈祷变成可执行检查。
- **二进制不写 PATH、不自我复制**（§9.1）：删掉了 v1 `noj-cli/README.md:26-29` 的 PATH 注册魔法，少一类"升级后命令指向旧二进制"的诡异故障。
- **崩溃恢复不需要专用命令**（§6.4："再跑一次 `apply`"）：对教练而言，少一个要记住的名词就是多一分成功率。

## 2. 发现表

严重度定义：

- **Blocker**：按现设计实施，目标用户很可能完不成首次部署，或遭遇站点/数据损失；必须在本设计定稿前修掉或明确取舍。
- **Major**：会造成明显卡顿、误导或返工，需要修，但不阻断实施。
- **Minor**：影响体验与专业度，可在实施中顺手处理。

### 2.1 Blocker

#### B1（Blocker）HTTP 明文部署：core 可能直接起不来或被浏览器丢 Cookie，而 VERIFY 只验 HTTP 200——这是相对 v1 的倒退

**spec 出处**：§5.5 屏幕 1 第①问"对外地址（域名或 IP + 端口，默认 8080）"（L235）、屏幕 2"推导与生成（不问）"清单（L236）、完成页（L241）；§6.6 VERIFY 检查集（L352-362）；§6.3 失败→回退（L335-337）；§11 验收口径第一条"从零到可用"（L625）

**仓库证据**：

- `docker-compose.prod.yml:10`（`name: noj-prod`）、`:12`（`NOJ_ENV: production`）、`:317`（`NGINX_PORT:-8080`）、`:46` 与 `:152`（`NOJ_ALLOW_INSECURE_HTTP:-false` → `NUXT_ALLOW_INSECURE_HTTP`）
- `.env.prod.example:40`：`NOJ_ALLOW_INSECURE_HTTP=false`（默认关闭）
- `noj-core/src/shared/config/production-config.ts:68-126`：`APP_URL` / `CORS_ALLOWED_ORIGINS` 必须是 HTTPS，**除非**显式开启 `NOJ_ALLOW_INSECURE_HTTP`（错误文案见 `:84`、`:117`）
- `noj-core/src/main.ts:273`：`await fatalStep("生产配置校验", …)` —— **这是致命步骤**
- `noj-ui/server/api/[...slug].ts:31-45, 237`：`secure: isProductionEnv() && !allowsInsecureHttp()`；代码注释自己写着"避免浏览器不保存 Cookie 导致'未提供认证令牌'"（`:34-35`）
- **v1 处理过这件事**：`noj-cli/src/prod/config.ts:1071` → `values["NOJ_ALLOW_INSECURE_HTTP"] = String(!https);`，且 v1 的向导**明确问 HTTP/HTTPS**（`noj-docs/docs/operators/production-deploy.md:71`）

**对学校教练的具体影响**：教练按最自然的路径走——在向导①里填服务器 IP、端口用默认 8080。设 `APP_URL=http://<ip>:8080`：

- 若 nojctl 没有像 v1 那样把 `NOJ_ALLOW_INSECURE_HTTP` 置为 true，则 **`noj-core` 在"生产配置校验"这一步致命退出**，容器起不来 → VERIFY 的 `/healthz` 不通过 → 触发"自动回退"，但**首装没有 `previous` 世代**（§6.3 L335 只描述回退到 previous，未定义首装失败）→ `state=partial`、退出 7，教练拿到一个"需要人工介入"的终点，而真正的原因（一个 env 键）不在任何他看得懂的地方。
- 即便绕过了校验，明文 HTTP 下浏览器**不保存 Secure Cookie**（`noj-ui` 注释自述的正是这个故障），表现为"登录以后又变回未登录 / 提示未提供认证令牌"。教练会怀疑"密码错了"，而不是"Cookie 标志错了"。
- 反向情形同样糟糕：如果 nojctl 为域名默认补 `https://`，而教练的域名还没做 DNS、也没有 TLS 终止（容器 nginx 只处理 HTTP，`docker-compose.prod.yml:8` 与 `production-deploy.md:131-132` 都写明 TLS 由外部边缘终止），那么 `APP_URL` 校验能过，但**站点在浏览器里根本打不开**，而完成页仍然宣布成功。

**建议改法（可直接照做）**：

1. §5.5 屏幕 1 恢复一问：`对外协议：HTTP（临时/内网） 或 HTTPS（有域名和证书/反代）`；若用户填的是 `https://…`，必须在屏幕 2 明确输出"TLS 不由本站点提供，需要你在外部（宝塔 / 宿主 Nginx / Caddy）转发到 `127.0.0.1:8080`"，并附两行可复制的 Caddy/Nginx 示例。
2. §5.5 屏幕 2 的推导清单加入 `NOJ_ALLOW_INSECURE_HTTP`（值 = 协议是否 http），并在摘要页把它翻译成人话："当前使用明文 HTTP：已放宽 Cookie 安全限制；配置 HTTPS 后请运行 `nojctl apply` 收紧"。同时在屏幕 5 摘要中显示"由你填写/由我推导的键数"，让"我推了什么"可见。
3. **把 core 的校验前移**：nojctl 在 PREPARE 里**复制** `production-config.ts:68-126` 的判据（APP_URL/CORS 必须 https，除非 flag），使失败发生在"零写入、退出 3"（§5.5 屏幕 4 已有的语义），而不是在 45 分钟拉镜像之后。长期做法是让镜像提供 `noj config check --json` 由 `compose run` 调用（与 §6.7 的 A1 思路一致）。
4. §6.6 VERIFY 增加两条：**真实登录**（POST `/api/v1/auth/login` 拿到 cookie，再带 cookie 调 `/api/v1/auth/me` 期望 200）；**judge 开启时一次样例评测**（仓库自带样例题 `noj-core/data/problems-src/1001`，可用 `problems build/import` + 一次提交）。
5. §6.3 增补"首装失败"行：无 `previous` 时不得宣称回退，输出必须是"未安装成功，已清理到 X；原因：<键名>；下一步：<可复制命令>"，退出码 3 或 6（而不是 7）。

#### B2（Blocker）邮件默认 disabled ⇒ 学生无法注册，而"稍后再配"没有自助补救路径

**spec 出处**：§5.5 屏幕 1 第③问"邮件 Provider（disabled/aliyun/tencent + 凭据掩码输入，或'稍后再配'）"（L235）；§5.7 `.env.prod` 是唯一真相源、无 `config` 子命令（L276-282）；完成页下一步只有 `versions`/`doctor`/`backup create`（L241）

**仓库证据**：

- `noj-core/src/main.ts:195-203`：邮件未就绪时"**公开注册已被禁止**（仅允许站点引导阶段的首次注册），开放公开注册前请在管理后台完成邮件配置并发送测试邮件"——**注意这句启动日志指向"管理后台"，但见下一条**
- `noj-core/src/shared/config/settings-registry.ts:261-270`：`email_provider` 的 `scope: "bootstrap"`（env-owned，启动期定型只读）
- `noj-core` AGENTS.md 明确：bootstrap 项"由 env 唯一决定，**不读 DB**；后台只读展示"
- `noj-core/src/domains/admin/routes/system.ts:234-265`：后台邮件接口只有 `status` 与 `test-send`；未就绪时 `test-send` 返回 400 并提示"请先补全配置"
- `noj-docs/docs/operators/production-deploy.md:125`：`EMAIL_PROVIDER=disabled` 时"公开注册被禁止"

**对学校教练的具体影响**：教练的 Day-1 目标是"让学生注册进来做题"。向导第③问里的"稍后再配"读起来是"以后再说，不影响"，实际后果是**公开注册被关闭**，且**唯一补救方式是手改 `.env.prod` 里的 4 个键（`EMAIL_PROVIDER` + 3 个凭据）再运行 `apply`**——后台改不了（bootstrap scope）。教练会先去后台找邮件设置、看到"未就绪"、点"发送测试邮件"拿到 400，然后卡在那里。这是"部署成功但学校用不了"的第二条裂缝，而且它比 B1 更隐蔽：站点首页 200、能登录管理员账号，只有学生注册那一步失败。

**建议改法**：

1. 屏幕 1 第③问的选项文案改为带后果的：「不配置（**学生将无法自助注册**，只能由管理员手动建号，且之后必须修改服务器上的配置文件才能开放）」「阿里云 DirectMail」「腾讯云 SES」。同时把"稍后再配"这个模糊选项**删掉**。
2. 完成页在"邮件未配置"时插入固定区块：`⚠ 公开注册目前是关闭的` + 三行可复制内容（要改的 4 个键、值从哪来、`nojctl apply`）。
3. §5.7 的"无 `config` 子命令"需要按 M4 的建议放宽：至少提供一个**白名单** `nojctl config`（键集合 = 向导已知的键 + 邮件 4 键 + 对外地址相关键），复用向导的校验与掩码输入。否则"零基础"只在第一次安装成立。
4. 向 core 提一个跨模块 follow-up：把 `email_provider` 及其凭据从 `bootstrap` 迁到 `runtime`（数据库管理），让后台邮件页真正做到它启动日志承诺的事。这条应写进 §13，因为它决定了 nojctl 是否需要长期承接邮件配置。

#### B3（Blocker）没有"停站/开站"：`stopped` 状态下没有任何命令能让站点恢复运行

**spec 出处**：§5.1 命令表（L149-160：`deploy` / `apply` / `versions` / `status` / `logs` / `doctor` / `backup` / `uninstall`，无 `start`/`stop`/`restart`）；§5.6 规则⑤"栈处于 `stopped` 时摘要注明'切换后会启动'，然后照常启动"（L261-262）；§2 术语把 `stopped` 列为四个状态之一（L63）；§6.1 `state.json` 同样有 `stopped`（L296-297）

**仓库证据**：v1 有 `start|stop|restart`（`noj-cli/README.md:57`；`noj-docs/docs/operators/production-deploy.md:143-146`），教练现在正在用它们。

**对学校教练的具体影响**：

- **假期/停机省钱**："暑假把服务器停掉"→ 没有 `stop`，只能 `uninstall`（那会移除生成物，见 B4 → 无法重装）；不卸载就只能让容器一直跑。
- **维护窗口/故障处置**：`apply` 只在**有变更**时才会"照常启动"（§5.6 规则⑤挂在"切换"语境下）；如果栈是 `stopped` 且没有配置漂移，`apply` 走到 no-op 分支（§5.6 L255，退出 0），站点**仍然停着**。这是一个真实的死路：状态是 `stopped`，没有任何命令的目标状态是 `running`。
- **被攻击/被刷时**：教练的第一反应是"先把站关掉"。也没有。

**建议改法**（两种，选一即可，推荐同时做）：

1. **语义修正（零成本）**：把 `apply` 的期望状态显式定义为"`current` 世代 + 运行中"，即 no-op 判定加入"栈是否在运行"；`stopped` + `apply` = 启动动作（免门禁，摘要一行"将启动当前世代 <版本>"）。这完全符合 §1.2 与 §5.1 给 `apply` 的定位（"唯一让实际与期望状态一致的命令"），也顺带修掉"崩溃后系统处于 stopped 且自己起不来"的风险。
2. **补命令**：新增 `nojctl stop`（停栈，保留一切）与 `nojctl start`（启动 `current` 世代，不需要联网、不重建文件），并在 `status` 输出最后一行固定打印"下一步：`nojctl start`"之类。`down/up` 命名也可。
3. 无论选哪个，`uninstall` 不应是"停站"的唯一入口（见 B4）。

#### B4（Blocker）目录守卫与卸载产物互锁：卸载以后装不回来，唯一出路是删数据

**spec 出处**：§9.3"`deploy` 只接受空目录或不存在的目录（不存在则创建）。空 = 没有任何条目"（L554）；同一节末尾"`uninstall`（默认保留 `.env.prod` / `backups/`）提示'目录里仍留有 `.env.prod` 与 `backups/`；要重新 `deploy` 请先移走它们，或使用 `--purge`'"（L559-560）；§9.5"`--purge`：额外删数据卷 + `.env.prod` + 备份"（L576）

**对学校教练的具体影响**：这三条放在一起，构成一个闭环死路：

```
uninstall（默认）→ 目录里剩 .env.prod + backups/ → deploy 拒绝（非空目录）
                 → 唯一被提示的出路 --purge → 删掉数据卷与备份 → 数据没了
```

"要重新 `deploy` 请先移走它们"对教练等于没有建议：他不知道 `mv` 什么、移到哪、会不会影响以后恢复；而 `--purge` 会连**备份**一起删（§9.5 L576），也就是把最后的退路也删掉。更糟的是这条死路会被真实触发：临时卸载试一下（放假、迁移前）、或首装失败后按提示卸载重来。

**建议改法**：

1. §9.3 第一条改为：`deploy` 接受 **空目录**、**不存在的目录**，或**仅含本工具产物（`.env.prod` / `backups/` / `.nojctl/` 的残留）**的目录；遇到外来条目（例如别人手写的 `docker-compose.yml`、源码、其它数据）才拒绝。
2. `deploy` 遇到"已有 `.env.prod`"时不要静默复用、也不要报错：摘要里明确列出"复用已有 `.env.prod`（键 69 个，最后修改 <时间>）"，并给 `--reconfigure` 重新走向导。
3. `uninstall` 默认改为**把 `.env.prod` 移入 `backups/retired-<时间>/`**（或写 `.nojctl/state.json` 的 `uninstalled` 标记 + 保留 `state.json` 骨架），使"卸载后重装"成为一条经过测试的路径（§10.5 e2e 加一条"卸载后重新 deploy 成功、数据卷仍在"）。
4. `--purge` 的提示中必须显式区分："`--purge` 会删除**数据与备份**；如果你只想重新安装，请直接运行 `nojctl deploy`"。

#### B5（Blocker）既有安装零迁移路径，且 v1 备份也读不了——现网部署者被抛下

**spec 出处**：§1.1"**不接管任何既有安装**（v1 装的、手工搭的一律拒绝）……`v1 → nojctl` 迁移工具不在本次"（L28）；"**不兼容 v1 产物**：不读 `noj-cli` 的 `snapshot-*.nojbackup`，不嗅探其 `.bootstrap-*.tmp` / `.env.prod.staged`"（L29-30）；§9.3 结论②"从旧实例迁移由用户自行决定"（L562-564）；§13.4 迁移工具列为 follow-up（L659）

**仓库证据**：现网文档教的全部是 v1 命令——`install`（`production-deploy.md:55`）、`update`（`:169-179`）、`start/stop/restart`（`:143-146`）、`backup drill`/`schedule`（`:238-268`）、`judge *`（`judge-workers.md:18-66`）、`config check`（`production-deploy.md:149`），以及 `.nojbackup` 的 payload 说明（`production-deploy.md:75-76`）。

**对学校教练的具体影响**：本设计把用户分成两类——"新装的人"和"已经在跑的人"。第二类恰好是**今天唯一真实存在的用户**（他们照着 `noj-docs` 装好了站，正在上课用）。nojctl 发布后：

- 不能就地升级（不接管目录）；
- 不能把老站的备份恢复到新站（不读 `.nojbackup`），于是连唯一现实的迁移路径"v1 备份 → 新目录 deploy → 恢复数据"也被设计上封死；
- 命令面也断了（`start/stop/restart/update/judge/problem/drill/schedule` 全没有，见 M12），教练读完新版文档会发现"我原来会用的命令全部消失了"。

结果：这批用户要么永远停在冻结的 v1（并逐渐与镜像/迁移脱节），要么请人重装并手工搬数据。这个代价在 spec 里**没有一处披露**（§1.1 只用"不接管"四个字带过，没有说明代价与建议动作）。

**建议改法**（三选一，必须在 spec 定稿前定稿，不能留到 follow-up）：

1. **`adopt`（最省用户力气）**：`nojctl deploy --adopt <dir>`，读既有 `.env.prod` + 检测运行中的 compose 栈 → 渲染第一代 `current` 世代并接管；前提是"漂移守卫"（§9.4）能识别外来 live 文件并覆盖。这条与 §4.2 不变量 10（"受管部署永远至少有一个世代"）冲突，需要明确写"adopt 时以现有运行态作为 `current` 的初始世代"。
2. **`import`（最省实现力气）**：`nojctl backup import <v1.nojbackup>`，读 v1 单文件（`postgres.dump` + `redis.rdb` + `minio/` + 加密的 `.env.prod`，见 `production-deploy.md:75-76`）→ 落到 `backups/` 目录，之后走 `restore`。这条不改目录守卫语义，且顺带修掉 M8（v1 备份里有 Redis）。
3. **受支持的迁移手册（最低成本）**：新增 `noj-docs/docs/operators/v1-to-nojctl-migration.md`，内容是可直接复制的命令序列（v1 备份 → 校验 → 新目录 `deploy` → `restore` → 换 DNS/端口 → 老目录下线），并**在 CI 里演练一次**（用 v1 产出的快照 fixture）。同时在 §12 批次里占一格，Release Notes 模板必须写"本版本不接管既有安装，迁移步骤见 <链接>"。

> 无论选哪条，都不应在没有迁移路径的情况下把这个 CLI 作为**替换**发布（如果发布定位是"新装专用、老站保持不动"，那也要在 README 第一屏写清楚，并说明老站的安全更新策略）。

#### B6（Blocker）同机第二个实例会接管第一个实例的容器与数据卷

**spec 出处**：§7.1 Artifacts 只有 `docker-compose.prod.yml` / `deploy/*` / `env.delivery.json` / `artifact_hash`（L397-399），**没有 compose 项目名**；§5.5 屏幕 4 只检查"端口占用"（L238）；§9.1 明确 `--dir` 支持多安装（L535）；v1 文档也教"管理多个安装时显式指定 `--dir`"（`noj-cli/README.md:84`）

**仓库证据**：`docker-compose.prod.yml:10` → `name: noj-prod`（固定项目名）；`docker-compose.prod.yml` 的命名卷 `pgdata` / `redisdata` / `miniodata` / `noj-packages` / `noj-storage` / `judge-cache` 都**没有** `name:`/`external:`，因此卷名由项目名派生（`noj-prod_pgdata` 等）；`noj-docs/docs/operators/judge-workers.md:305-307` 也依赖这一点（容器名 `noj-prod-redis-1`）。

**对学校教练的具体影响**：`--dir` 的存在意味着"在一台机器上放两个安装"是被支持的用法（测试站 + 正式站、一台服务器服务两个学校、先试再切）。但只要两个目录渲染出的 compose 项目名相同：

- 第二个 `deploy` 会以相同项目名 `up -d`，**接管第一套容器**（按第二套配置重建）并继续挂载**同一批命名卷**——第一个站的数据库/对象存储/判题缓存被第二个站接管；
- 端口检查（§5.5 屏幕 4）只会拦住"端口相同"的情况；教练只要给第二个站换个端口（例如 8081），检查就通过了，事故静默发生；
- 没有任何提示告诉他"这台机器上已经有一个 noj-prod 项目"。

（**假设 A3**：接管行为依据 docker compose 的项目名语义推断；仓库事实是项目名固定 + 卷名项目派生，未做实测。）

**建议改法**：

1. §7.1 的 Artifacts 增加"项目名 = `noj-<install_dir 的稳定短哈希>`"（或 `--project-name` 覆盖），并在 §7.5 黄金文件里断言两个不同目录渲染出的项目名不同。
2. §5.5 屏幕 0/4 增加检查：`docker compose ls` 中存在同名项目 → 退出 3，并明确输出"这台机器上已有 NOJ 安装（目录 …，正在运行 …）；同一台机器上部署第二个实例需要不同的项目名与端口，请使用 `--project-name`"。
3. 顺带在 §6.6 VERIFY 增加"运行中的容器属于本项目名"的断言（防止第二实例把第一个项目当成自己的）。

#### B7（Blocker）前置探测失败的出口是不可执行的：Docker 没装 / 没权限 / compose 太老

**spec 出处**：§5.5 屏幕 0"静默：docker/compose 版本、架构、磁盘、目录守卫、能否连 GHCR；失败退出 3"（L234）；§11 验收口径"`deploy` 在空目录上从零到可用（含 rootless 引导），全程无需用户理解 compose / env / Docker"（L625）

**仓库证据**：v1 明确不安装 Docker daemon，并且这是有意的边界（`production-deploy.md:93-95`）；rootless 的官方步骤本身需要 `sudo apt-get install uidmap docker-ce-rootless-extras`、`dockerd-rootless-setuptool.sh install`、`loginctl` linger（`judge-workers.md:113-168`）。

**对学校教练的具体影响**：目标画像里"拿得到一台 Linux 服务器"通常意味着**一台刚开的 Ubuntu/Debian VPS**，上面没有 Docker。"怎么装 Docker"是整个旅程的第一道墙，而 spec 对这道墙的规定只有四个字"失败退出 3"——教练会看到一条英文报错（`docker: command not found` 或 `permission denied while trying to connect to the Docker daemon socket`），然后没有任何下一步。第二道墙紧接着出现：Docker 装好后当前用户不在 `docker` 组，**必须重新登录 SSH 才生效**，这一步即使是有经验的运维也常踩，教练几乎必然踩。第三道墙在屏幕 3（rootless）——而 spec 自己承认环境事实是"`sudo` 需密码"（§3.8 L98-99）。

**建议改法**：

1. 屏幕 0 的失败输出必须分三类，且每类都给**可复制**的处理块：
   - 未安装：按发行版（读 `/etc/os-release`）给出官方源安装的 4–6 行命令，或 `curl -fsSL https://get.docker.com | sh`（如团队不接受该脚本，就给 apt/dnf 官方步骤）。
   - 已安装但无权限：明确输出 `sudo usermod -aG docker $USER` + `newgrp docker` + **"或退出 SSH 重新登录"**，并说明"这不影响已开着的终端"。
   - compose < 2：给出安装 `docker-compose-plugin` 的命令。
2. 顺带把"`nojctl doctor` 可以在没有安装目录时运行"变成一个明确的入口（只做主机体检），这样教练在跑 `deploy` 之前可以先体检一遍；文档首页的"第一步"改成 `nojctl doctor`。
3. 屏幕 3 的 rootless 引导脚本必须**自带 sudo 提示语**（"下面这段需要在另一个终端以 root 执行；如果提示输入密码，输入你的登录密码"），并在探测失败时给出两个明确选项：重试 / 跳过（跳过时按 M13 的文案说明"跳过 = 本站不能判题"）。

### 2.2 Major

#### M1（Major）口令门禁：39 字符英文全大写句子 + 断言"HAVE BACKED UP"，工具既不创建也不校验

**spec 出处**：§5.3 门禁表与规则（L195-206，`apply` 口令 `I UNDERSTAND THE RISK AND HAVE BACKED UP`）；§5.6 摘要示例把它印在最后一行（L266-274）；§1.2 判断 2"升级链路不对数据负责：`apply` 不备份、不还原、不碰数据"（L45-46）；§8.4"`apply` 永不调用 backup/restore"（L524）

**对学校教练的具体影响**：两道摩擦同时存在：

1. **语言与长度**：中文母语、非技术用户，在一个紧张的升级动作中被要求逐字敲入 39 个英文字符（`I UNDERSTAND THE RISK AND HAVE BACKED UP`），且只有 2 次机会（L203）——打错一次就更容易慌。规格里其他地方（L266-274 摘要、L288 生成文件头、L557 目录提示）都是中文，这个英文句子是全局唯一的例外（见 m4）。
2. **形式主义**：这句话断言"我已经备份了"，但工具**无法验证**，也**拒绝**帮忙（§1.2 L45、§8.4 L524）。于是它实际训练的是一种行为：**照抄屏幕上印的句子**（L273 直接把句子印出来让人抄）。它不产生知情，只产生"我抄过一行英文"的肌肉记忆。真正能保护教练的是"备份新鲜度"这个可检查的事实，而不是一句声明。

**建议改法**（可执行）：

1. **把门禁改成状态驱动**：`apply` 在门禁前检查最近一次 `backup verify` 通过的备份时间。若 `< 7 天`：门禁降级为一句中文确认（`输入 y 继续`）+ 显示"最近备份：2 天前（已验证）"。若 `> 7 天` 或**没有备份**：不再要求输入英文句子，而是给三个选项：`[b] 现在创建备份并继续`（内联调用 backup create，成功后自动继续）、`[y] 我知道风险，不备份直接继续`、`[n] 取消`。
2. 保留一句"硬门禁"只用于真正不可逆的动作：`backup restore`、`uninstall --purge`。且口令改为**本地语言短确认**（如 `输入 我确认删除全部数据`）或"输入备份 id 的后 6 位"（后者的好处：证明他知道自己要恢复到哪个点）。
3. `--json`/非 TTY 场景保留 `--acknowledge-*`，但在人类 help 里默认不展示（见 m7）。
4. 门禁文案里禁止出现"HAVE BACKED UP"这类**工具无法验证的声明**；换成工具能保证的事实，例如"将回退到 `<version>`（应用层）；数据库不会被回滚；最近备份：<时间>"。

#### M2（Major）"自动回退"的期望管理不诚实，且退出码判据自相矛盾

**spec 出处**：§6.3"回退成功 → 退出 6，输出'已自动回到 `X`，站点正常；原因：…'"（L335-337）；§6.7 归因表"migrate 退出 ≠ 0 → 切回上一世代，退出 **7**（库可能停在中间点）"与"migrate 退出 0、应用层未起 → 切回上一世代，退出 **6**"（L377-381）；§5.2 退出码定义"6 = 失败但系统处于干净的已知状态"（L192）、"7 = 需要人工介入"（L193）；§1.2 判断 2（L45-46）

**仓库证据（为什么这很要紧）**：迁移可以是不可逆的删除——`production-deploy.md:190-217` 记录了一个会执行 `DELETE FROM llm_providers WHERE created_by <> '0'` 的迁移，并要求升级前用 SQL 核查题目引用。也就是说"库可能停在中间点"不只是"多了几列"。

**对学校教练的具体影响**：文件层面确实回到上一世代（这是设计的价值，值得保留），但教练读到的是"**已自动回到 0.10.1-beta.2，站点正常**"——他会理解为"什么都没变，可以放学了"。而真实状态可能是：数据库已经执行过目标版本的迁移（甚至删了数据），应用层却退回了旧版本。下次升级时他会以为一切正常。这份 spec 在 §1.2 里对自己的边界非常诚实（"apply 不碰数据"），但**推到用户面前的那句话不诚实**。

此外 §6.3 与 §6.7 对同一场景给出不同判据：§6.3 说"回退成功 → 6"，§6.7 说"migrate 非零 → 回退 + 7"。实现者只能选一个，用户看到的是不一致的语义。

**建议改法**：

1. 回退文案改为三段式，且**不出现"站点正常"这种笼统结论**：
   ```
   ✅ 应用层已回到 0.10.1-beta.2（容器健康、HTTP 正常）
   ⚠ 数据库没有被回滚：目标版本的迁移可能已经执行（本工具不查库，无法确认）
   ⚠ 如果这次升级包含删除类迁移，数据可能已经变化
   下一步：nojctl backup list（查看升级前备份）· nojctl doctor
   ```
2. 统一退出码判据（建议以 §6.7 为准并写进 §5.2 的注解）：**只要 migrate 已成功执行（或无法确认未执行），回退后不得报 6**，应报 7 并在 `state.last_error` 里记 `migration_ahead`，因为 `current` 世代已经不能代表数据库状态。
3. §5.2 补一句"退出码 6 的前提是**部署描述与数据均未越界**"。

#### M3（Major）`apply` 摘要把"95 条迁移"当风险信息；文档化的升级前必检项在 nojctl 路径里无处执行

**spec 出处**：§5.6 摘要示例"迁移：目标版本声明 95 条（本工具不查库，见 §6.7）"（L269）；§6.7"摘要里的迁移信息来自 manifest……**不含'新增 N 条'这个精确增量**……此为 A1 的已知代价"（L383-384）；§13.3 把"镜像提供 `noj db status --json`"列为 follow-up（L658）

**仓库证据**：`production-deploy.md:190-217`（BYOK 悬空 Provider 的升级前 SQL 检查）——现行文档要求操作者在升级前**跑 SQL**；而 nojctl 的设计原则是"部署链路零数据库访问"（§6.7 L374-375），且 §1.1 没有提供任何数据库访问入口。结果是：**nojctl 用户无法执行当前文档要求的升级前检查**。

**对学校教练的具体影响**：门禁前一屏给出的是"迁移 95 条"——对教练而言这是一个既无法理解也无法行动的数字（95 条比 3 条可怕，但与"我要不要现在升级"无关）。他真正需要知道的是三件事：这次升级会不会动我的数据、会不会有几分钟不可用、失败了会怎样。现在的摘要只回答了第三件（而且答案不完整，见 M2）。

**建议改法**：

1. **提前 §13.3 到 v1**：目标镜像提供 `noj db status --json`（读数：已应用迁移数、末条 tag、`__drizzle_migrations` 计数），nojctl 通过 `compose run --rm core` 调用它，于是摘要可以给出**真实增量**："本次将执行 2 条迁移（0095 新增字段 / 0096 删除 llm_providers.created_by）"。manifest 侧只需声明"目标版本的迁移区间"，不需要精确计数。
2. **提供升级前检查钩子**：渲染产物里保留一个 `precheck` 一次性服务（或 `nojctl apply` 在 COMMIT 前 `compose run --rm core /app/bin/noj db precheck`），由镜像侧实现"这类迁移有前置数据条件"的检查；不通过则零写入、退出 3，并把镜像的检查输出原样打给用户。这既保住"nojctl 不写 SQL"的原则，又把"谁知道 schema/数据"留在镜像里（与 §13.3 同一个思路）。
3. **摘要措辞改人话**：把"迁移：95 条"换成"数据库变更：需要执行 2 条（含 1 条会删除数据，详见 <链接>）"，没有增量数据时宁可不显示。

#### M4（Major）日常配置变更没有引导路径：换域名/换端口/HTTP↔HTTPS/开关 judge/补邮件全都要手改 69 键的 `.env.prod`

**spec 出处**：§1.1"**不做 `config` 子命令**：`.env.prod` 由用户手写"（L31-32）；§1.2 判断 5"配置归用户"（L52-53）；§5.7"`.env.prod` 是唯一配置真相源（0600，用户手写、向导首装生成）。`nojctl` 只在向导补键时写入，否则永不覆盖"（L278-279）

**对学校教练的具体影响**：这套设计在**第一次**配置上做到了"结构上不可能填了不生效"（§1.2 判断 5 的措辞），但第二次开始就回到了 v1 的水平——教练得用 `nano/vim` 打开一个 250 行的文件、找到键、改对格式、保存、再 `apply`。真实会发生的变更至少五种：**换域名**（免费域名 → 正式域名 / 学校域名）、**换端口**（80/443 被占用）、**从 HTTP 切到 HTTPS**（见 B1）、**补邮件配置**（见 B2）、**开关 judge**。这五种恰好都是向导里已经"知道怎么做"的键——知识已经在工具里，只是没有暴露。

**建议改法**：

1. 提供一个**白名单** `nojctl config`：
   - `nojctl config`（无参）= 交互式重跑向导的 4 问，显示每个键的当前值（掩码），确认后写 `.env.prod` 并提示 `apply`；
   - `nojctl config set APP_URL=https://oj.school.edu` / `config set NGINX_PORT=80`（只接受白名单键 + 复用向导的校验与行号定位，见 §5.7 的错误格式）；
   - `nojctl config show [--reveal]`（脱敏展示）。
   白名单范围：对外地址相关（`APP_URL`/`CORS_ALLOWED_ORIGINS`/`DOMAIN`/`NGINX_PORT`/`NOJ_ALLOW_INSECURE_HTTP`）、邮件 4 键、`JUDGE_ENABLED`、`NOJ_VERSION`。其余键保持"手改"路径不变，并在 `.env.prod.example` 里注明"这一组建议用 `nojctl config` 修改"。
2. 文档侧加一页"常见变更速查"：换域名 / 换端口 / 开 HTTPS / 配邮件 / 关判题——每项都是 1–2 条命令 + 一句注意（例如换域名后要重新登录、CORS 自动跟随）。
3. 若团队坚持 v1 不做 `config`，则必须在 §1.1 的非目标里**同时写明后果**："v1 的用户在首次部署后修改任何配置都需要手工编辑 `.env.prod`（250 行 / 69 键）"——把这个代价显式化，而不是让它藏在"配置归用户"这句话里。

#### M5（Major）`--dir` 缺省为当前目录 + 不写 PATH + 陌生目录只给一条警告 ⇒ 日常第一步就是困惑

**spec 出处**：§9.1"调用模型：`nojctl [--dir <安装目录>] <命令>`，`--dir` 缺省为当前目录"（L535-536）；§9.3"只读命令（`status`/`doctor`/`logs`/`versions`/`backup list`）可在外来目录运行，但输出置顶 `⚠ 该目录不是 nojctl 管理的，本工具不会改动它`"（L557-558）

**仓库证据**：v1 有目录发现（`--dir` → 当前目录及祖先 → 安装后二进制所在目录，`noj-cli/README.md:82-89`）并注册 PATH（`:28-29`）。新设计**同时删掉了这两个便利**。

**对学校教练的具体影响**：教练 SSH 登录后落在 `~`，运行 `nojctl status`，看到的是一条 ⚠ 声明而不是状态——他会以为"工具坏了"或"站没了"。要拿到状态，他必须记住安装目录（`/opt/neuro-oj`）并每次写 `--dir`。对一年只登录几次的教练，这是"每次都要重新学一遍"的税；对交接给同事（M11）更是障碍。

**建议改法**（无需恢复 PATH 写入）：

1. `--dir` 解析顺序改为：`--dir` 参数 → 当前目录向上查找 `.nojctl/state.json` → `~/.config/nojctl/last-dir`（由 CLI 在每次成功操作后写入，0600）→ 若 `/opt/neuro-oj` 等常见位置只有一个受管安装，直接使用并在输出顶部注明"使用安装目录 /opt/neuro-oj（`--dir` 可覆盖）"。
2. 找不到任何安装时，不要只给 ⚠：输出"未找到受管安装。你可能是想运行：`nojctl status --dir /opt/neuro-oj`"，并把发现的候选目录列出来（扫描 `~/.config/nojctl/last-dir`、`/opt/*`、`/srv/*` 下的 `.nojctl/state.json`）。
3. `status` 输出的最后一行固定为"下一步"（例如 `nojctl logs core` / `nojctl apply` / `nojctl start`），让从不记命令的用户每次都能被指路。

#### M6（Major）完成页给"URL"，但域名未解析 / 未做外部 TLS 终止时打不开；TLS 完全没被设计提及

2. 完成页固定输出**两种访问方式**：
   ```
   现在就能用：http://198.51.100.7:8080   （内网/临时）
   正式域名：https://oj.school.edu        需要你先做两件事：
     1) 把域名 A 记录指向 198.51.100.7
     2) 在外部（宝塔/Nginx/Caddy）把域名反代到 127.0.0.1:8080 并申请证书
   完成第 2 步后运行：nojctl config set APP_URL=https://oj.school.edu && nojctl apply
   ```
3. §1.1 非目标里补上"**不提供 TLS 证书申请与续期**（由外部边缘终止）"，并把证书续期提醒放进 `doctor`（见遗漏故事 US-8）。

#### M7（Major）备份口令只有"请抄写"这句话；异地保存只有一行文档 ⇒ 磁盘故障时数据与备份同时丢失

**spec 出处**：§8.1"`deploy` 时自动生成随机 passphrase 存 0600，完成页**显著提示抄写**；`doctor` 常驻检查该文件存在与权限。丢失 passphrase = 备份不可恢复"（L490-492）；"单文件的好处：`scp` 一个文件即可异地保存"（L493）；§8.4"异地拷贝 = 一行 `scp`（文档说明，不做命令）"（L525）；§5.5 完成页"备份口令提示（请抄写，丢了就恢复不了）"（L241）

**仓库证据**：`production-deploy.md:253-256`（口令遗失 = 备份不可恢复，建议每季度演练）——现行文档用的是 GPG 口令文件 + `--passphrase-file`（`:238-240`、`:266`），新设计改成"deploy 自动生成随机口令"。

**对学校教练的具体影响**（三重）：

1. **口令没被确认过**：完成页说"请抄写"，但没有"确认已抄写"这一步，也没有记录。教练关掉终端后，他手上到底有没有那串口令，系统和人都不知道。而**丢失口令不会让任何命令失败**——`backup create` 成功、`backup verify` 成功，只有真正 `restore` 时才发现。这是最危险的一类失败：静默的虚假安全感。
2. **口令与备份同机**：口令文件按设计留在安装目录（0600），备份在 `<dir>/backups/`（§9.2 L549）。服务器磁盘损坏或误删，两者一起消失。
3. **"一个文件即可异地保存"是不准确的**：恢复需要**两件**东西——备份文件 + 口令。但这句话直接写进 spec（L493）与 `production-deploy.md:254` 的"口令文件必须异地独立保存"形成了两个不同心智模型。教练会 `scp` 那个 `.nojbackup`，以为万事大吉。

**建议改法**：

1. `deploy` 完成页把口令显示为**便于抄写的分组形式**（如 6 组 5 字符的 base32），并要求一次**回抄确认**（输入其中一组或全部，证明他真的写下来了）；确认结果记入 `state.json`（`passphrase_ack_at`）。未确认时，`doctor` 与 `apply` 门禁必须持续告警（"备份口令从未被确认抄写：若本机故障，备份无法恢复"）。
2. 每次 `backup create` 的输出固定两行：
   ```
   要恢复这个备份，你需要两样东西：① 本文件 …nojbackup ② 口令文件 <路径>
   口令不在备份包里，请把这两样分别存到另一台机器/网盘。
   ```
3. `doctor` 增加两项**可自动判定**的检查：
   - 口令文件与 `<dir>/backups/` **是否在同一文件系统**（比较 `stat -c %d`）→ 同盘则告警"备份与数据在同一块磁盘上，磁盘损坏会同时丢失"；
   - 是否存在**任何**异地保存的证据（例如 `backups/offsite.marker` 或用户确认记录）→ 从未确认则给出一行可复制的 `scp` 命令（含两个文件）。
4. 把"备份可用性"写进 §11 验收：**恢复路径必须在 e2e 中被真实执行一次**（换一个空目录 + 只有备份与口令）。

#### M9（Major）镜像与磁盘只会涨：没有回收动作，`doctor` 只报告占用

**spec 出处**：§6.3 FINALIZE"按 `keep_generations` 清理旧世代"（L333）；§4.2 不变量 10"默认保留上一个可回退世代（`keep_generations`，缺省 1）"（L142-143）；§5.1 `doctor` 检查项含"磁盘"（L158）、`status` 显示"世代/备份磁盘占用"（L156）

**仓库证据**：镜像按版本 tag 引用（`docker-compose.prod.yml:148`：`noj-ui:${NOJ_VERSION}`，共 7 个镜像），因此每次 `apply` 换版本都会在本地留下 7 个新镜像层；`production-deploy.md:21-22` 给出的目标磁盘只有 10 GiB（仅启动/诊断）/ 40 GiB（含同机 Judge）。

**对学校教练的具体影响**：一学年升级 10 次 ≈ 70 个镜像 tag 的增量；备份默认保留 7 份全量（§8.2 L503）。`doctor` 会告诉他"磁盘 84%"，但**不告诉他做什么**——删哪个、用什么命令、删了还能不能回退，他都不知道。（教练最可能的反应是删 `/var/lib/docker` 或整个 `backups/` 目录，这两种都很糟。）

**建议改法**：

1. §6.3 FINALIZE 增加一步：**清理既不是 `current` 也不是 `previous` 的镜像**（`docker image rm` 受管镜像 tag；保留 digest 可回退，与"verify 通过前不清理"的既有规则一致）。
2. `doctor` 的磁盘检查输出必须是可行动的：
   ```
   磁盘：/ 已用 78%（剩余 8.4 GiB）
   可回收：旧版本镜像约 6.1 GiB · 已过期备份 3 份约 4.2 GiB
   建议：nojctl backup prune（默认 dry-run）· docker image prune -a（会删除未使用镜像）
   ```
3. `status` 在占用超过阈值（如 85%）时给单行告警；`backup prune` 增加"按可用空间自动建议保留份数"（m6）。

#### M10（Major）账号找回与第二个管理员没有受支持路径

**spec 出处**：§5.5 屏幕 1 第④问"首个管理员（可选，调容器内 `/app/bin/noj bootstrap first-admin`，跳过则打印可复制命令）"（L235）；§1.1 非目标"不做题包管理（v1 的 `problem`）"等（L34），命令面只有 8 条（§5.1 L149-160）

**仓库证据**：`noj-docs/docs/operators/cli.md:98-102`："仅空站（除系统 root 外无用户）可成功执行……删除管理员或重启也不会重新开放。已有用户的升级站点同样关闭"；`:103-105`："已有站点需要恢复管理员时，由部署者人工核实用户身份后使用维护命令 `bootstrap admin`（通过 `ADMIN_EMAIL` 指定目标）"——而该命令的执行方式是 3 行 `docker compose … --entrypoint /app/bin/noj core …`（`cli.md:20-22`、`:90-92`）。v1 的 `noj-cli` 还提供过包装（`cli.md:31`：`noj-cli bootstrap first-admin …`）。

**对学校教练的具体影响**：两种必然发生的事故他都没有办法：（a）管理员密码忘了/账号被误删；（b）教练换届，需要给新老师开管理员。当前唯一路径是手工拼一条带 `--env-file`、`-f`、`--entrypoint` 的长命令（`cli.md:44-54`）——这正是本设计要消灭的那类操作。而且教练不知道"仅空站可用"这个前提，会反复尝试 `first-admin` 然后失败。

**建议改法**：

1. 增加一个**通用的逃生舱**：`nojctl core -- <args>`（等价于 `compose run --rm --entrypoint /app/bin/noj core <args>`，自动带 `--env-file`/`-f`），并在 help 里给出两个最常用示例：`nojctl core -- bootstrap admin --help`、`nojctl core -- db migrate`。实现成本极低（本设计已有 compose 执行层），收益覆盖账号找回、题目导入、迁移排障。
2. 或增加专用命令：`nojctl admin create|reset`（包装 `bootstrap admin` 与 `change-password` 路径），交互式输入邮箱/用户名，并打印"新管理员首次登录必须改密"。
3. 屏幕 1 第④问的"跳过"必须把后果说清："跳过 = 站点没有管理员，任何人都无法登录管理后台；补建命令：`nojctl admin create`"。

#### M13（Major）v1 的独立判题机与水平扩展被移除，只剩"同机 rootless 开/关"

**spec 出处**：§1.1"**不支持系统 Docker daemon 跑 judge**：judge 只有'同机 rootless 开'与'关'两个状态"（L35）、"不做判题机独立安装"（L34）；§5.5 屏幕 3 失败可"输入 `skip`（置 `JUDGE_ENABLED=false` 继续）"（L237）

**仓库证据**：`judge-workers.md:16-31`（独立节点部署：`noj-cli judge install --dir /srv/noj-judge --redis-url … --socket-path …`）、`:14` 与 `:318-323`（多 Worker 水平扩展，共享同一 Redis 队列）、`:69-73`（架构不匹配时的处理）。

**对学校教练的具体影响**：

- 学校常见的资源分布是"Web 服务器 + 实验室里的一台机器/GPU 机"，把评测放在 Web 机上既吃 CPU 又有隔离顾虑；nojctl v1 把这条路径关掉了（v1 文档教的就是这条路）。
- 更严重的是 `skip` 的后果：**"跳过 rootless" = 这个 OJ 不能判题**。对学校而言，一个不能判代码题的 OJ 基本等于不能用（客观题不需要 judge，因此站点看起来是"正常"的——这会让问题更隐蔽）。而 §11 的验收口径仍会把这种部署当作成功（见 B1 第 4 点）。

**建议改法**：

1. `deploy` 在 `judge=off`/`skip` 时，完成页必须用最强措辞标注"**当前站点无法评测代码题**"（不是一行灰字），并给出两条补装路径：(a) `nojctl config set JUDGE_ENABLED=true && nojctl apply`（同机 rootless，附引导脚本）；(b) 独立判题机（指向新文档）。
2. v1 至少保留**独立判题机的受支持路径**：可以不是 nojctl 的一部分，但必须是"文档 + 经过测试的 compose 片段"，且 `nojctl doctor` 能识别"judge 不在本机"这种拓扑而不误报。若团队决定 v1 不提供，则必须在 §1.1 明确写出"v1 的用户无法把判题放到另一台机器上，也无法水平扩展"，让产品决策可见（而不是藏在"不做判题机独立安装"这半句里）。
3. 把 `skip` 的默认建议反过来：屏幕 3 探测失败时，默认选项应是"重试/看指引"，"跳过"要输入确认词。

#### M14（Major）受限网络下 GHCR 不可达即终止，没有镜像源/代理/离线三条出路

**spec 出处**：§3.8"目标服务器常处于受限网络（Docker Hub 直连超时、`sudo` 需密码），因此'下载官方镜像/包'不能作为唯一路径"（L98-99）；§5.5 屏幕 0"能否连 GHCR；失败退出 3"（L234）；屏幕 6 第②步"拉镜像（逐镜像进度）"（L240）

**仓库证据**：`production-deploy.md:27`："能够访问 GitHub 源码地址和 `ghcr.io/neuro-oj/` 镜像；网络受限时请先配置 Docker 镜像源或代理"——现行文档至少给了方向，而 spec 只是"失败退出 3"。

**对学校教练的具体影响**：教育部/学校网络对容器镜像仓库的限制是常态。教练遇到的是 45 分钟里的**拉取超时**（PREPARE 预算"单镜像 ≤ 20 min、总计 ≤ 45 min"，§6.6 L361），失败后退出 6，站点没起来；他再次运行，再次超时。spec 自己在 §3.8 承认了这个环境事实，却没有为它设计任何动作——这是"知道风险但不处理"。

**建议改法**：

1. 屏幕 0 的连通性检查（同时探 ghcr.io 与 ONE 个备用端点）失败时，输出三条可执行出路：
   ```
   a) 配置镜像加速/代理（给出 /etc/docker/daemon.json 片段，或 systemd drop-in 的 HTTPS_PROXY 写法）
   b) 在能联网的机器上导出镜像，再离线导入（给出 docker save/load 的完整命令序列）
   c) 联系我们获取离线包（给出链接）
   ```
2. 把 `--image-bundle <tar>` 参数（或 `nojctl images load`）列为 v1 候选/Follow-up，优先级高于 §13 里的若干项——它决定的是"能不能装上"，不是"好不好用"。
3. PREPARE 的镜像拉取必须**可断点续传 + 可诊断**：失败时打印每个镜像的成功/失败与耗时，并给出"重跑 `nojctl apply` 会跳过已缓存的镜像"的明确提示（§5.5 L243 已有"不重拉已缓存镜像"，把它放到失败输出里）。

## 6. 成功度量建议

**先说一个前提**：这份设计目前**没有任何可观测性**——没有埋点、没有诊断包、没有上报入口。上面 6 个指标里有 5 个在"无埋点"状态下**不可测**。因此第一件事是把最小采集能力做成 v1 的一部分（建议：默认关闭、显式同意、只上报计数与时序、不上报任何配置值与域名；另配 `doctor --bundle` 让用户自愿附图）。如果团队决定完全不采集，那么下面的目标值应改写为"发布后 4 周内的用户访谈/群内问卷结果"，并在 spec 里写明这个替代方案。

| # | 指标 | 目标值 | 为什么是它 |
| --- | --- | --- | --- |
| 1 | **首装用时**：从"下载二进制"到 `deploy` 退出 0 的墙钟时间（含 rootless 引导；分 P50/P90） | P50 ≤ 45 min，P90 ≤ 120 min | 这是"零基础教练能自己开站"的唯一直接证据；v1 的实际体验是"一下午 + 群里问三轮"。按 §6.6 的时间预算（PREPARE ≤ 45 min），P90 若超过 120 min 说明卡点在人为步骤（Docker 安装、rootless、DNS）而非下载 |
| 2 | **首装一次成功率**：`deploy` 一次（不重跑）到退出 0 的比例 | ≥ 70%（v1 时代视为 < 40%，**假设 A6**：无历史数据） | 一次成功率同时度量"文档/错误信息是否说人话"与"前置检查是否够早"。它与指标 3 组合能区分"第一次就顺"和"有人扶着才行" |
| 3 | **"部署成功但实际不可用"漏判率**：`deploy` 退出 0，但 24 h 内站点无法登录或无法完成一次评测的案例数 | **= 0**（任何一个案例都要立案） | 直接度量 B1 是否修好（VERIFY 只测 HTTP 200 的后果）。这个指标为 0 是"可用性验收口径"修好的**唯一**可信证据 |
| 4 | **失败收敛质量**：`apply` 失败事件中，以"干净回退（退出 6）"收场的比例；`partial`（退出 7）绝对数 | 干净回退 ≥ 95%；退出 7 **= 0**（每出现一次立案复盘） | 原子性是本设计的承重墙（§12 L649-650 自述）。对教练而言，退出 7 = "我完全不知道该干什么"，所以 7 的出现次数是最硬的质量指标 |
| 5 | **门禁摩擦**：门禁一次通过率；因门禁失败（退出 4）而放弃（24 h 内未重试）的比例 | 一次通过 ≥ 85%；放弃 ≤ 2% | 区分"有效知情确认"与"形式主义阻碍"。若一次通过率 < 70%，说明英文长句（M1）确实在伤害用户；若放弃率 > 2%，说明门禁在把人挡在升级之外 |
| 6 | **备份真实可用性**：安装中"存在 ≤ 7 天的新鲜备份 **且** 口令已确认抄写 **且** 至少一份在异地"的比例；从未验证过的备份比例 | 前三项同时满足 ≥ 80%；`backup verify` 失败率 ≤ 0.5% | 备份是数据的唯一保险，而设计把口令与异地全部交给用户（M7）。没有这把尺子，团队会以为"有 `backup create` 就等于有备份" |

**次要参考指标**（不设硬目标，作为诊断用）：`doctor` 首次全绿比例（反映环境健康度）、每 10 次部署产生的外部求助数（目标 ≤ 1）、`versions` 执行到 `apply` 的转化率（反映升级摩擦）、平均升级间隔（反映教练是否敢于升级）。

**采集方式**：指标 1/2/4/5 需要 CLI 埋点（建议在 `deploy`/`apply` 结束时上报一条匿名记录，含：耗时、退出码、失败阶段、是否使用 skip、nojctl 版本、OS/架构；**不含**域名、目录、任何配置值）；指标 3/6 用 `doctor --bundle` 自愿提交 + GitHub issue 模板必填；指标 6 的一部分（新鲜度/同盘/口令确认）可以在本地由 `doctor` 直接算出，无需联网。

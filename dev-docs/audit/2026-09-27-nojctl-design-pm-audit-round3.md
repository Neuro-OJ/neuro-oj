## 3. 本轮修复新引入的矛盾 / 漏洞（重点）

### 3.1 高（必须进 draft-4）

#### R1（高）安装身份与实例级密钥都不随数据一起延续：卸载后重装会让保留的数据卷变成孤儿、站点看起来是空的

**出处**：`install_id` 只存在于 `.nojctl/state.json`（L303）；`uninstall` 默认**移除 `.nojctl/`**（L544）；`deploy` 在只剩保留物的目录上"复用 `.env.prod` 的值"但 `install_id` 是"**部署时生成**"（L531、L303）；项目名 = `noj-<install_id 前 8 位>`（L408）；而 §9.3 结论②与 §9.5 都承诺"卸载后目录可直接重装"（L536、L544）。

**仓库证据**：prod compose 的命名卷全部**没有** `name:`/`external:`（`docker-compose.prod.yml:514-523` 顶层 `volumes:` 段：`pgdata` / `redisdata` / `miniodata` / `noj-packages` / `noj-storage` / `judge-cache`；服务侧挂载见 `:395`、`:420`、`:450`），因此卷名由**项目名派生**（`noj-<id>_pgdata`）。项目名一变，同名卷就不存在 → 新建空卷。

**用户后果（两条，都属于"教练会以为数据没了"）**：

1. **卷被孤立**：教练因为"重装试试/换配置"跑了 `uninstall`（默认保留数据卷）再 `deploy` → 新 `install_id` → 新项目名 → **全新空卷**，站点起来后一片空白；旧数据仍静静躺在磁盘上（占空间、不可见、也没有任何提示）。这与 §9.3 结论②的"可直接重装"在**用户可观察层面直接矛盾**。
2. **密钥被重新生成**：§5.5 屏幕 2（L232）无条件"强随机生成 `JWT_SECRET` / `TFA_ENCRYPTION_KEY` / `POSTGRES_PASSWORD` / `REDIS_PASSWORD` / `MINIO_ROOT_*` / S3 凭据"，**没有"复用既有 `.env.prod` 时沿用原值"的例外**。若实现照字面做：`POSTGRES_PASSWORD` 变了，而 `pgdata` 里的角色口令是 initdb 时写死的（官方镜像在数据目录已存在时跳过初始化、忽略该环境变量）→ `migrate`/`core` 连不上库，`deploy` 直接失败在一个教练完全无法理解的错误上；即便站点能起来，`TFA_ENCRYPTION_KEY` 变了 → **已启用 TFA 的学生登录不上**（TOTP secret 是 AES-256-GCM 加密存储的，`noj-core/src/main.ts:143-153`），`NOJ_LLM_STORE_KEY` 变了 → **LLM 题全部静默失败**（`llm_providers.encrypted_api_key` 的信封加密主密钥，`noj-llm-gateway/src/config.ts:17,36`）。

（**假设 A1**：draft-3 未给 `.env.prod` 安排"安装身份"键；§5.7 的三类键（L275-277）里没有 `NOJCTL_INSTALL_ID` 之类，因此按现文本，身份确实只活在 `.nojctl/`。**假设 A2**：`.env.prod` 复用路径下密钥是否重新生成，spec 未写，我按字面理解为"会重新生成"，需要 spec 明确。）

**修法（三行文本，建议照抄）**：

1. 在 `.env.prod` 增加一个 `# [仅 nojctl 使用]` 分区，写两个键：`NOJCTL_INSTALL_ID`、`NOJCTL_PROJECT_NAME`（沿用 §5.7 已有分类机制）。这样 `uninstall`（保留 `.env.prod`）→ `deploy` 时**照单沿用**身份；搬目录也天然带着身份。
2. §5.5 屏幕 2 增加一句例外：**"若复用既有 `.env.prod`：其中已有的一切键（含全部密钥）一律沿用原值，只补缺失键；只有全新首装才生成新密钥。"** 并在 §7.4 第 2 层加一条校验：数据卷已存在而 `.env.prod` 缺失/密钥与卷不匹配风险 → **fail-closed，退出 3**，输出"检测到已有数据卷 `noj-xxxx_pgdata`，但没有对应的配置文件；直接继续会导致数据不可访问。可选：`--adopt-install-id <id>` / `--purge`"。
3. 验收：§10.5 e2e 增"`uninstall` → `deploy`（复用）→ 站点起来且**原有数据仍在**（抽查一行）"；§11 增"卸载后重装不丢数据（卷与密钥均沿用）"。

#### R2（高）"第 2 步：开启判题"没有命令落点——而它现在是**默认路径**的必经下一步

**出处**：所有者决定 judge 默认跳过（L43）；`deploy` 屏幕 3 是"可选二级项"（L233）；完成页第④段写"judge 未装 → **第 2 步指引**"（L237）；§11 验收也写"判题是可选的第二步"（L590）。但命令面（L161-172）**没有 `judge` 命令**；`deploy` 在已有 state 的目录上是"续跑/复用"分支（L530），语义未定义；`apply` 只改部署描述（L164），不做宿主机 rootless 安装；§13.9 明确"独立判题机不支持"。

**用户后果**：默认路径（绝大多数教练）走完后，完成页让他"开启判题（约 15 分钟）"，而他**没有任何命令可以敲**：重跑 `deploy` 会进入不明的"续跑/复用"分支（会重跑向导吗？会覆盖配置吗？——spec 没说），手改 `JUDGE_ENABLED=true` + `apply` 又完全不会配置 rootless Docker（那才是这一步 90% 的工作量与全部风险）。结果是：**本设计最想避免的"照文档拼命令/放弃"重新出现，而且出现在默认路径上。**

**修法（二选一，建议 A）**：

- **A（新增命令，推荐）**：`nojctl judge enable`（完整复用屏幕 3 的子流程：打印 rootless 脚本 → 等回车 → 7 项探测 → 预拉评测镜像 → 写 `JUDGE_ENABLED=true` + socket/gid 键 → 走一次 `apply` 事务 + VERIFY #4），并把完成页第 2 步的文案写成这一条命令。`nojctl judge disable` 顺带对称。
- **B（不加命令）**：明确 `deploy` 在"已有 state 且指定了 `--judge=on`"时进入"**二级项补做流程**"（不重跑三问、只做屏幕 3 + apply），并在 §9.3 第 2 行写清"`deploy` 的续跑 ≠ 重跑向导"。
- 无论选哪个，§5.1 命令表或 §5.5 屏幕 3 必须给出**教练可复制的那一行命令**；§11 验收加一条"默认跳过判题的部署，完成页给出的第二步命令能真的开起判题（e2e 覆盖）"。

**出处**：§12 批次 6.5 的九步大纲（L617）里，第 ⑤ 步"导入：`pg_restore`、写回 `dump.rdb`、`mc mirror` 反向同步、卷解包"只搬**数据容器**，没有任何一步搬**密钥**；而"新机 `deploy`（空目录）"（第 ④ 步）会生成一整套**新的**随机密钥。

#### R4（高）`deploy` 的 FINALIZE 无值可写：首装进入时运行态是 `uninitialized`，而 FINALIZE 只定义了 `running` / `stopped`

**出处**：§6.3 FINALIZE（L330）"按 `entry_runtime_state` 落 `state`（`running` 或 `stopped`；后者需先 `stop`）"；而 `deploy`（首装）进入事务时 `state` = `uninitialized`（§6.1 L298 的四态、§6.3 L327 也承认首装走同一张三阶段表）。

**用户后果（连锁）**：若实现者照字面执行，首装成功后 `state.json` 可能写成 `uninitialized`（或实现者自行发明第五种处理）。而 §5.1（L165）刚刚定义了"`start`/`stop` 遇 `uninitialized` → **退出 3**（提示先 `deploy`）"——于是**刚刚装好、站点正在跑的机器上，`nojctl stop` 会告诉他"还没有安装，请先运行 nojctl deploy"**。教练既停不了站，也不敢再跑一次 `deploy`。

**修法**：§6.3 加一行——"`deploy`（首装）的事务在 FINALIZE 一律落 `running`（首装必然启动；`uninitialized` 只存在于任何事务之前）"，并在 §10.4 加断言"首装成功后 `state == running` 且 `stop` 可用"。

### 3.2 中

#### R5（中）HTTPS 路径的登录冒烟可能被 `Secure` Cookie 语义误杀——B1② 的修复反而制造新失败

**出处**：§6.6 #2/#3（L367-368）探测走**明文回环** `http://127.0.0.1:<NGINX_PORT>` + `Host: <DOMAIN>`；而 HTTPS 路径下 `NOJ_ALLOW_INSECURE_HTTP=false`（L232），UI 代理据此给 Cookie 加 `Secure`（`noj-ui/server/api/[...slug].ts:237`：`secure: isProductionEnv() && !allowsInsecureHttp()`）。

**风险**：登录冒烟要求"拿 Cookie 再带 Cookie 调 `/me` 期望 200"。如果 nojctl 的 HTTP 客户端遵守 `Secure` 属性（reqwest + cookie store 等常见组合会遵守），那么**在明文回环上它不会回传该 Cookie** → `/me` 401 → VERIFY 失败 → 自动回退。也就是说：**一次完全正确的 HTTPS 部署会因为"探测手段"而失败**，正好是 B1② 想消除的那类"正确部署自我失败"。（**假设 A3**：客户端行为取决于实现，spec 未规定；但"不要在明文回环上依赖 Secure Cookie 的往返"是可以在设计层面写死的。）

**修法**：§6.6 #3 的判据改为**两段可分离**：①（必须通过）`POST /api/v1/auth/login` 返回 200 **且响应头 `Set-Cookie` 含 `noj:token`**（同时断言它在 HTTPS 模式下带 `Secure`、在 HTTP 模式下不带）；②（可选、advisory）`/me` 往返用"不强制 Secure 的 cookie 容器"完成，或干脆改调 `/healthz` 之外的公开只读接口做"会话可用性"佐证。并在 §10.4 加一条断言：HTTPS 配置下 VERIFY 不因 `Secure` 属性失败。

#### R6（中）`--yes` + `--json` 时"生成的密码"无处安放，与 §5.4 的 stdout 纯净性冲突

**出处**：§5.5 非交互（L243）"`--yes` 时管理员密码同样由工具生成并**打印一次**"；§5.4（L216）"**stdout 只含一个 JSON 文档**，人话走 stderr"；不变量 12（L153）"秘密……**只允许一次性打印给用户**"。

**用户后果**：`--json` 是给 CI/脚本用的（L200 明确"`--json` 与 CI 都依赖这条"），而在这条路径上密码必须"打印"——写进 stdout 就污染 JSON 契约、还会被日志/管道带走（正好违反不变量 12 的意图）；写进 stderr 又会和"人话"混在一起，脚本捕获不到、终端可能滚走。

**修法**：新增 `--admin-password-out <path>`（0600，脚本自己保管），规则写进 §5.5 与 §5.4：**`--json` 模式下密码一律不打印，必须落到该文件；未提供该参数时拒绝自动建号（退出 3）并提示 `nojctl core -- bootstrap first-admin --password-file`**。人类交互模式保持"只显示这一次"。

#### R7（中）N4 的四值表依赖一个**不存在的日志契约**：core 现在不打印"应用了几条迁移"

**出处**：§6.3 L341-348 的四值表要求区分"退出 0 + **日志显示已应用**"与"退出 0 + **日志无待应用**"；§5.2 的 6 号定义也依赖"日志显示无待应用迁移"（L197）。

**仓库证据**：`noj-core/src/shared/db/migrate.ts` 只有三行日志——`logger.info("开始数据库迁移", {migrations_folder, migrations_schema})`（L145）、`logger.info("数据库迁移完成")`（L154）、`logger.error("数据库迁移失败")`（L156）。**没有计数、没有逐条迁移输出、没有"无待应用"的区分标记。**

**用户后果（设计层面）**：照现文本实现，两个"退出 0"分支无法区分 →

- 要么保守取 7（"无法确认"）→ §5.2 的 6 号在"容器起来过"的场景下**永不出现**，§6.7 最后一行（L390"退出 0 且无待应用 → 6"）成为空文，而**最常见的良性失败（版本升级后应用没起来、schema 没变）会被报成"需要人工介入"**，把教练推向求助；
- 要么实现者自己猜（例如拿 `last_tag` 与 manifest 对比）→ 契约测试（L575"无法确认迁移状态 → 7"）与实现打架。

**修法（最省）**：把"机器可读的迁移结果行"作为**批次 2.5 的第 4 个 core 能力**写进 §5/§12——例如 `noj db migrate` 结束时打印 `NOJ_MIGRATE_APPLIED=<n>`（stdout 一行，向后兼容，无副作用），nojctl 只读这一行。同时 §3 的现状证据补一条（当前日志不足以判定），否则读者会以为四值表已可实现。若团队不愿动 core，则把四值表**降级为退出码语义**（未运行 → 无法判断 → 7；退出 0 → 无法判断 → 7；退出 ≠ 0 → 7），并承认"6 只用于 PREPARE 阶段失败"，同时删掉 §6.7 的"退出 0 且无待应用 → 6"行。

#### R8（中）复制目录（`cp -r`）会连 `install_id` 一起复制，而冲突检查只比"其它 `install_id`"→ 两个目录管同一套容器与卷

**出处**：§7.1（L408）"PREPARE 检查同名项目是否已被**其它 `install_id`** 占用，冲突即拒绝"；`install_id` 在 `.nojctl/state.json`（L303）里，随目录一起被复制。

**用户后果**：教练想"留个副本再试"（很常见）→ `cp -r /opt/neuro-oj /opt/neuro-oj-test` → 副本里 `install_id` 与线上相同 → 冲突检查**通过**（"不是其它 install_id"）→ 副本上的 `deploy`/`apply` 会对**同一批容器与命名卷**执行操作（compose 项目名相同），并且副本用的是自己的 `./deploy/nginx/...` 挂载文件（`docker-compose.prod.yml:319,499` 用相对路径，随目录解析）→ 线上站点的配置被副本文件接管的可能性存在。B6 当初修掉的"静默互相接管"以另一种形式回来了。

**修法**：冲突检查改为**按项目名 + 实际占用目录**双判据。经实测（**已验证**，非假设）：compose 会在容器上打 `com.docker.compose.project`、`com.docker.compose.project.working_dir`、`com.docker.compose.project.config_files` 标签（本机 dev 栈实测：`working_dir=/home/xyber-nova/Github/neuro-oj`）。因此 PREPARE 只需：若存在同名项目的容器、且其 `working_dir` ≠ 当前 `--dir` → **拒绝（退出 3）**，输出"该项目由另一个目录 `<path>` 管理（可能是目录副本）；请改用 `--dir` 指向原目录，或删除副本的 `.nojctl/` 后重新部署（会创建独立项目）"。同时 §10.4 加"复制目录被拒"的用例。

#### R9（中）`NOJCTL_PROJECT_NAME` 与 `state.project_name` 谁权威未定义 → 可能渲染出与在跑栈不同的项目名

**出处**：§7.1（L408）项目名"可用 `NOJCTL_PROJECT_NAME` 覆盖"；§6.1（L305）`state.project_name` 也记着项目名；§7.1 的 render 输入是 probe 里的 `install_id`（L403），而覆盖来自**环境变量**。

**用户后果**：用户在首装时用环境变量指定了 `NOJCTL_PROJECT_NAME=noj-school`（或导出在 `~/.bashrc` 里），后来换了终端/工作目录，环境变量没了 → 渲染按 `install_id` 得出 `noj-6b0f2c1e` → 与在跑的栈不一致：轻则 VERIFY "期望容器集合齐全"失败并被判为失败/回退，重则**起出第二套容器与空卷**（数据"看起来丢了"）。

**修法**：一句话写死优先级——**"首次 deploy 时确定项目名并写入 `state.project_name`；此后一切渲染、冲突检查、compose 调用一律以 `state.project_name` 为准；`NOJCTL_PROJECT_NAME` 仅在'目录内尚无 state.json'时生效，若其值与 `state.project_name` 不同则拒绝（退出 3）并提示。"** 并在 §7.5 黄金文件加一条断言。

#### R10（中）`--password-file` 削弱了 `first-admin` 的"本机授权"语义：必须校验权限与属主

**出处**：§0.1 N5（L20）"保持'本机授权'语义，**只去掉 TTY 要求**"；批次 2.5（L612）同一措辞；`noj-core/scripts/noj.ts:231-241` 的现状是"非 TTY 直接抛错 + `Secret.prompt` 两次"。

**风险**：TTY 要求本身就是一条权限边界（必须能登上这台机器并拿到交互终端）。改成"读任意路径的文件"后，若不做校验，等于把"能读到该文件"当成了授权——而这个文件正是 nojctl 自己写的（路径可猜、0600 有效但 root 可读；容器/备份/日志里也可能留下副本）。

**修法**：批次 2.5 的能力描述加两条硬约束——`--password-file` 必须 ① 是**普通文件**（拒绝 `/dev/fd` 之外的符号链接）② 权限 `0600`（或更严）且 **owner == 调用者 uid**，否则报错并给 `chmod 600 <path>` 提示；错误信息不得回显密码内容。nojctl 侧写临时文件时用 `0600` + `O_EXCL`（不覆盖既有文件）。

#### R11（中）管理员密码临时文件的生命周期：崩溃后谁删、`doctor` 是否发现残留

**出处**：§5.5 屏幕 6 ⑤（L236）"经 0600 临时文件传入，**用完即删**"；§6.6 #3（L368）"仅驻留内存与 0600 临时文件"。

**缺口**：`SIGKILL`、断电、`Ctrl-C`（提交窗口外）都会让"用完即删"落空，文件留在磁盘上；spec 没有规定**路径**（放哪？`/tmp` 还是 `.nojctl/`）、**命名**、**启动时清理**、`doctor` 检查。

**修法（首选先免落盘）**：批次 2.5 支持 `--password-file /dev/stdin`，nojctl 以 `docker compose run -T` + stdin 管道传入 → **完全不需要临时文件**。若必须落盘，则规定：路径 `<dir>/.nojctl/tmp/`、文件名含随机后缀、`0600`；任何 nojctl 命令启动时清理该目录下超过 10 分钟的残留（并打印一行"已清理上次遗留的临时文件"）；`doctor` 报告残留；§10.4 已有"秘密不外流"用例，再加一条"临时目录清理"用例。

## 7. 是否值得再出一版 draft-4

### 7.1 结论：**值得出一版，但范围必须受控**

理由（三点）：

1. **R1/R2/R4 都是"设计决定"，不是实现细节**：`install_id` 放哪、卸载保留什么、`deploy` 之后状态写什么、"第二步开判题"敲哪条命令——这些一旦留给实现者自由发挥，出的是**互不兼容的两种行为**（例如一半实现"复用密钥"、一半"重新生成"），返工成本远高于现在改 6 行文本。
2. **R5/R6 涉及对外接口**（VERIFY 判据、`--json` 与密码的交互、新增 `--admin-password-out`），属于"契约"，越晚改越贵。
3. **R3/R7 涉及别的模块**（core 的迁移日志、迁移手册内容），必须在实施计划排批次前就写进 spec，否则批次 2.5 会漏项、手册会漏步。

同时：draft-3 的结构、分工、批次划法都不需要动，**draft-4 应是"补丁版"**（预计 ±40 行），不是重写。

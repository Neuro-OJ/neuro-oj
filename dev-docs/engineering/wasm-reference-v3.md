# NOJ WASM v3 参考毫秒

`noj-wasm-v3` 固定 20,000,000 fuel = 1 NOJ 参考毫秒。题目时限以整数乘法转换为
fuel 预算；结果的 `equivalent_time_ms` wire 字段继续沿用，v3
界面展示为“参考时间”。该单位是固定工作量，不保证等于实际 CPU 毫秒。

## 标准边界

v3 保持 v2 的 Wasmtime 49.0.1、修补 WASI SDK
34、编译参数、算子及批量内存成本、确定性时钟和随机流、内存/输出限制与宿主运行保护。程序自身的
IO 解析与格式化继续消耗
fuel，不排除标准库成本。只有标准版本、摘要、换算尺度和单位说明变化。

v1、v2
的清单、摘要和基准快照保持原样，历史结果继续显示等效时间；历史结果不自动重测。Worker
拒绝旧标准任务，Core 为新任务绑定 v3。工具链文件摘要仍对应 v2
修补产物，不重新构建或改写源码。

## 选择尺度的依据及限制

本地 Lemon 与 NOJ 的 25 个选手、50 个提交中，排除已知越界未定义行为后，144
个两端 AC 且原生时间至少 10ms 的 club 测试点，其 v2 等效时间/原生时间中位数为
20.25，P10–P90 为 13.71–31.89。基于这些观测并经用户确认，v3 采用整数尺度
20,000,000 fuel/ms。它不是经过多题型独立验证的通用 CPU
时间预测模型，也不承诺复现官方成绩。

road
的首个失败会使后续点跳过，不能以耗尽预算的截断数据拟合完整耗时。后续拟合仍需要独立逐点运行与更广的算法样本。源码越界、GNU
标准库扩展缺失及编译资源限制等兼容性差异应独立归因。

## 部署和题目时限

先暂停新 WASM 任务入队并排空旧任务，再同时升级 Core 和
Worker，核对只读标准接口及 Worker 内置摘要后恢复入队。未配套升级的旧任务返回 SE
并提示重测，不自动回退。

本地 club 的标准 IO 题 P5 和文件 IO 对照题 P7 均恢复每点 1000ms，与 road P6
的官方时限一致；1000ms 对应 20,000,000,000
fuel。原生后端仍使用原生计量，站点历史成绩保持原样。

## 验证

清单检查分别冻结三个版本，并要求 v3 的工具链与全部运行规则和 v2 一致。Rust
测试覆盖整数预算、溢出、取整与拒绝旧任务；真实 SDK 基准使用独立 v3
快照，分析工具也从标准读取预算和换算尺度。界面测试验证历史单位名称不变。

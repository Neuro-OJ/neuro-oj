# NOJ 架构整治方案：单 Core、明确所有权、可恢复的执行链路

日期：2026-10-20
状态：已批准，按 P0–P8 批次实施。本文件是实施、验收与交接的单一事实源；批次完成后在
[跟踪清单](#7-跟踪清单)勾选并补充验证记录。

## 1. 目标与既定取舍

目标是让维护者更容易判断：一个行为由谁负责、修改应落在哪里、失败后谁来恢复、一次变更需
要验证什么。

已确认的取舍：

- **部署模型**：一个 Core；Judge 可横向扩展。保留 Core、Judge、LLM Gateway 三个运行
  服务，继续使用 Deno/Hono、Nuxt、Rust、PostgreSQL、Redis 与 Compose。
- **允许的内部调整**：重划 Core 内部模块、删除历史适配、协调修改 API 与评测协议；协议
  升级使用维护窗口，先排空再整体切换。
- **测试**：服务、路由与数据库集成测试统一使用隔离的真实 PostgreSQL；纯逻辑单测保持零
  外部依赖。拒绝以 PGlite / 手写 DDL 伪装真实数据库行为。
- **契约**：跨语言契约统一与类型生成后置。本轮继续手写 TS/Rust 类型并用现有契约夹具验证
  必要改动；不引入生成链。
- **保留产品语义**：不可变题目版本、提交绑定版本、有效成绩策略、比赛保密、共享撤销、教学
  历史与域内配额不变。数据库物理表不随目录调整批量改名。

## 2. 审查结论

本轮覆盖 Core 启动与关闭、模块调用、权限与读模型、数据库与测试适配、后台任务、Nuxt 数据
加载、Judge 执行与调度、Gateway 配额与记账、存储生命周期、CLI 升级流程、部署升级和 CI。
下列问题直接进入改造清单：

| 领域 | 当前问题 | 改造结果 | 实现依据 |
|---|---|---|---|
| 模块边界 | 大量门面整体转出内部实现，存在双向业务依赖 | 公共接口有限且显式，跨模块写流程集中编排 | noj-core 域门面与 `index.ts` 导出面 |
| 身份与事务 | 可选身份回退 root；事务要求主要依赖调用约定 | 身份必填，系统身份显式，必须原子的函数只接收 `DbTx` | noj-core 身份与授权入口 |
| 数据库测试 | 生产连接模块同时处理 PGlite、手写 DDL、模板缓存和事务代理 | 生产连接保持简单；测试使用正式迁移和隔离数据库 | `noj-core/src/shared/db/connection.ts:1` |
| 升级流程 | update 先 `up --wait` 再验签；启动配置与验签配置不是同一份解析结果 | 目标发布集先解析、拉取、验签，之后才迁移或启动 | `noj-cli/src/prod/lifecycle.ts:1548` |
| 数据库迁移 | 获取迁移锁失败或超时后继续无锁迁移 | 失败立即终止，不执行后续 DDL | `noj-core/src/shared/db/migrate.ts:72` |
| Gateway 健康检查 | ready 探针实际只执行 Redis ping | 探针覆盖真实数据库访问、Redis 与记账 worker 状态 | `noj-llm-gateway/src/app.ts:52` |
| Gateway 所有权 | 每次 LLM 调用通过 HTTP 回查 Core 的配额政策 | Gateway 持有并执行配额政策，Core 负责治理入口授权 | `noj-llm-gateway/src/quota-policy.ts:9` |
| Judge 编排 | 执行入口传递二十余项零散配置与资源参数，资源与取消生命周期分散 | 固定的 WorkerContext 与单次 RunContext 承担这些职责 | `noj-judge/src/judge/runner.rs:84` |
| 前端读取 | BFF 合并浏览器请求后仍逐题读取完整详情；前端再用通用信封与断言消费 | Core 提供授权后的批量摘要，BFF 按页面组织返回值 | noj-ui BFF 请求扇出 |
| 后台生命周期 | 消费者、定时任务和 worker 使用不同停止方式，关闭时没有完整等待 | 所有后台组件拥有统一的停止与完成句柄 | Core/Gateway 启动装配 |

目前域边界、文件规模、Provider 装配和运行时契约四项门禁通过。上述结论主要来自源码审查；
全量测试、真实故障注入和生产恢复演练属于后续实施验收。

## 3. 目标结构与依赖规则

### 3.1 保留运行边界，重组 Core 内部

~~~text
Nuxt Web / BFF ─┐                   ┌─ Judge Workers ── LLM Gateway ── Providers
IDE / CLI 客户端 ┼─ Core HTTP ─ Core ─┤        │                │
                 │                   │        └─ Redis MQ ──────┘
                 │                   ├─ PostgreSQL
                 │                   └─ 对象存储
~~~

Judge → Core 表示结果最终由 Core 接收和落库，实际传输继续使用 Redis。单个业务事务能够
完成的操作留在一个 PostgreSQL 事务中；跨服务操作明确各自的提交点与重试责任。

Core 分区：

| 分区 | 所有权与归并方式 |
|---|---|
| access | 合并身份与工作空间的账户、角色、成员、邀请、访问上下文；内部保留身份与空间子模块 |
| problems | 题目、草稿、版本、共享绑定、题单、客观题内容；客观题判分执行移出 |
| evaluations | 提交、自测、尝试、有效成绩、重测任务、客观题判分执行、Judge 消息 |
| contests | 比赛生命周期、参赛关系、赛题固定版本、赛制和正式榜单 |
| education | 班级、作业、学情、教学互动和教学通知 |
| communication | 社区、私信和内容审核，保留各自的权限与存储子模块 |
| assets | 对象登记、上传预约、引用保护、容量核算和交付；作为明确的业务模块存在 |
| platform | 实例设置、公告、法律与同意记录等平台能力 |
| read-models | 跨模块展示查询、搜索、统计、榜单和教学聚合 |
| application / http / runtime | 分别承担流程编排、协议适配和外部能力装配；管理端路由归入 HTTP 组合层 |

采用 `modules` 作为代码分区名称，避免与产品中的 Domain 混淆。目录搬迁随职责迁移一起
完成，不安排仅修改路径的大批次。

### 3.2 依赖规则

- HTTP 层处理解析、认证入口、状态码与响应转换；业务服务不接收 Hono Context。
- 单模块操作直接进入对应应用用例；跨模块写入由应用用例开启事务并编排。
- 业务模块不调用其他模块的写服务；需要异步跟进的工作在原事务中登记持久任务。
- 查询层可以联表，但必须复用统一访问政策，并在分页、计数和聚合之前过滤权限。
- 模块维护自己的业务不变量。公共能力显式导出；消费者、sweeper、缓存重置和测试注入入口
  不进入公共门面，生产门面不得整体 `export *`。
- `read-models` 可依赖业务模块的只读能力；业务模块不得反向依赖搜索、榜单或页面查询。
- `runtime` 不反向依赖业务模块；存储引用和容量等业务规则留在 `assets`。
- 生产代码的模块运行时依赖必须无环；类型依赖单独检查，不能通过类型文件间接引入运行副作用。
- 仅在外部能力需要替换时引入接口（数据库、存储、邮件、时钟、Gateway 客户端）；普通业务
  函数保留直接调用方式，不引入依赖注入容器。
- 简单 CRUD 保持紧凑实现；跨模块流程才增加编排层，不要求每个函数套多层模板。

## 4. 子系统设计

### 4.1 身份、授权与事务

~~~ts
type Actor =
  | { kind: "guest" }
  | { kind: "user"; userId: UserId }
  | {
      kind: "system";
      purpose: "bootstrap" | "migration" | "background_task";
    };
~~~

- 用户操作要求 `UserActor`；移除缺省 root、旧角色字符串参数以及从多个位置猜测身份的逻辑。
- 系统身份仅由启动、迁移和后台任务装配点创建，不能由 HTTP 请求字段构造。
- 将数据库根连接与事务句柄分开。需要锁、原子事件登记或多表更新的内部函数要求 `DbTx`，
  不接受 `RootDb | Tx` 联合类型；业务函数不接收 Hono Context。
- 应用用例负责事务，内部函数不自行猜测是否再开事务；独立可调用入口与事务内部实现使用不同
  函数。
- 写入继续遵守统一锁序；上传、下载和上游模型执行放在数据库锁外，受理前在事务内重新确认
  权限、版本和配额。授权结果只在当前请求或事务内复用，不跨请求缓存成员资格与共享授权。
- 跨服务管理请求保留有界超时、revision 与请求幂等；成功以远端持久提交为准，不声称跨库
  原子性。

授权政策集中在明确的只读政策层，由应用用例和读模型调用：账户与空间访问、源资源共享、比赛
保密、教学关系各具唯一事实解析与判断入口；列表与单资源读取复用同一组 SQL 可见性条件，禁止
先分页再过滤；“查看学情”“查看提交源码”“查看题目内容”继续是不同能力。

### 4.2 数据库、测试与运行装配

- 生产数据库模块仅保留连接创建、事务和关闭；删除 PGlite 适配、手写 schema DDL、模板指纹与
  测试事务代理。测试辅助代码移到测试目录。
- 所有数据库测试使用正式迁移建立结构。测试启动器创建独立测试模板库，各分片从模板复制独立
  数据库；普通路由测试通过明确的清理与种子恢复隔离，需要并发验证的测试使用真实独立连接。
  不再拦截数据库连接、伪装整组业务操作处于某个测试事务中。
- 测试命令不隐式读取开发 `.env`；只清理本次创建的数据库与 Redis 命名空间。纯判分、策略
  选择、格式转换等单测不启动 PostgreSQL。
- 数据库迁移由安装或升级步骤显式执行；生产 HTTP 服务启动只检查 schema 是否匹配，不执行
  DDL 或隐式初始化。开发 `dev-setup` 继续串联迁移、种子和初始化。
- 新迁移只追加、由工具生成，不修改历史迁移和 `_journal.json`。
- Core 与 Gateway 均由装配层显式创建依赖、应用与后台任务，不引入 DI 容器：

~~~ts
interface ManagedTask {
  stop(): void;
  done: Promise<void>;
}
~~~

关闭顺序：停止新写入与新任务领取 → 等待在途操作 → 关闭长连接 → 关闭 Redis 与数据库。
配置继续区分启动配置与业务设置；单 Core 的派生配置使用不可变快照，数据库提交后原子替换；
计费、任务进度与 Judge 资源租约继续持久化。单实例假设同步登记到工程文档。

### 4.3 持久后台任务与事实投影

建立一套小范围持久任务原语，服务评测派发、搜索更新、教学投影和通知发送：

- 登记任务必须传入业务事务；返回成功表示任务记录已随业务提交。任务保存类型、去重键、必要
  定位字段、执行时间、重试次数、租约和处理结果，不保存临时 token 或签名 URL。
- 每个处理目标单独登记任务、独立重试；批量重测等业务任务表继续表达业务进度，后台任务仅负责
  可靠执行，不吞并业务状态机。
- 领取使用数据库锁与租约；续租、完成和失败必须校验领取令牌。指数退避，最长间隔五分钟；连续
  失败二十次进入失败状态，提供明确的人工重试入口。
- 重复处理以业务唯一键、revision 或尝试状态实现幂等；不承诺外部邮件等副作用恰好一次。
- 搜索以数据库事实重建索引；教学投影依据最新有效成绩与版本策略重算，不累加事件成绩。
- 统一记录积压量、最老任务年龄、失败数和投影延迟。SSE 用于实时提示与重放，REST 与数据库
  事实用于最终校准。
- 已有教学 outbox 分阶段迁入：先保留原任务身份与处理状态，再切换生产者，最终删除旧 worker。
- 评测提交成功时数据库必须同时存在可恢复的派发依据。Redis 传输暂不可用时，完整受理的提交
  保持 pending 并在恢复后自动派发；无法验证必要准入条件时明确拒绝，不返回虚假的受理成功。

### 4.4 题目、提交、比赛、教学与对象存储

- 题目发布、切换有效策略、重测继续是独立动作。评测尝试写终态、更新正式判定和重算有效成绩
  在一个事务内完成；平台错误保留已有正式成绩。
- 客观题内容归 `problems`，判分与尝试归 `evaluations`；本轮保留现有物理表和 ID。
- 提交受理形成明确执行计划：使用域、源题、绑定、版本、比赛或作业来源及冻结的运行选择。比赛
  和教学通过显式执行上下文复用受理流程；评测模块不反向调用比赛或教学服务寻找上下文。
- 普通题与客观题复用尝试、正式判定、有效成绩及教学通知流程；客观题保留即时执行器。
- 共享撤销即时影响资源读取；历史成绩与历史提交按既有规则保留。搜索、统计、个人历史和文件
  下载一起参加权限验收，防止辅助入口绕开主路径。
- 对象存储保留已建立的状态机与预约/删除互斥：`assets` 统一提供上传预约、完成登记、绑定和
  删除入口；业务代码不直接删除物理对象、不自行拼装交付 URL；版本引用不因后台清理或上传补偿
  被删除；有效交付链接按请求签发。
- 区分“对象明确不存在”和“存储服务无法确认”，不把网络故障写成资源丢失。本轮沿用现有引用
  结构，不增加通用多态引用表。

### 4.5 Judge：单次运行的生命周期

- `WorkerContext`：Docker、Redis、路径、缓存、安全限制与调度器。
- `RunContext`：已验证任务、运行标识、取消信号、资源租约和本次创建的容器。

执行流程固定为：解码与验证 → 准入与领取 → 准备资源 → 执行后端 → 构造可信结果 → 可靠投递
→ 确认消息 → 释放资源。AI 双容器、prediction、OI Native、OI WASM 保留各自执行实现，通过
明确枚举分派；保留现有资源池、公平性、内存预算与 WASM 成本标准。

- 相同运行标识具有执行租约；租约丢失时取消执行并显式等待清理。
- 正常、错误和取消路径都执行异步清理；Drop 与启动清扫承担异常兜底。
- 结果持久投递成功或写入可恢复本地 fallback 后，才能完成确认流程；恢复行为使用同一运行标识
  去重。核对公平性实际作用范围，使配置名称、注释与测试一致。
- 评测协议升为 v3：显式区分正式提交与自测（`task_kind`），不再按 ID 前缀识别；正式提交
  必须携带尝试、版本和重判序列，自测必须携带明确自测运行标识；必需字段不再用历史缺省值补齐；
  可信封套与 evaluator 可控 details 分开校验；未知协议与缺失必要字段进入可诊断拒绝路径。
  调度协议与 WASM 成本标准保持独立版本。TS 与 Rust 同步手写修改，扩展正例、反例与序列化
  夹具；本轮不引入生成链。

### 4.6 Gateway：集中配额政策与账本所有权

Gateway 持有 Provider、模型映射、实例配额上限、域配额、调用预占与结算账本：

- Core 当前持有的实例 LLM 配额政策迁入 Gateway，由其自身迁移管理；Core 验证管理者权限后
  调用内部管理接口，Gateway 完成 revision 比较、政策写入与审计。
- 配额修改成功以 Gateway 持久提交为准；超时通过操作编号查询结果或幂等重试，避免重复创建。
- 新调用预占时读取当前持久政策，不再回调 Core；降额后新受理调用使用新政策，已预占调用按既有
  账本结算，紧急停止仍走显式撤销机制。
- 保留当前冻结 Domain、Provider、模型与预算的尝试语义；Provider Key 只在 Gateway 内解密。
- 保留持久调用账本、不确定调用状态和可重放结算；网络中断不自动触发可能重复计费的上游请求。
- ready 实际检查数据库、Redis 与记账 worker；关闭时停止领取新结算任务并等待在途工作。
- 迁移在维护窗口执行：读取旧政策 → 写入 Gateway → 校验值与 revision → 切换读写入口 →
  停止旧回查 → 后续清理批次删除旧设置；不重置当日用量，不重新解释已有 token 预算。

### 4.7 Core 读模型与 Nuxt

新增域内批量题目摘要接口：

~~~text
POST /api/v1/domains/:slug/problem-summaries
~~~

单次最多五十个引用，返回调用者可见的标题、题型、作答版本、可用性及本人进度。单项不可访问时
返回统一不可用结果，不区分不存在与无权访问；查询使用批量授权与集合查询，不循环调用题目详情
服务。

Nuxt 保留按视图聚合的 BFF，但改变消费方式：

- 首页、班级、作业、题单分别定义明确页面返回类型；页面加载器持有页面数据，子组件通过 props
  或明确上下文消费。
- 移除通用 unknown section 信封与首屏快照向多个异步键注入的桥接逻辑；全局中间件处理导航与
  身份守卫，具体页面入口加载首屏数据。
- 页面统一消费首屏数据，局部操作使用细粒度刷新；会话状态区分未加载、已验证登录和已验证匿名；
  可读 Cookie 仅用于显示提示，不提供权限判断。
- SSR payload、水合和 SPA 导航使用同一组数据键规则；身份与空间变化立即使旧请求失效。实时
  刷新统一绑定账号、空间、资源和页面代次；SSE 与轮询共享取消机制，轮询串行执行；旧响应不写入
  新页面。
- 题单继续每页二十题，作业按当前页批量补齐标题；每个 BFF 内身份与空间上下文各解析一次。
- 验证 1440、768、390px 与键盘操作；首屏水合不重复请求已包含的数据。

### 4.8 CLI 升级与发布集

- 正式发布使用一个发布集清单，记录组件镜像 digest、迁移级别、协议版本、CLI/IDE 版本与 SDK
  标准摘要。CLI 始终使用同一份已解析发布集进行验签、迁移和启动，目标资产验证必须在启动前
  完成。
- 维护窗口执行顺序：
  1. 解析目标发布集，检查磁盘空间、配置与备份能力，拉取并验签目标资产。
  2. 停止新提交与新重测受理，让已受理评测继续派发和完成。
  3. 等待任务队列、processing、在途尝试和结果 fallback 完成恢复；确认所有登记的 Judge 节点
     状态。
  4. 暂停任务领取，停止服务，创建一致性备份并验证备份结构。
  5. 显式执行 Core 和 Gateway 迁移。
  6. 启动同一发布集的服务，验证真实依赖、节点版本和代表性正常用户流程。
  7. 写入成功部署记录，解除维护状态。
- 排空默认超时三十分钟，可由 CLI 参数调整；超时终止升级，不强杀任务或清空队列。远端 Judge
  由其所在节点 CLI 升级，服务端根据节点报告验证结果。
- 升级保留步骤日志，支持从已知状态检查与恢复。迁移前失败保持旧发布集；迁移后失败保持维护状态，
  通过明确的备份恢复流程回退，不能只换回旧镜像。
- 旧默认域写入与执行别名在协调发布中退役，保留一个发布周期的 `410 ENDPOINT_RETIRED` 提示，
  然后删除。现有显式域路由与可保留的页面深链接继续工作。

## 5. 实施批次

每个批次独立提交、独立验收，经 PR 合入 `main`。使用 jj、GPG 签名与中文提交；非平凡变更
新增 Agent Note。

| 批次 | 内容 | 完成标准 |
|---|---|---|
| P0：冻结基线 | 固定受审版本，登记模块、表和后台任务所有权；记录代表性请求、查询与行为基线 | 当前本地 UI 提交与 `main` 的归属清楚，架构改造不夹带未说明的已有工作 |
| P1：修复安全顺序 | 验签前置、迁移锁失败终止、Gateway 真实探针；加入升级排空的过渡能力 | 故障测试证明失败时不会启动目标镜像或执行无锁迁移 |
| P2：运行与测试底座 | 显式 Runtime、受管后台任务、隔离 PostgreSQL 测试；删除 PGlite 与手写 DDL | 标准任务能从干净环境运行，生产连接不再导入测试适配 |
| P3：业务所有权 | 身份与事务接口收紧；按用例迁移模块、授权政策与门面 | 无缺省 root、无模块运行时循环、无跨模块写服务调用 |
| P4：可靠执行 | 持久后台任务、搜索修复、教学投影迁移与可观测性 | 提交后崩溃、重复领取、Redis 中断均有确定恢复结果 |
| P5：Gateway 收敛 | 配额权威迁移、去掉 Core 回查、完善关闭与记账验收 | Core 暂时离线不影响已授权调用的配额读取与记账 |
| P6：Judge 整理 | Worker/Run 两种上下文、统一结果与清理、必要协议 v3 改动 | 多 Worker、租约丢失、取消和 fallback 回放通过 |
| P7：读取与前端 | Core 批量摘要、页面独立 BFF、会话与刷新收敛；同步 IDE | 题目数量增长不再增加逐题 Core 请求，首屏水合无重复取数 |
| P8：协调发布与删除旧路 | 发布集、升级演练、旧接口与适配清理、文档和门禁同步 | 完成存量升级、正常用户旅程和备份恢复演练 |

P1 的过渡能力保留旧评测协议，用于先升级现有节点，使后续协议切换具备排空和版本报告能力。

## 6. 验收标准

### 6.1 必须通过的行为验收

| 类别 | 场景与结果 |
|---|---|
| 身份 | 缺少用户身份不能执行用户写入；系统身份无法从 HTTP 构造 |
| 权限 | 共享撤销、成员移除、模块关闭、比赛保密对详情、列表、搜索、统计和下载同时生效 |
| 事务 | 授权依据变化与受理并发时，不留下越权受理或半完成写入 |
| 版本与成绩 | 发布、切策略、重测互不混淆；重复、过时结果不覆盖正式成绩；平台错误保留历史判定 |
| 后台任务 | 数据库提交后进程退出仍可恢复；重试不重复物化成绩；失败任务可定位和重试 |
| Judge | 多节点资源预算有效；同一运行租约、取消、续租失败、容器清理和 fallback 回放符合约定 |
| Gateway | 降额后新预占受限；重复结算不重复扣量；未知上游结果不自动重发；数据库故障导致 ready 失败 |
| 数据库测试 | 空库与有代表性存量数据的升级均通过；并发与约束在真实 PostgreSQL 执行 |
| Web | SSR、水合、SPA、身份切换与旧请求晚到均正确；验证 1440、768、390px 和键盘操作 |
| 升级恢复 | 验签失败不启动；迁移锁失败不执行 DDL；中途退出可检查；备份能真实恢复并完成用户流程 |

Deno 测试继续通过 `deno task` 执行；模块迁移时同步调整规定的测试入口。CI 中要求的依赖
缺失直接失败，不能以忽略用例代替成功。

### 6.2 性能与结构验收

- 题单和作业的当前页摘要采用批量读取；增加页内题目数不增加逐题 Core HTTP 请求。
- 摘要查询只取需要字段，不读取完整题面、答案或运行配置；首屏水合不重复请求已包含的数据。
- 记录浏览器请求数、Core 请求数、SQL 数量、响应体积及冷暖延迟，使用固定数据集比较。
- 生产数据库模块不包含测试数据库后端、手写测试 DDL 和全局测试状态重置。
- 模块公共入口没有整体转出的内部实现，运行时依赖无环。
- Core 与 Gateway 的后台任务均可停止并等待完成，数据库关闭后不再有后台写入。
- Core 不再持有 Gateway 配额政策的第二份权威状态。

### 6.3 文档、门禁与收尾

交付内容包括目标架构图、模块与表所有权、授权入口、任务恢复说明、接口退役表、发布集格式、
升级与恢复手册，以及各批次验证记录。现有门禁随结构调整：边界检查验证实际依赖方向；测试与
CI 模块映射使用同一份工程元数据；删除 PGlite 后同时删除对应 parity 门禁与失效文档。每条
保留的关键门禁都要有“故意破坏后确实失败”的反例测试。

本轮保留已有业务状态机、计分单位和 WASM 标准；数据库结构变化集中于可靠任务与政策所有权
所需部分。跨语言契约生成留待后续单独讨论。

## 1. 目标

在**正式举办公开赛之前**，对 Neuro OJ 做一轮定向审计并**自行完成修复**，消除四类可能
导致开赛事故的缺陷：

1. **评测机被卡**（评测槽位被占死 / 队列停摆 / 资源耗尽）；
2. **容器逃逸**（沙箱容器触达宿主或内网基础设施）；
3. **数据泄露**（赛题、隐藏用例、他人提交与成绩在赛期泄露）；
4. **竞赛公平性受影响**（赛中可串通、可交流解法、可探测他人进度）。

四轴之外，用剩余预算对**上一轮审计过的面做二次审计**，并对其余模块做广度审计。

**反作弊系统的功能设计与改进不在本轮范围内**（用户明确排除）——本轮只修"可能被利用
或导致既有防护静默失效的 bug"。

## 5. 执行协议

### 5.1 串行 subagent 的硬实现

- 每次**只调一个 subagent 并前台等待返回**；严格"同一时刻 ≤1 个 subagent 活动"。
- **明令禁用会引入并发的设施**：Agent Teams（`spawn_teammate`）、`workflow` 扇出、
  任何多 subagent 同发。理由：会触达 DeepSeek API 并发上限，使整晚结果不可信。
- 可并行的只有**非 API 作业**（cargo 编译、门禁、docker、测试），走后台 job 执行，
  与 subagent 串行不冲突。
- **超时熔断**：单次派发超预算（>25 min 未返回）视为失败，记录后可重派 1 次；
  再失败即弃面并记录。

### 5.2 两类审计任务

| 类型 | 适用面 | 任务书的额外要求 |
|---|---|---|
| **I 新面审计** | 未审过 / 无对应整改 | 完整面清单 + 触发路径 |
| **II 已审面二次审计** | 9-28 VULN-01..22 覆盖域、9-05 作弊审计、9-15 全量审计 | 任务书**必须附带上一轮结论清单**，并显式要求两件事：**(a) 对每条已宣布修复的 VULN 构造绕过尝试**（验证修复是否真成立，而非重跑结论）；**(b) 漏网搜索**——找同类但上一轮未枚举到的路径 |

### 5.3 subagent 任务书模板（每面按此填充）

```text
你是 Neuro OJ 的定向安全审计员。本次审计面：<面名>。任务类型：<I 新面 / II 二次审计>。

【仓库】/home/xyber-nova/Github/neuro-oj
【约束】
- 只读审计：**不得修改任何文件**，不得提交、不得推送。
- 搜索必须用 rg（本仓约定），不要用 grep。
- **否定性结论**（"不存在"/"已修好"）必须给二次检索证据：同义词 + 行为描述各再检索一次。
  仓规：`grep 0 命中 ≠ 不存在`（历史教训：把真实存在的 fuzz 测试误判为"文档虚报"）。
- 每条 finding 必须是**可复现的**：给最小触发路径（请求样例 / 命令 / 测试），
  不接受"可能有风险"的推测式结论。

【上一轮既有结论（类型 II 必读；类型 I 也需读以避免重报）】
<paste: 相关 VULN 清单 + 残留表 + 对应 Agent Note 摘要>

【主攻方向】<面清单>
【交付】只输出结构化报告，不要输出过程叙事：
| id | 严重度 | 位置 file:line | 触发路径/最小 PoC | 影响面（谁能触发、后果） | 与上一轮关系 | 复核建议 |
外加两节：<① 已审但未发现问题的子面清单（附检索证据）>、<② 我认为需要人工裁决的设计级问题>
【严重度口径】Critical=可直接导致开赛事故（卡死评测/逃逸/整题泄露/赛中批量串通）；
High=单点可利用且有实际后果；Medium=需要前置条件或影响有限；Low=加固建议。
```

### 5.4 复核（防假阳性）

- subagent 返回后，Lead 做复核；当 finding 数 **>5** 时，**另派一个 verifier subagent**
  专门做证伪尝试（与首轮任务书不同：verifier 的任务是**尽力推翻**每条 finding）。
- 门槛口径（可判定）：`≤5 条 → Lead 自审`；`>5 条 → 另派 verifier`。
- **三态结论**：确认 / 证伪 / 存疑。**只有"确认"进入修复**；证伪进报告并附证伪证据；
  存疑进"待人工裁决"。
- **假阳性率（证伪数 / 总数）作为审计质量指标写入报告。**

### 5.5 修复循环（每个面一轮）

```text
subagent 审计 → 报告落盘 → 复核 → 确认项排序 → 逐条修复
  → 反向验证（修复前失败 / 修复后通过）→ 模块门禁 → root 门禁
  → Agent Note → jj describe + jj new → 该面 bookmark
```

**交付粒度**：**每个面一个 bookmark + 一个 Draft PR**（面内每条修复各自成一个 jj change，
便于逐条 review 与单独回滚），PR base 指向栈内前一个 bookmark。
理由：11 个面若每条修复一个 PR 会到 20+ 个，评审不可读且 base 链易乱。

## 6. 验收标准

设计原则：**无人值守下最大的敌人是"假绿"**（本仓历史反复出现：写了测试却永不执行、
门禁双入口分叉导致本地绿 CI 红、陈旧镜像掩盖真实缺陷）。因此每条标准都必须**可证伪**。

### L0 — 会话级红线（任一违反即整晚结论作废）

1. **`main` 零改动**，四条判据同时成立：
   - ① 会话开始记录的 `origin/main` SHA（`6dbdd76b`）在会话结束时**不变**；
   - ② 本地 `main` bookmark **不前进**；
   - ③ `git rev-list --count origin/main..<bookmark>` = 该 bookmark 的预期提交数；
   - ④ 无任何对 main 的 push / merge / tag。
   > 9-11 教训已入库：`git log HEAD..origin/main` 为空**不构成证据**——栈基是 main 的
   > 后代时，该条件对正确的与错误的 agent 恒真。
2. **不触碰**：`_journal.json`、`deno.lock`、`Cargo.lock`、`.env.prod`、真实凭据、生产库。
3. **全部提交 GPG 签名有效** + 中文 Conventional Commits（抽样验证）。
4. **并发约束**：全程同一时刻 ≤1 个 subagent；不使用 Agent Teams / workflow 扇出。
5. **工作副本可续**：每个 change 自成可编译/可检查单元；进度日志随时可续。

### L1 — 审计本身的质量

每条 finding 必备字段：位置 `file:line` · 类型（I/II）· 所属轴 ·
**触发路径或最小 PoC** · 影响面 · 严重度 · **与上一轮 VULN 的关系**（新发现 / 已修但仍可
绕过 / 上轮已裁定的重提——后者必须带新证据，否则视为噪声）。

- **复核三态**：确认 / 证伪 / 存疑（口径见 §5.4）。
- **假阳性率必须写入报告。**
- **否定性结论**必须给二次检索证据。
- 报告必须**同时列出"审过但未发现问题的子面"**（否则无法区分"审过没问题"与"没审"）。

### L2 — 修复质量（每条修复，成对证据）

1. **复现–阻断成对证据**：修复前能触发（PoC 输出或失败测试），修复后不能触发。
2. **回归测试反向验证**：新增测试必须在**修复前失败**（临时回退验证一次），
   证明它不是恒真空测试。
3. **不新增静默跳过**：`silent-skip-report.ts --check` 绿；确需新增则按门禁口径说明原因
   并更新基线。
4. **门禁全绿**：相关模块 `deno task check` / `cargo clippy`；root
   `deno run -A scripts/check-all.ts`；judge 改动跑 `cargo nextest run --all-targets`；
   触及域跑规定命令 `deno task test:domain <domain>`（**不手拼 `deno test`**）。
5. **不回归既有测试**：与前置基线快照对照，失败数不增加；基线若不绿，先定性"是否 main
   固有"（判据：在 `origin/main` 的独立副本上复现同样失败）。
6. **高危类附加**：影响面说明 + 回滚方式（revert 哪个 change 回到安全态）+ 可执行验证步骤
   （迁移：空库与存量库两种形态都跑；拓扑：`docker network inspect` 实测）。
7. 每条修复一个 Agent Note，`verify-agent-note-format.ts` 通过。

### L3 — 四轴的可判定断言矩阵

每条：**输入 → 期望 → 实测输出**。

**A 评测机可用性**
- A1 单次恶意提交不能永久占死槽位（塞死对端 stdin / 无限输出 / 拒退）→ 槽位在有限时间内
  释放且后续任务仍被消费
- A2 总超时在所有路径有效（写管道阻塞、evaluator 先死、支持包注入中）
- A3 Worker 崩溃重启后孤儿容器被回收（实例标签跨重启稳定，实测）
- A4 资源限制不可绕过：pids / 内存 / 写满磁盘 / 执行时间 / 输出量
- A5 单条任务不整体阻塞队列（背压与优先级语义）

**B 容器逃逸**
- B1 沙箱容器**既无 DNS 也无路由**到 postgres / redis / minio / core（真实 e2e 网络实测）
- B2 不能经网关 IP（`172.17.0.1`）触达宿主或同宿主其他容器
- B3 不能访问宿主 docker socket；`no-new-privileges` 生效；cap 全丢
- B4 tmpfs `noexec/nosuid/nodev`；挂载面无宿主敏感路径
- B5 产物/支持包解压拒绝路径穿越、绝对路径、symlink/hardlink 逃逸、解压炸弹
- B6 Evaluator 只能触达允许目标（llm-gateway），且是**物理层**保证而非配置约定

**C 数据泄露**（判据：任一读路径被遗漏即**整轴不通过**）
- C1 未结束公开赛（**含赛前筹备期**）内，非特权用户与匿名经任一读路径都拿不到
  题面 / 标题 / 难度 / 标签 / 存在性
- C2 隐藏用例与标准答案不漏（列表 / 详情 / 下载 / bundle / 报错 / 日志 / SSE 任一形态）
- C3 他人提交内容、结果、得分、排队位置不可见（含匿名与非所有者）
- C4 判分 oracle 不可用（无 correct / 分数 / 通过率回显可做二分探测）
- C5 日志、错误响应、SSE、审计接口不泄露内部地址 / 凭据 / 路径 / 角色

> 路径矩阵必须**穷举**：列表 / 详情 / 搜索 / 题单 / 个人主页 / 导出 / 导出快照 / SSE /
> 队列 / 统计 / 管理端非特权视图……

**D 赛时公平性**（不含反作弊系统设计）
- D1 赛中无可用通信信道：答疑默认私密、题解/讨论门控**赛前即生效**、私信/社区边界明确
  且不可用于广播解法
- D2 无法探测他人进度：排名 / 提交数 / 耗时 / 评测完成时点不构成侧信道
- D3 提交回执无 oracle；重测与提交次数上限在**服务端**强制（非前端提示）
- D4 封榜与结算时序无倒挂（封榜期非管理员只见本人）
- D5 VULN-04/05 给出明确裁定：维持 or 新证据升级

### L4 — 交付完整性

- **证据文档**：finding → 复核结论 → 修复 → 成对证据（命令 + 输出）→ change/PR 链接
- **工作日志**：时间线 + 每面状态
- **待人工 review 清单**：未取证 / 存疑 / 被证伪 / 设计级问题（含被排除的反作弊系统设计
  建议、`noj-cli` 与 `noj-lmcc-extension` 未审提示）
- **Draft PR 清单**（逐条声明 base）
- **"未取证"规则**：无法在本环境取证的项一律不得标"完成"，只能是"已修待复验"或"未开始"，
  并写明复验条件（真实 LLM Provider、生产拓扑、GPU 等）

### L5 — 整晚成功判定

| 结论 | 判据 |
|---|---|
| **成功** | L0 零违反 + 四轴断言矩阵**全部有结论**（通过 / 失败并已修 / 明确标注未取证） |
| **可接受但未完成** | L0 零违反 + 每轴都有"审计结论 + 已修项 + 未完成项说明" |
| **失败** | L0 任一违反，或有轴**既无结论也无说明**（沉默遗漏是最坏结果） |

## 7. 熔断、截断与"停下上报"

- 单条 finding 修复尝试**上限 3 次**，超限记录根因并跳过；**不做半成品提交**。
- **06:00 后不开新面**，只做收尾。
- **07:00 硬停**：立即停止开新工作，把当前轮写到可提交状态再收尾（不留半写坏的工作副本）。
- 高危类若**拿不到 before/after 证据**，该 change **不进入栈**，降级为报告里的"补丁提案"。
- **必须停下等 Owner（不自行决定）**：
  1. 需要改 main / 打 tag / 发 Release / 合并 PR；
  2. 发现**生产已被入侵或数据已泄露的迹象**（立即留证并停止自动修改）；
  3. 需要动 `.env.prod`、真实凭据或生产数据库；
  4. 问题属"设计级变更"（含被排除的反作弊系统设计、需改契约者）→ 记入待人工清单，不改；
  5. **栈基被他人推进导致冲突** → 停下上报，**不自行 rebase 强推**（9-11 spec 点名的
     结构性风险）。

## 9. 风险与处置

| 风险 | 处置 |
|---|---|
| 基线不绿 → 无法区分"我引入的失败" | 前置阶段先冻结基线快照；不绿则先在 `origin/main` 独立副本上定性是否 main 固有 |
| judge 二进制陈旧导致错误结论 | 强制重建；报告记录构建时间与镜像 digest |
| `noj-eval-net` 从未在本地生效 | 前置阶段起 e2e 栈并 `docker network inspect` 实测 |
| 串行派发导致预算不足 | §4 的阶段切分 + §7 的硬上限与截断；**完整性 > 数量** |
| subagent 误报（假阳性） | §5.4 复核三态；只有"确认"进入修复；假阳性率入报告 |
| 修 high-risk 面引发回归 | §6 L2 成对证据 + 回滚说明；拿不到证据则只交补丁提案 |
| 无人值守卡死 | 单点尝试上限 3 次；每面结束即写进度日志保证可续 |
| 与 Owner 并行改动冲突 | 开工前记录 `origin/main` SHA；会话中若远端前进，按 §7.5 停下上报 |
